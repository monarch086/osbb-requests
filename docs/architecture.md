# Архітектура

- `Frontend` — Angular SPA. Nginx віддає статичні файли, генерує публічну конфігурацію та проксіює `/admin/*` до Web API.
- `OsbbRequests.WebApi` — локальний ASP.NET Core API. Cognito підтверджує особу, а застосунок перевіряє активність, ролі та права за даними PostgreSQL.
- `OsbbRequests.CommandListener` отримує Telegram updates через long polling. `OsbbRequests.CommandProcessor` обробляє команди та зберігає результат разом із записом за update ID, щоб повторна доставка команди не виконувала її знову.
- `OsbbRequests.Jobs` запускає завдання Hangfire для доставки сповіщень, записаних у PostgreSQL у тій самій транзакції, що й відповідна зміна. Якщо Telegram отримав повідомлення, а запис про доставку зберегти не вдалося, можливе повторне повідомлення.
- `OsbbRequests.Domain`, `OsbbRequests.Services` і `OsbbRequests.Shared` містять моделі, бізнес-операції та спільний код. `OsbbRequests.Postgres` реалізує сховища і містить міграції.
- `serverless.yml` керує Cognito та CloudFront з функцією редіректу. Стара CloudFront-адреса зберігає шлях і повертає `302` на `zeleniy-ostriv2.com`.

## Локальний Web API

`OsbbRequests.WebApi` працює через ASP.NET Core і Kestrel у Compose на `127.0.0.1:8082`. Контролери використовують спільні сервіси з `PostgresAdminStore`. Моделі EF Core та міграції лежать у `OsbbRequests.Postgres`. Контейнер Web API отримує лише конфігурацію Cognito й доступ до PostgreSQL. Для Cognito GetUser використовується access-токен, клієнт SDK створюється без AWS credentials.

Параметри маршруту, фільтри й JSON у локальному Web API прив’язує ASP.NET Core. Некоректний JSON повертає `400` з полем `error`, непідтримуваний тип тіла повертає `415`, а тіло понад 30 003 байти повертає `413`.

Сервіс `frontend` у тому самому профілі Compose збирає Angular і віддає адмінпанель через Nginx, типово на `127.0.0.1:8083`. `OSBB_FRONTEND_BIND` дозволяє прив’язати порт до адреси в локальній мережі. Nginx формує публічну конфігурацію Cognito та середовища під час запуску контейнера, проксіює `/admin/*` до `web-api` в мережі Compose та повертає `index.html` для прямих переходів за маршрутами Angular.

Усі дані обмежені джерелом імпорту та комплексом. Початковий імпорт був одноразовим. Локальний API працює з `osbb_dev`. Права адміністратора зберігаються у локальній базі. Локальний API читає `administrators."IsSuperAdmin"`. Міграція заповнює цю булеву колонку зі знімка, отриманого під час початкового імпорту з DynamoDB. Атрибути `RequireAdminAccess` перевіряють активність і дозволи. Зміни, аудит, перевірки версій та постановка подій `LOCAL_PENDING` виконуються транзакційно. Події PostgreSQL доставляє окремий контейнер `OsbbRequests.Jobs`.

PostgreSQL і DynamoDB формують поле `changes` нових подій редагування заявки зі спільного контракту. Воно містить відповідального, пріоритет, планову дату, видимість, місце й ознаку зміни серійних номерів ключів.

### Локальна доставка сповіщень

`OsbbRequests.Jobs` реєструє щохвилинне завдання Hangfire в PostgreSQL і запускає спільний `NotificationProcessor`. Робоча черга міститься в `notifications`, службові записи планувальника — у схемі `hangfire`. Воркер бере лише `LOCAL_PENDING` у налаштованому комплексі, перевіряє одержувача перед надсиланням і зберігає узгодження `message_id` → заявка для відповіді мешканця. Розгортання аудиторії розсилки й оновлення позиції в ній виконуються в одній транзакції.

Для кожної спроби є 90-секундна оренда. Після тимчасового збою завдання зберігається до повторної спроби. Якщо процес завершується між надсиланням і записом результату, Telegram може отримати повідомлення повторно. Результати доставки без тексту й відповідності для відповідей зберігаються 30 днів.

## PostgreSQL

Файл `.env.data.dev` задає назви баз, пароль і рядки підключення для хоста й контейнерів. Спільна оболонка Angular показує стрічку для `environment=dev` на всіх маршрутах. `OSBB_DATA_ENV_FILE` вибирає такий файл для локальних скриптів. Compose передає рядок підключення кожному споживачу окремо. Скрипт запуску Web API бере Cognito ID із цього файлу й працює з налаштованою робочою базою. Web API і бот обирають комплекс безпосередньо через `complexes`.

Початковий імпорт DynamoDB був одноразовим. Похідні таблиці зберігають мешканців, заявки, ключі, історію, повідомлення, сповіщення, аудити, доступи та статистику. `source_records` містила тимчасову JSON-копію; `DropEmptySourceRecords` видаляє її лише за умови порожнечі. `RetireImportMetadata` видаляє каталог `import_sources`, журнал `import_runs` та FK до каталогу. API знаходить комплекс за його зовнішнім ID у `complexes`. `SourceId` поки лишається ключовою областю в робочих таблицях. Імпортер вилучено після одноразового перенесення.

У довіднику `complexes` зовнішній ID комплексу зберігається один раз у локальній базі. Мешканці, заявки, розсилки, сповіщення, квартири й членство використовують числовий `ComplexId`. Профіль має внутрішній ID та унікальну пару «комплекс + Telegram user ID». Телефони й згоди посилаються на профіль через `ResidentId`. Для історичних квартир і членства цей зв’язок може бути відсутнім. ID реєстрації та відомості про перевірку зберігаються в самих історичних записах.

У PostgreSQL поля профілю мешканця зберігаються в окремих колонках таблиці `residents`. Міграція переносить значення з наявного `Payload` до видалення колонки, тож повторний імпорт для перенесення даних не потрібен.

Телефони мешканця зберігаються в `resident_phones`. Частковий унікальний індекс дозволяє щонайбільше один основний номер на профіль. Дата й версія згоди містяться в `resident_consents`. Відсутність дати за наявної версії означає, що згоду ще не надано. Телефон у `request_key_items` фіксується на момент замовлення. Для `api_daily_statistics` ключ складається з джерела, UTC-дати типу PostgreSQL `date` та ендпоінта.

Таблиця `requests` зберігає поля заявок в окремих колонках. Статус, видимість і тип локації зберігаються як назви значень, планова дата має тип `date`, а ключі зберігаються в `request_key_items`. Міграція переносить поля й додає відсутні рядки ключів із `Payload` без повторного імпорту.

`requests.Version` зберігає версію заявки й перевіряється перед зміною в адміністративному API. Ключі заявки зберігаються у `request_key_items`. Редагування й видалення ключів фіксуються у `resident_events` з адміністратором, датою, ідентифікатором заявки та значеннями до й після зміни. Відсутній тип після зміни позначає видалення ключа. Ці події прив’язані до реєстрації мешканця та можуть зберігатися після видалення заявки.

Таблиця `administrators` зберігає email, ім’я, активність, версію та дати в окремих колонках. Доступи й налаштування сповіщень містяться у пов’язаних таблицях. `resident_memberships` зберігає ID реєстрації, виконавця й час перевірки в окремих колонках.

Додаткові квартири зберігаються в `resident_apartments` по одному рядку на квартиру.

Міграція `RemoveProjectedSourceRecords` видаляє сирі копії після звірки з типізованими таблицями та прибирає стан діалогів старого бота. `NormalizeLegacyRegistrationHistory` переносить версії реєстрацій у `resident_registration_snapshots`, а старі рішення про доступ — у `resident_membership_history`. Історичні записи не змінюють поточний профіль або права. При видаленні профілю локальний бот очищає ім’я, контакти, адресу й текст рішення в архівних знімках.

Міграція `NormalizeNotifications` переносить дані черги, результати доставки та прив’язки Telegram-повідомлень до заявок із JSON у типізовані колонки `notifications`. Імпортований TTL зберігається окремо в `LegacyExpiresAt`; воркер очищає локальні записи за `ExpiresAt`. Після завершення доставки воркер очищає текст, ідентифікатор одержувача й решту даних черги.

Міграція `NormalizeResidentAndRequestEvents` переносить історію мешканців і заявок у типізовані колонки. `resident_events` зберігає рішення про реєстрацію, зміну типу та імені й деталі змін ключів. `request_events` зберігає автора, дію, статуси, пояснення й локацію. Знімок параметрів заявки на момент редагування міститься в `request_event_snapshots` і прив’язаний до конкретної події. Адмінпанель отримує історію в чинному форматі.

У `administrator_events` дія, автор і час події зберігаються в типізованих колонках. Подія зміни доступів містить окремий знімок п’яти прапорців на момент зміни. Міграція `NormalizeAdministratorEvents` переносить ці дані з попередньої колонки `Data` перед її видаленням.

Міграція `RemoveDuplicateLegacyRegistrations` одноразово очистила дублікати у тодішній таблиці `source_records`. Відмінні історичні версії збережено в типізованих таблицях.

Міграція `RemoveObsoleteImportedRecords` одноразово очистила застарілі відповіді й службові проєкції. Прив’язки повідомлень до заявок залишилися в `notifications` для обробки відповідей мешканців.

Adminer у тому самому Compose-стеку типово доступний на `127.0.0.1`, порт 8081; `OSBB_ADMINER_BIND` і `OSBB_ADMINER_PORT` дозволяють явно вибрати інтерфейс і порт. HTTP не шифрує пароль або дані. Сервіс чекає готовності PostgreSQL і використовує `postgres` як адресу сервера у внутрішній мережі. Автоматичного входу немає: користувач вводить наявні облікові дані PostgreSQL; пароль не передається як змінна Adminer.

`scripts/osbb-data backup` виконує `pg_dump --format custom` локальної бази через Compose і перевіряє каталог архіву `pg_restore --list`. Тимчасовий файл має права `0600` і видаляється після помилки; готовий архів публікується лише після успіху, без перезапису. Архіви зберігаються локально в ігнорованому `backups/` або заданому `OSBB_BACKUP_DIR`, містять персональні дані й не охоплюють глобальні ролі PostgreSQL. Це знімок бази, а не узгоджений стан DynamoDB і не гарантія завершеного імпорту.

Відповідь на Telegram-сповіщення про заявку: sender зберігає відповідність `NOTIFICATIONS#<complex>` / `MESSAGE#<owner>#<message_id>` → requestId (раніше записані `USER#<owner>` / `NOTIFICATION_MESSAGE#<message_id>` також читаються) у тій самій транзакції, що й результат доставки. Для старих повідомлень і невизначеного результату відправлення доступна `/comment номер текст`. Команда або відповідь перевіряє активне membership, власника й комплекс; запис історії з update ID, перевірки доступу та receipt виконуються однією транзакцією. Коментар приватний, має до 1000 символів і показується в історії з актуальним ім’ям мешканця. Відповіді на повідомлення з невідомим ID не змінюють поточний діалог. Доставка Telegram має at-least-once семантику: у разі втрати відповіді Telegram або збою після відправлення окреме сповіщення може залишитись без прив’язки, для нього використовується команда.

У деталях заявки на ключі API повертає для кожного телефона структуровані відомості з чинних схвалених профілів: ім’я, будинок і квартиру за наявності. Для сумісності також повертається попередній список імен; пошук та перевірка профілю виконуються один раз для кожного унікального номера.
