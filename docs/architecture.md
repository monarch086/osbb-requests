# Архітектура

## Реалізований каркас

`OsbbRequests.Bot` та `OsbbRequests.AdminApi` — незалежні Lambda з тонкими точками входу та посиланням на `OsbbRequests.Shared`. Runtime — .NET 10, Linux ARM64. Поточна інфраструктура не має сховища даних і дозволів на доступ до нього. Webhook не має HTTP event, API має лише health endpoint.

## Напрям розвитку

Обробники команд відповідають за діалоги Telegram; сервіси — за сценарії та переходи статусів; репозиторії — за сховище; клієнти — за виклики Telegram. API вебпанелі використовує ті самі сервіси й правила доступу. Інтерфейс вебпанелі буде окремим компонентом; фреймворк ще не обрано.

Основні сутності: будинок, мешканець, адміністратор і його повноваження, заявка, категорія, коментар, вкладення, підписка, зв'язок дубліката, запит повторного відкриття, подія аудиту та вихідне сповіщення.

Плановані AWS-компоненти: DynamoDB для структурованих даних, приватний S3 для вкладень, Secrets Manager або SSM SecureString для секретів, outbox із воркером для сповіщень. Остаточні ключі та індекси DynamoDB визначаються з операцій доступу до додавання таблиць у `serverless.yml`:

- заявки мешканця за датою;
- загальнодоступні заявки конкретного будинку;
- адміністративні фільтри за статусом, категорією, місцем та датою;
- коментарі та історія конкретної заявки;
- підписки користувача та підписники заявки;
- невідправлені сповіщення за часом наступної спроби.

Повнотекстовий пошук потребує окремого рішення; DynamoDB сам по собі не забезпечує його. Контакти мешканців не включаються в публічні проєкції чи індекси.

## Правила реалізації

- Перевіряти webhook secret до розбору payload; підтримувати повторні доставки Telegram через стійку дедуплікацію `update_id`.
- Не підключати HTTP event webhook до появи автентифікації та надійного збереження update. У заглушці немає успішного підтвердження обробки.
- Зберігати зміну заявки, аудит і подію outbox узгоджено перед відправленням повідомлення. Повторна доставка Telegram може дублювати повідомлення при неоднозначному мережевому результаті; не обіцяти exactly-once.
- Перевіряти права на сервері для кожної заявки, коментаря, вкладення та підписки; не покладатися на приховані кнопки.
- Доступ до фотографій надавати тимчасовими URL після перевірки прав; S3 залишається приватним.
- Для адміністративних операцій використовувати автентифікацію, перевірку ролей і оптимістичну конкуренцію змін.
- Фіксувати автора та UTC-час кожної зміни; показувати час користувачу в `Europe/Kyiv`.
- Розділити IAM-ролі функцій при додаванні доступу до даних; не додавати wildcard-дозволи.
- Не журналювати payload Telegram, контакти, фото, токени та секрети.
