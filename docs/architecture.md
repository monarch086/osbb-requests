# Архітектура

## Реалізовано

Чотири Lambda з двох ZIP-артефактів:

- `OsbbRequests.Bot.Function` — HTTP webhook, перевірка секрету та публікація в SQS.
- `OsbbRequests.Bot.CommandFunction` — обробка команд із FIFO-черги.
- `OsbbRequests.Bot.NotificationFunction` — щохвилинна доставка автору заявки з транзакційного outbox.
- `OsbbRequests.AdminApi.Function` — публічний `GET /health` і захищені Cognito JWT маршрути `/admin/*`.

Webhook читає тільки свій SSM parameter і має лише `sqs:SendMessage` до черги. Воркер читає тільки токен бота, отримує повідомлення з черги та працює з однією таблицею. API вебпанелі має окрему роль із доступом до заявок і окремої таблиці адміністраторів; запис `IsSuperAdmin` заборонений IAM. Секрети читаються під час роботи, не під час пакування.

`WebhookHandler` перевіряє secret до десеріалізації. До черги потрапляють тільки update ID, user ID, chat ID і текст або власний контакт для реєстрації; групові повідомлення, редагування, боти, вкладення без тексту/контакту та сторонні адресовані команди ігноруються. Повні Telegram payload не зберігаються.

`CommandHandler` маршрутизує команди й перевіряє доступ до комплексу. `CommandProcessor` забезпечує порядок: читання receipt → сценарій → атомарний commit → доставка → delivered. `DynamoCommandRepository` інкапсулює сховище. `TelegramClient` надсилає plain text через довгоживучий HttpClient із 10-секундним timeout; кожен виклик отримує cancellation token.

## Ключі DynamoDB

Таблиця `osbb-requests-<stage>-command-data`, ключі `pk` / `sk`:

| pk | sk | Призначення |
| --- | --- | --- |
| `USER#<telegramId>` | `MEMBERSHIP` | `buildingId`, `active`; схвалює адміністратор |
| `USER#<telegramId>` | `REGISTRATION` | Поточний реєстраційний профіль: ПІБ, телефон, стан і version |
| `REGISTRATION#<reference>` | `META` | Поданий запит на доступ і рішення адміністратора |
| `BUILDING#<buildingId>` | `REGISTRATION#<reference>` | Приватний список запитів на перевірці, Query без Scan |
| `BUILDING#<buildingId>` | `RESIDENT#<telegramId D20>` | Каталог схвалених мешканців: snapshot реєстрації, один запис на мешканця, без TTL |
| `REGISTRATION#<reference>` | `EVENT#DECIDED` | Автор, час і пояснення рішення адміністратора |
| `USER#<telegramId>` | `REQUEST_LOOKUP` | Очікування номера для `/request`, комплекс і version |
| `USER#<telegramId>` | `REQUEST#<updateId D20>` | Приватна заявка у JSON `payload` |
| `REQUEST#<updateId>` | `EVENT#CREATED` | Автор, UTC-час і початковий статус |
| `NOTIFICATIONS#<complexId>` | `DUE#<UTC time O>#<requestId>-v<version>` | Приватне завдання доставки, attempts і 90-секундна lease, без TTL |
| `NOTIFICATIONS#<complexId>` | `RESULT#<requestId>-v<version>` | Delivered/Undeliverable і час без тексту, TTL 30 днів |
| `NOTIFICATIONS#<complexId>` | `CONTROL` | Спільна пауза воркера після Telegram 429 |
| `UPDATE#<updateId>` | `REPLY` | Збережена відповідь, delivered, TTL `expiresAt` |

Одне середовище обслуговує один житловий комплекс (чотири будинки по 25 поверхів) і один Telegram-бот. Номер заявки дорівнює update ID швидкої команди або фінального опису покрокового діалогу; внутрішні ключі доповнюються нулями до 20 цифр для числового порядку сортування. `/my` використовує Query за власником, request prefix і курсором, до 10 елементів, від новіших update ID до старіших. Це порядок ідентифікаторів Telegram, а не універсальна хронологія: після тривалого простою Telegram може вибирати випадковий наступний update ID. Дати подання зберігаються окремо в UTC.

Створення заявки, початкової історії й receipt виконується однією транзакцією з умовними Put. Усі повтори update читають узгоджено збережену відповідь. Відсутність membership, неактивний запис або невідповідність комплексу блокують сценарії заявок. Деталі заявки читаються лише з partition власника.

Receipt зберігається 30 днів для дедуплікації та повторної доставки відповіді; заявки й історія не мають TTL. Точну довгострокову політику зберігання заявок і персональних даних ще потрібно погодити.

## Повторні доставки

FIFO group ID — chat ID, deduplication ID — update ID. Коротку дедуплікацію SQS доповнює DynamoDB receipt. Воркер використовує `ReportBatchItemFailures`, зупиняється на першій помилці та повертає також необроблені записи; batch size налаштований на 1. Timeout воркера — 30 секунд, visibility — 180 секунд, після п'яти отримань невдалі повідомлення переходять у DLQ.

Receipt із текстом відповіді працює як outbox для поточної команди: SQS забезпечує повторну спробу доставки. `delivered` записується після `sendMessage`. Якщо Telegram прийняв повідомлення, але відповідь загубилася або запис delivered не відбувся, повторне повідомлення можливе. Exactly-once доставка не гарантується. Для майбутніх сповіщень про адміністративні зміни потрібен окремий outbox і воркер.

Для `429` TelegramClient передає retry_after воркеру, який змінює visibility поточного повідомлення; помилка зміни visibility журналюється, update залишається невдалим. DLQ потребує моніторингу й redrive оператором. Операційне Telegram-сповіщення воркера необов'язкове, configurable і не містить тексту заявки.

## Подальший розвиток

Покроковий діалог створення реалізовано. Фотографії, коментарі, підписки, запити повторного відкриття, розширені сценарії переходів статусів ще не реалізовані. Базові ролі, зміна статусу з поясненням та Angular-вебпанель уже реалізовані. Для них потрібні:

- приватний S3 для вкладень і тимчасові URL після перевірки прав;
- окрема публічна проєкція без Telegram ID, контактів і приватного листування;
- індекси для майбутніх сценаріїв підписок; pending outbox вже використовує Query основної таблиці;
- автентифікація адміністраторів, перевірка ролей і конкуренції змін;
- пошук: DynamoDB сам по собі не забезпечує повнотекстовий пошук;
- явні дозволені переходи статусів та обов'язкові пояснення виконання/відхилення.

Вебпанель використовує Angular і Cognito за прикладом PingLight. Публічність заявки означатиме доступ мешканцям свого комплексу, а не анонімний доступ з інтернету. Фото й коментарі потребують окремої перевірки перед публікацією.

## Реєстрація мешканців

Діалог: `AwaitingPhone` → `AwaitingFirstName` → `AwaitingLastName` → `Pending`. Телефон береться тільки з Telegram contact із `user_id`, що відповідає відправнику, а ім’я та прізвище вводяться користувачем окремо. Telegram ID не показується в діалозі мешканця. У приватних списках реєстрацій і зареєстрованих мешканців активні адміністратори бачать `telegramChatId` як рядок; для приватного Telegram-чату це `UserId` мешканця. Публічні проєкції його не містять.

`RegistrationService` готує зміну профілю. `CommandOutcome` містить цю зміну та тип reply keyboard; збережена відповідь також містить keyboard для коректного retry. Транзакція репозиторію одночасно з receipt записує профіль з optimistic version; при завершенні діалогу додає два записи для адміністративного перегляду. Receipt створюється умовно, тому повторний update не застосує наступний крок двічі.

`manage-residents.py` залишається операторським резервом для вебпанелі. Він виконується з окремими AWS credentials оператора. Адміністратор бачить ім’я, прізвище, телефон і reference реєстрації. Схвалення/відхилення однією транзакцією перевіряє незмінність профілю та snapshot, оновлює обидва, встановлює membership, видаляє pending-проєкцію та записує аудит. Воркер бота не має DeleteItem і не виконує адміністративних рішень.

Після схвалення через API або `manage-residents.py` та сама транзакція додає приватне сповіщення `ResidentNotification` зі стабільним ID `registration-<reference>-v<version>`; воркер доставляє його в Telegram зі стандартними повторами. Воно містить підтвердження доступу, дату та команди `/new`, `/my`, `/complex`, без ПІБ, телефону або email адміністратора. Відхилення не створює сповіщення; рішення також доступне через `/start`. Повторне схвалення вже опрацьованої реєстрації не створює нової події. `/cancel` очищує незавершений профіль, але вже збережені receipt та SQS-повідомлення мають власні строки зберігання. Реєстрації не мають TTL і містять приватні контактні дані; вони ніколи не є частиною публічної проєкції заявки.

## Вхід і повноваження адміністраторів

Cognito забезпечує акаунти та підтверджений email. API Gateway перевіряє JWT issuer, client/audience та scope `aws.cognito.signin.user.admin`; API додатково вимагає `token_use = access`. Публічний клієнт не має client secret. Перша автентифікована операція `/admin/me` звіряє `sub` і verified email через Cognito GetUser та транзакційно створює неактивний запис через умовний Update і подію `NewAdministrator` у приватному outbox. Конкурентне створення повертає наявний запис; окремого enqueue після commit немає. Паролі й токени не передаються в таблиці чи журнали API.

Дозволи читаються ConsistentRead з `osbb-requests-<stage>-administrators` на кожному запиті. Самої автентифікації недостатньо. Адміністративні транзакції перевіряють `IsActive`, а зміни доступу — також `IsSuperAdmin`, безпосередньо під час запису. Це захищає від відкликання прав між перевіркою та зміною даних. Інтерфейс ховає недоступні дії, але рішення завжди приймає сервер.

`IsSuperAdmin` існує як Boolean DynamoDB; відсутність означає false. DTO не містять редагованого IsSuperAdmin і відхиляють невідомі JSON-поля. IAM whitelist UpdateItem виключає IsSuperAdmin; explicit Deny додатково забороняє запис цього атрибута та повну заміну/видалення адміністративного запису. Flag встановлюється лише людиною в AWS Console. API не змінює доступ до власного або іншого super admin запису. Зміни доступу інших адміністраторів записуються в аудит основної таблиці.

`BuildingRequestsIndex` основної таблиці індексує `requestBuildingId` / `requestCreatedAt`. API приймає `status` як один статус або перелік через кому (`New,InProgress`), перевіряє кожне значення за назвами enum та прибирає дублікати. Відсутнє або порожнє значення означає всі статуси. Frontend початково вибирає «Нова» та «В роботі»; очищення вибору скасовує фільтр. Застосовані масиви статусів копіюються окремо від форми, тому зміни до натискання «Знайти» не впливають на пагінацію. API виконує один Query із `requestStatus IN (...)` та фільтрами категорії та contains-пошуком нормалізованого місця/опису. Це substring search, а не повнотекстовий індекс. Порожня сторінка з cursor можлива після фільтрації; UI дозволяє завантажити наступну. GSI є eventually consistent. Історія й деталі читаються узгоджено з основної таблиці. Після перевірки доступу до заявки `HistoryAsync` отримує її перевірену модель, Query читає до 100 подій, а за наявності `EVENT#CREATED` один GetItem читає `USER#<owner>/REGISTRATION`. Ім’я та прізвище додаються як `actor` лише до події створення (`action=Created`) і лише за збігом власника та комплексу; використовується поточний профіль, історичний snapshot імені не зберігається. За відсутності відповідного профілю або імені повертається «Мешканець». Контакти й `actorId` не повертаються; записи аудиту та публічні проєкції не змінюються. Старі записи доповнює окрема умовна операторська міграція.

Розділи Angular Router: `/requests`, `/residents`, `/administrators`. AppComponent відновлює сесію та показує маршрутизований WorkspaceComponent після входу; адреса зберігається під час авторизації. Кожен перехід створює окремий робочий простір, скасовує застосування застарілих відповідей і скидає пагінацію та фільтри. CanDeactivate блокує перехід під час запису. Маршрут адміністраторів перевіряє роль після `/me` й перенаправляє інших користувачів на заявки; API окремо перевіряє права. CloudFront Function переписує лише три відомі шляхи (також із кінцевим `/`) на `/index.html`, зберігаючи поведінку статичних ресурсів.

Frontend — Angular SPA у приватному S3, опублікована через CloudFront Origin Access Control. CORS дозволяє її origin та локальний dev origin; API зберігає bearer authentication незалежно від CORS. Конфігурація фронтенду містить лише публічні ID Cognito та API URL. Сесія зберігається у sessionStorage, приватні відповіді мають Cache-Control: no-store.

## Каталог зареєстрованих мешканців

`GET /admin/residents` доступний активним адміністраторам і виконує ConsistentRead Query за partition свого комплексу та prefix `RESIDENT#`, до 25 записів із cursor. Сервер повертає reference реєстрації, ПІБ, телефон, дату підтвердження та Telegram Chat ID рядком у полі `telegramChatId`; повний профіль і внутрішні ключі не повертаються. Cursor перевіряється на відповідність будинку й списку. Неавторизовані та неактивні акаунти не можуть читати каталог.

API та операторський скрипт під час схвалення записують проєкцію каталогу в одній транзакції з профілем, snapshot, membership, аудитом і видаленням pending-запису. Відхилення не створює запису каталогу. Ключ за мешканцем запобігає дублям після повторного схвалення. Каталог є історією підтверджених реєстрацій; він не замінює перевірку актуального membership під час операцій бота.

Одноразовий `scripts/backfill-residents.py` сканує лише як операторська міграція, за замовчуванням працює в dry-run і обробляє поточні схвалені профілі відповідного комплексу. ConditionCheck перевіряє незмінність вихідного профілю, а умовний Put не перезаписує наявний запис. Профілі та доступ мешканців не змінюються. Runtime API не отримує дозволу Scan.

## Комплекс, будинки й чернетки заявок

Історичні `BuildingId`, `BUILDING_ID` та індекс `BuildingRequestsIndex` ідентифікують комплекс/tenant. Їхні значення й ключі не змінюються: схвалений мешканець має доступ до заявок комплексу, а фізичний будинок заявки зберігається окремо. `Scope` — `Building` або `Complex`; для першого обов'язковий `BuildingNumber` як рядок `4Б`, `4В`, `4Г` або `4Д`, для другого він відсутній. `Floor` може бути 1–25 або 0 («Парадне») лише для `Building`; null означає «Без поверху». Перевірка `ComplexLayout.IsValid` спільна для бота й API. Старий payload без scope читається як невизначений; нові заявки та адміністративні оновлення вимагають явної прив'язки.

`RequestCreationService` веде діалог `Scope → Floor (лише будинок) → Category → Description → Completed`. Чернетка лежить у `USER#<telegramId>` / `REQUEST_DRAFT` і має optimistic version. Кожен крок записується атомарно з receipt, завершення — також із заявкою та початковою історією. Повторний update не просуває діалог двічі; `/new` відновлює поточний крок, `/cancel` переводить у `Cancelled` та очищує поля. Завершений стан теж не містить місця чи опису. Чернетка не є заявкою й не публікується до завершення. Поточний membership перевіряється для кожного кроку. Telegram-клавіатура входить до receipt для коректного retry.

Після категорії бот одразу запитує опис. `Location` залишається в enum на старій числовій позиції для читання чернеток: `/new` переводить такий стан у `Description` з перевіркою version, а наступне текстове повідомлення може одразу завершити його як опис. Раніше введене місце в чернетці зберігається; у нових чернетках місця немає, у нових заявках `Location` — порожній рядок. UI та повідомлення приховують порожнє поле, історичні місця залишаються доступними.

`Finish` явно встановлює `Visibility=Public` для покрокового й швидкого створення. Повідомлення до та після створення пояснюють, що заявку бачитимуть усі мешканці комплексу. Типове `Private` у моделі лишається для безпечного читання історичних payload без поля Visibility; наявні заявки не мігруються. Швидкий `/new` має формат `будинок/комплекс | поверх/Парадне/- | категорія | опис` (текст після третього роздільника — опис).

Заявка й GSI-проєкція містять `requestTarget` (`Complex` або `Building4Б`, `Building4В`, `Building4Г`, `Building4Д`) та необов'язковий `requestFloor`. API фільтрує їх у Query наявного індексу; `target=Unspecified` знаходить старі записи без `requestTarget`. Оновлення scope/payload/індексних атрибутів та аудиту атомарне. Додаткових таблиць, індексів, Scan у runtime або міграції зі здогадуванням номерів будинків немає.

## Фільтрування статусів

`GET /admin/requests` фільтрує статус лише за `status`. Без нього повертаються всі статуси, включно з `Completed`; `status=Completed` вибирає тільки виконані. Додаткового прапорця видимості виконаних заявок немає. Решта фільтрів додається до того самого Query; порожня відфільтрована сторінка може мати cursor.

## Введення номера заявки

`/request` без номера або з некоректним номером пропонує ввести номер наступним повідомленням. `RequestLookupService` зберігає versioned стан у `USER#<telegramId>` / `REQUEST_LOOKUP` окремо від чернетки створення. Запит номера та завершення очікування записуються атомарно з receipt через умовний Put. Повтори update не відкривають діалог повторно. Некоректне введення залишає очікування активним; коректний номер завершує його навіть для ненайденої заявки. `/cancel` або будь-яка інша явна команда припиняє очікування. `/request номер` працює без додаткового кроку. `/my` приймає необов'язковий курсор і без нього показує список.

Перед обробкою наступного повідомлення перевіряється актуальний membership; заявка читається лише в partition відправника з перевіркою комплексу. Стан перегляду не зберігає номер чи вміст заявки і не змінює чернетку `/new`.

## Відкриті заявки комплексу

`/complex` доступна тільки за активного membership і охоплює весь tenant. `ComplexRequestsService` використовує `Query` на `BuildingRequestsIndex` з `requestBuildingId = tenant`, статусами `New` / `InProgress`, порядком від новіших дат і лімітом 5 переглянутих записів. Для кожного кандидата виконується strongly consistent GetItem основного запису: перевіряються актуальні комплекс, `Visibility=Public` і відкритий статус. Запізнення GSI після зміни видимості, статусу або видалення не розкриває застарілий payload.

До повідомлення потрапляє лише `PublicRequestSummary`: номер, статус, дата, scope/будинок/поверх, категорія, місце та текст Public-заявки. Власник, контакт, пояснення адміністратора та приватне листування відсутні. Пагінація використовує строго менший `requestCreatedAt` і base64url-курсор дати та номера; внутрішні ключі власника не потрапляють у команду. Курсор перевіряється перед Query. Відфільтрована порожня сторінка може мати продовження. Результат обмежений розміром повідомлення Telegram, Scan і нових індексів немає.

## Видалення власної нової заявки

`/delete [номер]` використовує той самий `REQUEST_LOOKUP`: `Action=Delete`, спочатку очікується номер, потім підтвердження «Так». У стані підтвердження зберігаються номер і версія заявки, без її вмісту. Старі стани без Action трактуються як View. `/cancel` та інші команди очищують поточний сценарій; чернетка `/new` зберігається окремо.

На кожному кроці перевіряється membership. Заявка читається узгоджено з partition власника з перевіркою комплексу та статусу `New`; після підтвердження додатково порівнюється версія. Commit атомарно записує receipt, завершує діалог, перевіряє активний membership комплексу, видаляє основний запис за умовами version/status/complex і додає `REQUEST#id` / `EVENT#DELETED` з автором і часом. Історія не видаляється і не має TTL. Умова версії запобігає гонці з адміністративним оновленням; повтор після конфлікту повторно читає поточний стан. Після збою Telegram доставка використовує збережену відповідь без повторного видалення.

IAM воркера доповнено Query лише потрібного GSI та DeleteItem/ConditionCheckItem лише таблиці command-data. Права webhook та адміністраторської таблиці не розширюються.

## Сповіщення про адміністративні зміни

`DynamoAdminStore.UpdateRequestAsync` у тій самій транзакції з ActorCheck, versioned Update та аудитом додає `ResidentNotification`, якщо змінився Status або нормалізоване Resolution. Номер та наступна версія формують стабільний event ID. Окремого виклику Telegram або SQS з API немає; конфлікт прав чи версії не створює сповіщення. Повторне збереження незмінного статусу/пояснення не надсилає його знову. Видалення пояснення також повідомляється, решта адміністративних полів самі по собі не створюють події. Контакти, email адміністратора, опис і приватне листування в подію не додаються; текст пояснення доступний тільки автору в приватному Telegram-чаті.

Спільний payload `ResidentNotification` зберігає сумісність із раніше створеними повідомленнями заявок; `RequestId` та `RequestVersion` для реєстрацій дорівнюють null.

`NotificationSchedule` (EventBridge Scheduler, rate 1 minute, flexible window OFF) асинхронно викликає `NotificationFunction`. І Scheduler, і Lambda мають окремо налаштовані retries та спільну стандартну SQS NotificationFailureQueue з 14-денним retention. Це черга помилок запуску, а не самих повідомлень: невідправлені повідомлення лишаються в DynamoDB до обробки. Секрет читає лише роль воркера; AdminApiRole не отримує Telegram-секретів. DynamoDB-доступ воркера обмежений LeadingKeys partition поточного комплексу, без Scan. Окремі read-only дозволи дають воркеру Query `AdministratorsTable/DirectoryIndex` і GetItem поточних налаштувань адміністратора; записів до таблиці адміністраторів він не виконує.

`DynamoNotificationRepository` узгоджено читає CONTROL, потім Query за partition та діапазоном `DUE#` до поточного часу, Limit 25. Claim використовує умовний Update з випадковим leaseToken та leaseExpiresAt = now + 90 seconds; відсутні або зайняті завдання пропускаються. Lambda має timeout 60 секунд, внутрішній бюджет 50: при перериванні lease відновлюється наступним запуском. Після sendMessage транзакція прибирає DUE-запис за leaseToken та додає RESULT без тексту з TTL 30 днів. Обидва ключі лишаються в одному приватному partition і не потрапляють до BuildingRequestsIndex.

Тимчасова помилка атомарно переносить DUE-ключ на наступний час і збільшує attempts: 60, 120, 240 секунд тощо, до 3600 секунд. Невідправлені записи не мають TTL чи максимального числа спроб. Для 429 враховується retry_after і зберігається спільний pauseUntil, який може лише збільшуватись; поточний batch зупиняється. HTTP 400/403 закривають завдання як Undeliverable і не блокують решту; операційний notifier отримує тільки ID події. Фатальна помилка читання/запису журналюється лише за типом, після необов'язкового notifier виняток передається Lambda для повтору/DLQ.

Успішно завершені завдання не надсилаються повторно. Вузьке вікно між Telegram і commit результату залишається at-least-once: після збою можливий дублікат. Повтори окремих подій можуть змінити порядок повідомлень; текст містить точний час зміни. Історія заявки зберігається без TTL, а попередні адміністративні зміни не ставляться в новий outbox заднім числом.

## Пагінація вебпанелі

Query для заявок, pending-реєстрацій, зареєстрованих мешканців та адміністраторів має Limit 25; runtime не використовує Scan. Cursor з LastEvaluatedKey повертається без змін до наступного запиту й перевіряється на комплекс/каталог. Для обох списків мешканців додатково перевіряється prefix sk, щоб cursor одного списку не використовувався в іншому. Ліміт DynamoDB застосовується до переглянутих записів до фільтрів, тому результат може бути меншим за 25 або порожнім із cursor.

`PaginationComponent` відображає Bootstrap-навігацію та передає дії батьківському `WorkspaceComponent`. Батьківський компонент зберігає поточний номер, cursor наступної сторінки та історію вхідних cursor для переходу назад. Успішна відповідь замінює список; перехід за номером перечитує відповідну сторінку, зберігаючи відомі cursor наступних сторінок. Якщо оновлена відповідь змінила cursor наступної сторінки, подальші cursor відкидаються; якщо cursor відсутній, історія обрізається на поточній сторінці. Загальної кількості та довільного переходу на неотримані сторінки API не обчислює. Числовий пагінатор показує до 10 сусідніх сторінок, першу й останню відомі, а пропуски позначає трикрапкою. Нова доступна сторінка додається за отриманим next cursor; довільного завантаження всього каталогу заради загальної кількості немає.

Застосовані фільтри зберігаються окремо від редагованих полів форми. Новий пошук, розділ чи список мешканців скидає пагінацію; refresh зберігає поточний вхідний cursor. Номер, дані й cursor змінюються лише після успішного переходу. Навігація блокується під час завантаження/збереження; epoch та номер запиту захищають від запізнілих відповідей після виходу або зміни користувача. Призначення відповідального продовжує завантажувати всі сторінки окремого списку assignees.

## Сповіщення адміністраторам

Адміністративний запис містить `TelegramChatId` (рядок або null), `NotifyNewResidents`, `NotifyNewRequests`, `NotifyNewAdministrators` (відсутні означають false). `PATCH /admin/administrators/{id}/notifications` приймає лише ці поля та `version`. Активний адміністратор може змінити власні підписки, активний супер адміністратор — також чужі. Для чужого запису транзакція містить ActorCheck ролі та versioned Update; для власного — перевірку IsActive безпосередньо в Update, щоб не звертатися двічі до одного ключа в транзакції. IsSuperAdmin не входить до Update чи його умови; IAM заборона запису цього поля збережена. Settings Update не змінює IsActive. Аудит не містить Chat ID або тексту повідомлень.

`DynamoCommandRepository.CommitAsync` разом із receipt та результатами додає broadcast для завершеної Pending-реєстрації або нової заявки. Чернетки не створюють подій. API додає broadcast для першого адміністративного акаунта в тій самій транзакції з його створенням. Стабільні ID: `new-resident-<reference>-v<version>`, `new-request-<requestId>`, `new-administrator-<sub>`. Broadcast — `ResidentNotification` з AdministratorEvent та OwnerId=0; він ніколи не відправляється в Telegram напряму.

Після lease `ExpandAsync` читає сторінку DirectoryIndex (Limit 25), а для кожного кандидата — узгоджений GetItem основного запису. Поточні IsActive, підписка й валідний Chat ID визначають одержувачів. Транзакція додає індивідуальні DUE-повідомлення (`<eventId>-admin-<sub>`) і checkpoint audienceCursor зі зняттям lease або видаляє завершений broadcast із RESULT=Expanded. При збої checkpoint і повідомлення не розходяться; Retry переносить також audienceCursor. Обробка не обмежується першими 25 адміністраторами. Відсутні підписки та неактивні записи пропускаються. Вибір кандидатів через GSI є eventually consistent.

Індивідуальна доставка повторно GetItem перевіряє актуальну активність, тип підписки та збіг Chat ID. За зміни налаштувань або доступу завдання завершується як Skipped без Telegram. Від’ємні Chat ID дозволені лише для адресних адміністративних повідомлень. Telegram-відправлення та commit результату залишаються at-least-once; стандартні retries, 429 pause, Undeliverable та TTL лише результатів спільні з повідомленнями мешканцям. Типовий broadcast потребує одного запуску для розподілу й наступного для доставки (1–2 хвилини). Повідомлення містять час за Києвом та короткі відомості про подію, без телефону мешканця чи опису приватної заявки.

## Текст заявки у списках бота

`/my` показує повний опис власних заявок; `/complex` додає Description до `PublicRequestSummary` лише після перевірки поточного основного запису (свій комплекс, Public, New/InProgress). ПІБ, контакти та Resolution до цієї проєкції не входять. Загальнодоступний опис — саме текст Public-заявки, а не приватне листування.

`RequestListText` формує одне повідомлення до 4096 UTF-16 code units разом із заголовком і командою наступної сторінки. Повні валідні описи до 2000 символів не скорочуються. За браку місця список завершується на межі заявки: `/my` продовжує за ID останньої показаної заявки, `/complex` — за її CreatedAt#Id. Якщо всі отримані елементи показано, зберігається cursor репозиторію; це також забезпечує перехід після порожніх відфільтрованих сторінок. Backend-ліміти читання залишаються 10 та 5 відповідно. Завеликі поля старих записів обмежуються захисно, без розриву UTF-16 surrogate pair; runtime не додає Scan чи нових індексів.
