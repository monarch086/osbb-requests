# Архітектура

## Реалізовано

Три Lambda з двох ZIP-артефактів:

- `OsbbRequests.Bot.Function` — HTTP webhook, перевірка секрету та публікація в SQS.
- `OsbbRequests.Bot.CommandFunction` — обробка команд із FIFO-черги.
- `OsbbRequests.AdminApi.Function` — лише `GET /health`.

Webhook читає тільки свій SSM parameter і має лише `sqs:SendMessage` до черги. Воркер читає тільки токен бота, отримує повідомлення з черги та працює з однією таблицею. API вебпанелі не має доступу до заявок. Секрети читаються під час роботи, не під час пакування.

`WebhookHandler` перевіряє secret до десеріалізації. До черги потрапляють тільки update ID, user ID, chat ID і текст; групові повідомлення, редагування, боти, вкладення без тексту та сторонні адресовані команди ігноруються. Повні Telegram payload не зберігаються.

`CommandHandler` маршрутизує команди й перевіряє доступ до будинку. `CommandProcessor` забезпечує порядок: читання receipt → сценарій → атомарний commit → доставка → delivered. `DynamoCommandRepository` інкапсулює сховище. `TelegramClient` надсилає plain text через довгоживучий HttpClient із 10-секундним timeout; кожен виклик отримує cancellation token.

## Ключі DynamoDB

Таблиця `osbb-requests-<stage>-command-data`, ключі `pk` / `sk`:

| pk | sk | Призначення |
| --- | --- | --- |
| `USER#<telegramId>` | `MEMBERSHIP` | `buildingId`, `active`; додає оператор |
| `USER#<telegramId>` | `REQUEST#<updateId D20>` | Приватна заявка у JSON `payload` |
| `REQUEST#<updateId>` | `EVENT#CREATED` | Автор, UTC-час і початковий статус |
| `UPDATE#<updateId>` | `REPLY` | Збережена відповідь, delivered, TTL `expiresAt` |

Одне середовище обслуговує один будинок і один Telegram-бот. Номер заявки дорівнює update ID команди створення; внутрішні ключі доповнюються нулями до 20 цифр для числового порядку сортування. `/my` використовує Query за власником, request prefix і курсором, до 10 елементів, від новіших update ID до старіших. Це порядок ідентифікаторів Telegram, а не універсальна хронологія: після тривалого простою Telegram може вибирати випадковий наступний update ID. Дати подання зберігаються окремо в UTC.

Створення заявки, початкової історії й receipt виконується однією транзакцією з умовними Put. Усі повтори update читають узгоджено збережену відповідь. Відсутність membership, неактивний запис або невідповідність будинку блокують сценарії заявок. Деталі заявки читаються лише з partition власника.

Receipt зберігається 30 днів для дедуплікації та повторної доставки відповіді; заявки й історія не мають TTL. Точну довгострокову політику зберігання заявок і персональних даних ще потрібно погодити.

## Повторні доставки

FIFO group ID — chat ID, deduplication ID — update ID. Коротку дедуплікацію SQS доповнює DynamoDB receipt. Воркер використовує `ReportBatchItemFailures`, зупиняється на першій помилці та повертає також необроблені записи; batch size налаштований на 1. Timeout воркера — 30 секунд, visibility — 180 секунд, після п'яти отримань невдалі повідомлення переходять у DLQ.

Receipt із текстом відповіді працює як outbox для поточної команди: SQS забезпечує повторну спробу доставки. `delivered` записується після `sendMessage`. Якщо Telegram прийняв повідомлення, але відповідь загубилася або запис delivered не відбувся, повторне повідомлення можливе. Exactly-once доставка не гарантується. Для майбутніх сповіщень про адміністративні зміни потрібен окремий outbox і воркер.

Для `429` TelegramClient передає retry_after воркеру, який змінює visibility поточного повідомлення; помилка зміни visibility журналюється, update залишається невдалим. DLQ потребує моніторингу й redrive оператором. Операційне Telegram-сповіщення воркера необов'язкове, configurable і не містить тексту заявки.

## Подальший розвиток

Діалог створення з фотографіями, коментарі, підписки, запити повторного відкриття, ролі адміністратора, переходи статусів та вебпанель ще не реалізовані. Для них потрібні:

- приватний S3 для вкладень і тимчасові URL після перевірки прав;
- окрема публічна проєкція без Telegram ID, контактів і приватного листування;
- індекси адміністративних фільтрів, історії, підписок і pending outbox;
- автентифікація адміністраторів, перевірка ролей і конкуренції змін;
- пошук: DynamoDB сам по собі не забезпечує повнотекстовий пошук;
- явні дозволені переходи статусів та обов'язкові пояснення виконання/відхилення.

Фреймворк вебпанелі ще не обрано. Публічність заявки означатиме доступ мешканцям свого будинку, а не анонімний доступ з інтернету. Фото й коментарі потребують окремої перевірки перед публікацією.
