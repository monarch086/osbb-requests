# Архітектура

## Реалізовано

Чотири Lambda з двох ZIP-артефактів:

- `OsbbRequests.Bot.Function` - HTTP webhook, перевірка секрету та публікація в SQS.
- `OsbbRequests.Bot.CommandFunction` - обробка команд із FIFO-черги.
- `OsbbRequests.Bot.NotificationFunction` - щохвилинна доставка автору заявки з транзакційного outbox.
- `OsbbRequests.AdminApi.Function` - публічний `GET /health` і захищені Cognito JWT маршрути `/admin/*`.

Webhook читає тільки свій SSM parameter і має лише `sqs:SendMessage` до черги. Воркер читає тільки токен бота, отримує повідомлення з черги та працює з однією таблицею. API вебпанелі має окрему роль із доступом до заявок і окремої таблиці адміністраторів; запис `IsSuperAdmin` заборонений IAM. Секрети читаються під час роботи, не під час пакування.

`WebhookHandler` перевіряє secret до десеріалізації. До черги потрапляють тільки update ID, user ID, chat ID і текст або власний контакт для реєстрації; групові повідомлення, редагування, боти, вкладення без тексту/контакту та сторонні адресовані команди ігноруються. Повні Telegram payload не зберігаються.

`CommandHandler` маршрутизує команди й перевіряє доступ до комплексу. `CommandProcessor` забезпечує порядок: читання receipt → сценарій → атомарний commit → доставка → delivered. `DynamoCommandRepository` інкапсулює сховище. `TelegramClient` надсилає plain text через довгоживучий HttpClient із 10-секундним timeout; кожен виклик отримує cancellation token.

## Ключі DynamoDB

Таблиця `osbb-requests-<stage>-command-data`, ключі `pk` / `sk`:

| pk | sk | Призначення |
| --- | --- | --- |
| `USER#<telegramId>` | `MEMBERSHIP` | `buildingId`, `active`; автоматичне схвалення або рішення адміністратора в Manual |
| `USER#<telegramId>` | `REGISTRATION` | Поточний реєстраційний профіль: ПІБ, телефон, будинок, квартира, стан і version |
| `REGISTRATION#<reference>` | `META` | Поданий запит на доступ і рішення адміністратора |
| `BUILDING#<buildingId>` | `REGISTRATION#<reference>` | Приватний список запитів на перевірці, Query без Scan |
| `BUILDING#<buildingId>` | `RESIDENT#<telegramId D20>` | Каталог схвалених мешканців: snapshot реєстрації, один запис на мешканця, без TTL |
| `REGISTRATION#<reference>` | `EVENT#DECIDED` | Автор, час і пояснення рішення адміністратора |
| `USER#<telegramId>` | `REQUEST_LOOKUP` | Очікування номера для `/request`, комплекс і version |
| `USER#<telegramId>` | `COMPLEX_CURSOR#<complexId>#<token>` | Повний курсор `/complex`, 10-символьне посилання, TTL 30 днів |
| `USER#<telegramId>` | `REQUEST#<updateId D20>` | Приватна заявка у JSON `payload` |
| `REQUEST#<updateId>` | `EVENT#CREATED` | Автор, UTC-час і початковий статус |
| `NOTIFICATIONS#<complexId>` | `DUE#<UTC time O>#<requestId>-v<version>` | Приватне завдання доставки, attempts і 90-секундна lease, без TTL |
| `NOTIFICATIONS#<complexId>` | `RESULT#<requestId>-v<version>` | Delivered/Undeliverable і час без тексту, TTL 30 днів |
| `NOTIFICATIONS#<complexId>` | `CONTROL` | Спільна пауза воркера після Telegram 429 |
| `UPDATE#<updateId>` | `REPLY` | Збережена відповідь, delivered, TTL `expiresAt` |

Одне середовище обслуговує один житловий комплекс (чотири будинки по 25 поверхів) і один Telegram-бот. Номер заявки дорівнює update ID швидкої команди або фінального опису покрокового діалогу; внутрішні ключі доповнюються нулями до 20 цифр для числового порядку сортування. `/my` використовує Query за власником, request prefix і курсором, до 10 елементів, від новіших update ID до старіших. Це порядок ідентифікаторів Telegram, а не універсальна хронологія: після тривалого простою Telegram може вибирати випадковий наступний update ID. Дати подання зберігаються окремо в UTC.

Створення заявки, початкової історії й receipt виконується однією транзакцією з умовними Put. Усі повтори update читають узгоджено збережену відповідь. Відсутність membership, неактивний запис або невідповідність комплексу блокують сценарії заявок. Деталі заявки читаються лише з partition власника.

Receipt зберігається 30 днів для дедуплікації та повторної доставки відповіді; заявки й історія не мають TTL. Точну довгострокову політику зберігання заявок і персональних даних ще потрібно погодити.

## Повторні доставки

FIFO group ID - chat ID, deduplication ID - update ID. Коротку дедуплікацію SQS доповнює DynamoDB receipt. Воркер використовує `ReportBatchItemFailures`, зупиняється на першій помилці та повертає також необроблені записи; batch size налаштований на 1. Timeout воркера - 30 секунд, visibility - 180 секунд, після п'яти отримань невдалі повідомлення переходять у DLQ.

Receipt із текстом відповіді працює як outbox для поточної команди: SQS забезпечує повторну спробу доставки. `delivered` записується після `sendMessage`. Якщо Telegram прийняв повідомлення, але відповідь загубилася або запис delivered не відбувся, повторне повідомлення можливе. Exactly-once доставка не гарантується. Для майбутніх сповіщень про адміністративні зміни потрібен окремий outbox і воркер.

Для `429` TelegramClient передає retry_after воркеру, який змінює visibility поточного повідомлення; помилка зміни visibility журналюється, update залишається невдалим. DLQ потребує моніторингу й redrive оператором. Операційні сповіщення надсилає спільний TelegramServiceNotifier окремим сервісним ботом, без тексту заявки; його збій не змінює результату обробки.

## Подальший розвиток

Покроковий діалог створення реалізовано. Фотографії, коментарі, підписки, запити повторного відкриття, розширені сценарії переходів статусів ще не реалізовані. Базові ролі, зміна статусу з поясненням та Angular-вебпанель уже реалізовані. Для них потрібні:

- приватний S3 для вкладень і тимчасові URL після перевірки прав;
- окрема публічна проєкція без Telegram ID, контактів і приватного листування;
- індекси для майбутніх сценаріїв підписок; pending outbox вже використовує Query основної таблиці;
- автентифікація адміністраторів, перевірка ролей і конкуренції змін;
- пошук: DynamoDB сам по собі не забезпечує повнотекстовий пошук;
- явні дозволені переходи статусів та обов'язкові пояснення виконання/відхилення.

Вебпанель використовує Angular і Cognito за прикладом PingLight. Публічність заявки означатиме доступ мешканцям свого комплексу, а не анонімний доступ з інтернету. Фото й коментарі потребують окремої перевірки перед публікацією.

## Реєстрація мешканців

Діалог: `AwaitingPhone` → `AwaitingFirstName` → `AwaitingLastName` → `AwaitingBuilding` → `AwaitingApartment` → `Approved` (типовий Automatic) або `Pending` (Manual). Телефон береться тільки з Telegram contact із `user_id`, що відповідає відправнику, а ім’я та прізвище вводяться користувачем окремо. Далі окрема клавіатура `RegistrationBuilding` пропонує лише 4Б, 4В, 4Г та 4Д; «Весь комплекс» не є варіантом проживання. Номер квартири - додатне ціле число, збережене нормалізованим рядком. Нові стани й keyboard додані в кінець enum для збереження старих числових значень. `BuildingNumber` та `ApartmentNumber` - nullable поля приватного профілю; відсутні значення старих профілів залишаються null, у тому числі вже подані Pending. Незавершені діалоги продовжуються з поточного кроку; подія NewResident та відповідна Approved/Pending-проєкція створюються лише після номера квартири. Скасування очищує також адресу. Telegram ID не показується в діалозі мешканця. У приватних списках реєстрацій і зареєстрованих мешканців активні адміністратори бачать `telegramChatId` як рядок; для приватного Telegram-чату це `UserId` мешканця. Публічні проєкції його не містять.

`RegistrationService` готує зміну профілю. `CommandOutcome` містить цю зміну та тип reply keyboard; збережена відповідь також містить keyboard для коректного retry. Транзакція репозиторію одночасно з receipt записує профіль з optimistic version; при завершенні діалогу додає два записи для адміністративного перегляду. Receipt створюється умовно, тому повторний update не застосує наступний крок двічі.

`manage-residents.py` залишається операторським резервом для вебпанелі. Він виконується з окремими AWS credentials оператора. Адміністратор бачить ім’я, прізвище, телефон і reference реєстрації. Схвалення/відхилення однією транзакцією перевіряє незмінність профілю та snapshot, оновлює обидва, встановлює membership, видаляє pending-проєкцію та записує аудит. Ручні рішення залишаються в API та операторському скрипті; воркер бота може лише автоматично завершити нову реєстрацію згідно з налаштованим режимом.

Після схвалення через API або `manage-residents.py` та сама транзакція додає приватне сповіщення `ResidentNotification` зі стабільним ID `registration-<reference>-v<version>`; воркер доставляє його в Telegram зі стандартними повторами. Воно містить підтвердження доступу, дату та команди `/new`, `/my`, `/complex`, без ПІБ, телефону або email адміністратора. Відхилення не створює сповіщення; рішення також доступне через `/start`. Повторне схвалення вже опрацьованої реєстрації не створює нової події. `/cancel` очищує незавершений профіль, але вже збережені receipt та SQS-повідомлення мають власні строки зберігання. Реєстрації не мають TTL і містять приватні контактні дані; вони ніколи не є частиною публічної проєкції заявки.

## Вхід і повноваження адміністраторів

Cognito забезпечує акаунти та підтверджений email. API Gateway перевіряє JWT issuer, client/audience та scope `aws.cognito.signin.user.admin`; API додатково вимагає `token_use = access`. Публічний клієнт не має client secret. Перша автентифікована операція `/admin/me` звіряє `sub` і verified email через Cognito GetUser та транзакційно створює неактивний запис через умовний Update і подію `NewAdministrator` у приватному outbox. Конкурентне створення повертає наявний запис; окремого enqueue після commit немає. Паролі й токени не передаються в таблиці чи журнали API.

Дозволи читаються ConsistentRead з `osbb-requests-<stage>-administrators` на кожному запиті. Самої автентифікації недостатньо. Адміністративні транзакції перевіряють `IsActive`, а зміни доступу - також `IsSuperAdmin`, безпосередньо під час запису. Це захищає від відкликання прав між перевіркою та зміною даних. Інтерфейс ховає недоступні дії, але рішення завжди приймає сервер.

`IsSuperAdmin` існує як Boolean DynamoDB; відсутність означає false. DTO не містять редагованого IsSuperAdmin і відхиляють невідомі JSON-поля. IAM whitelist UpdateItem виключає IsSuperAdmin; explicit Deny додатково забороняє запис цього атрибута та повну заміну/видалення адміністративного запису. Flag встановлюється лише людиною в AWS Console. API не змінює доступ до власного або іншого super admin запису. Зміни доступу інших адміністраторів записуються в аудит основної таблиці.

`BuildingRequestsIndex` основної таблиці індексує `requestBuildingId` / `requestCreatedAt`. API приймає `status` як один статус або перелік через кому (`New,InProgress`), перевіряє кожне значення за назвами enum та прибирає дублікати. Відсутнє або порожнє значення означає всі статуси. Frontend початково вибирає «Нова» та «В роботі»; очищення вибору скасовує фільтр. Застосовані масиви статусів копіюються окремо від форми, тому зміни до натискання «Знайти» не впливають на пагінацію. API виконує один Query із `requestStatus IN (...)` та фільтрами категорії та contains-пошуком нормалізованого місця/опису. Це substring search, а не повнотекстовий індекс. Порожня сторінка з cursor можлива після фільтрації; UI дозволяє завантажити наступну. GSI є eventually consistent. Історія й деталі читаються узгоджено з основної таблиці. Після перевірки доступу до заявки `HistoryAsync` отримує її перевірену модель, Query читає до 100 подій, а за наявності `EVENT#CREATED` один GetItem читає `USER#<owner>/REGISTRATION`. Ім’я та прізвище додаються як `actor` лише до події створення (`action=Created`) і лише за збігом власника та комплексу; використовується поточний профіль, історичний snapshot імені не зберігається. За відсутності відповідного профілю або імені повертається «Мешканець». Контакти й `actorId` не повертаються; записи аудиту та публічні проєкції не змінюються. Старі записи доповнює окрема умовна операторська міграція.

Розділи Angular Router: `/requests`, `/residents`, `/messages`, `/administrators`. AppComponent відновлює сесію та показує маршрутизований WorkspaceComponent після входу; адреса зберігається під час авторизації. Кожен перехід створює окремий робочий простір, скасовує застосування застарілих відповідей і скидає пагінацію та фільтри. CanDeactivate блокує перехід під час запису. Маршрути повідомлень та адміністраторів перевіряють роль після `/me` й перенаправляє інших користувачів на заявки; API окремо перевіряє права. CloudFront Function переписує лише чотири відомі шляхи (також із кінцевим `/`) на `/index.html`, зберігаючи поведінку статичних ресурсів.

Frontend - Angular SPA у приватному S3, опублікована через CloudFront Origin Access Control. ESLint використовує typed recommended з окремими правилами consistent-type-imports, prefer-readonly, prefer-output-readonly, switch-exhaustiveness-check, no-unnecessary-condition, member-ordering, curly/all і simple-import-sort; Stylelint обмежує ID-селектори та вкладеність SCSS. Prettier форматує код окремо. Union-типи статусів/пріоритетів відповідають backend-контракту; історія, що повертає рядкові значення, безпечно читає мапу як Partial. Непідтримувані етапи Cognito явно перераховані в switch і зберігають обробку помилки. Перевірки доступні у CI через npm run check --prefix src/Frontend. CORS дозволяє її origin та локальний dev origin; API зберігає bearer authentication незалежно від CORS. Конфігурація фронтенду містить лише публічні ID Cognito та API URL. Сесія зберігається у sessionStorage, приватні відповіді мають Cache-Control: no-store.

## Каталог зареєстрованих мешканців

`GET /admin/residents` доступний активним адміністраторам і виконує ConsistentRead Query за partition свого комплексу та prefix `RESIDENT#`, до 25 записів із cursor. Сервер повертає reference реєстрації, ПІБ, телефон, дату підтвердження та Telegram Chat ID рядком у полі `telegramChatId`; повний профіль і внутрішні ключі не повертаються. Cursor перевіряється на відповідність будинку й списку. Неавторизовані та неактивні акаунти не можуть читати каталог.

API та операторський скрипт під час схвалення записують проєкцію каталогу в одній транзакції з профілем, snapshot, membership, аудитом і видаленням pending-запису. Відхилення не створює запису каталогу. Ключ за мешканцем запобігає дублям після повторного схвалення. Каталог є історією підтверджених реєстрацій; він не замінює перевірку актуального membership під час операцій бота.

Одноразовий `scripts/backfill-residents.py` сканує лише як операторська міграція, за замовчуванням працює в dry-run і обробляє поточні схвалені профілі відповідного комплексу. ConditionCheck перевіряє незмінність вихідного профілю, а умовний Put не перезаписує наявний запис. Профілі та доступ мешканців не змінюються. Runtime API не отримує дозволу Scan.

## Комплекс, будинки й чернетки заявок

Історичні `BuildingId`, `BUILDING_ID` та індекс `BuildingRequestsIndex` ідентифікують комплекс/tenant. Їхні значення й ключі не змінюються: схвалений мешканець має доступ до заявок комплексу, а фізичний будинок заявки зберігається окремо. `Scope` - `Building` або `Complex`; для першого обов'язковий `BuildingNumber` як рядок `4Б`, `4В`, `4Г` або `4Д`, для другого він відсутній. `Entrance` - nullable int: 1, 2 або null («Не зазначено»), лише для Building; у 4Б допустимі null для старих заявок та 1. Відсутнє поле в наявному payload читається як null без перезапису, зокрема для 4Б. `Floor` може бути 1–25 або 0 («Парадне») лише для `Building`; null означає «Без поверху». Перевірка `ComplexLayout.IsValid` спільна для бота й API. Старий payload без scope читається як невизначений; нові заявки та адміністративні оновлення вимагають явної прив'язки.

`RequestCreationService` веде діалог `Scope → Entrance (4В/4Г/4Д) → Floor (лише будинок) → Category → Description → Completed`. Новий крок Entrance і клавіатуру RequestEntrance додано наприкінці enum без зміни числових значень попередніх станів. Для нового вибору 4Б під’їзд встановлюється в 1 без запиту. Старі незавершені чернетки продовжуються з поточного кроку, а при завершенні нової заявки 4Б під’їзд стає 1. Вже збережені заявки не змінюються. Чернетка лежить у `USER#<telegramId>` / `REQUEST_DRAFT` і має optimistic version. Кожен крок записується атомарно з receipt, завершення - також із заявкою та початковою історією. Повторний update не просуває діалог двічі; `/new` відновлює поточний крок, `/cancel` переводить у `Cancelled` та очищує поля. Завершений стан теж не містить місця чи опису. Чернетка не є заявкою й не публікується до завершення. Поточний membership перевіряється для кожного кроку. Telegram-клавіатура входить до receipt для коректного retry.

Після категорії бот одразу запитує опис. `Location` залишається в enum на старій числовій позиції для читання чернеток: `/new` переводить такий стан у `Description` з перевіркою version, а наступне текстове повідомлення може одразу завершити його як опис. Раніше введене місце в чернетці зберігається; у нових чернетках місця немає, у нових заявках `Location` - порожній рядок. UI та повідомлення приховують порожнє поле, історичні місця залишаються доступними.

`Finish` явно встановлює `Visibility=Public` для покрокового й швидкого створення. Повідомлення до та після створення пояснюють, що заявку бачитимуть усі мешканці комплексу. Типове `Private` у моделі лишається для безпечного читання історичних payload без поля Visibility; наявні заявки не мігруються. Швидкий `/new` підтримує `будинок/комплекс | під’їзд/Не зазначено/- | поверх/Парадне/- | категорія | опис`, а також попередній формат із чотирьох полів (текст після третього роздільника - опис).

Заявка й GSI-проєкція містять `requestTarget` (`Complex` або `Building4Б`, `Building4В`, `Building4Г`, `Building4Д`) та необов'язковий `requestFloor`. API фільтрує їх у Query наявного індексу; `target=Unspecified` знаходить старі записи без `requestTarget`. Оновлення scope/payload/індексних атрибутів та аудиту атомарне. Додаткових таблиць, індексів, Scan у runtime або міграції зі здогадуванням номерів будинків немає.

## Фільтрування статусів

`GET /admin/requests` фільтрує статус лише за `status`. Без нього повертаються всі статуси, включно з `Completed`; `status=Completed` вибирає тільки виконані. Додаткового прапорця видимості виконаних заявок немає. Решта фільтрів додається до того самого Query; порожня відфільтрована сторінка може мати cursor.

## Введення номера заявки

`/request` без номера або з некоректним номером пропонує ввести номер наступним повідомленням. `RequestLookupService` зберігає versioned стан у `USER#<telegramId>` / `REQUEST_LOOKUP` окремо від чернетки створення. Запит номера та завершення очікування записуються атомарно з receipt через умовний Put. Повтори update не відкривають діалог повторно. Некоректне введення залишає очікування активним; коректний номер завершує його навіть для ненайденої заявки. `/cancel` або будь-яка інша явна команда припиняє очікування. `/request номер` працює без додаткового кроку. `/my` приймає необов'язковий курсор і без нього показує список.

Перед обробкою наступного повідомлення перевіряється актуальний membership; заявка читається лише в partition відправника з перевіркою комплексу. Стан перегляду не зберігає номер чи вміст заявки і не змінює чернетку `/new`.

## Відкриті заявки комплексу

`/complex` доступна тільки за активного membership і охоплює весь tenant. `ComplexRequestsService` використовує `Query` на `BuildingRequestsIndex` з `requestBuildingId = tenant`, статусами `New` / `InProgress`, порядком від новіших дат і лімітом 5 переглянутих записів. Для кожного кандидата виконується strongly consistent GetItem основного запису: перевіряються актуальні комплекс, `Visibility=Public` і відкритий статус. Запізнення GSI після зміни видимості, статусу або видалення не розкриває застарілий payload.

До повідомлення потрапляє лише `PublicRequestSummary`: номер, статус, дата, scope/будинок/під’їзд/поверх, категорія, місце та текст Public-заявки. Власник, контакт, пояснення адміністратора та приватне листування відсутні. Пагінація використовує строго менший `requestCreatedAt`. Новий код має 10 символів: криптографічно випадковий рядок із 32 символів (цифри та латинські літери без неоднозначних i/l/o/u). Регістр вводу не враховується. Він вказує на item `USER#user / COMPLEX_CURSOR#complex#token` у чинній таблиці, де зберігаються userId, complexId і before (точна дата з offset та ID D20). Нові items мають `expiresAt` (Unix seconds) через 30 днів від запису; повторне читання строк не продовжує. GetComplexCursorAsync відхиляє записи з відсутнім/некоректним TTL або expiresAt <= поточний час, не чекаючи асинхронного видалення DynamoDB. Використовується чинний TTL-атрибут таблиці, строки зберігання заявок та receipt не змінюються. Курсор не містить контактів або вмісту заявки.

ComplexRequestsService формує один token на відповідь і додає в CommandOutcome.Pagination лише фінальний курсор з Footer, обраний після обмеження 4096 символів. CommitAsync зберігає його умовним Put `attribute_not_exists(pk)` у тій самій транзакції з receipt і змінами станів діалогу. Колізія коду не перезаписує старий курсор: за відсутності receipt транзакційна помилка передається воркеру для повторної обробки з новим token; за наявності receipt повертається збережена відповідь переможця. Збій надсилання використовує той самий receipt і код, без додаткового запису курсора.

Перехід додає один strongly consistent GetItem за користувачем, комплексом і token; невідомий, прострочений або чужий код пропонує почати з /complex без Query списку. Membership перевіряється перед резолвом. Курсор не надає доступу до даних, актуальні статус/видимість заявок перевіряються як раніше. Сторінка з продовженням додає один невеликий запис у транзакції; кінцева сторінка - жодного. Нових таблиць, індексів, IAM-дозволів чи міграцій немає.

Для сумісності декодуються попередні `p_`-коди з 26 символів (18 байтів: ticks, ID, UTC offset) та старі текстові base64url-курсори. У короткому форматі повний before зберігає точність до 100 нс та offset; D20 для ID відповідає GSI. Такий самий D20 використовується при завершенні повідомлення на межі заявки, щоб не пропускати записи з однаковими датами та різною довжиною ID. Курсор перевіряється перед Query. Відфільтрована порожня сторінка може мати продовження. Результат обмежений розміром повідомлення Telegram, Scan і нових індексів немає.

## Видалення власної нової заявки

`/delete [номер]` використовує той самий `REQUEST_LOOKUP`: `Action=Delete`, спочатку очікується номер, потім підтвердження «Так». У стані підтвердження зберігаються номер і версія заявки, без її вмісту. Старі стани без Action трактуються як View. `/cancel` та інші команди очищують поточний сценарій; чернетка `/new` зберігається окремо.

На кожному кроці перевіряється membership. Заявка читається узгоджено з partition власника з перевіркою комплексу та статусу `New`; після підтвердження додатково порівнюється версія. Commit атомарно записує receipt, завершує діалог, перевіряє активний membership комплексу, видаляє основний запис за умовами version/status/complex і додає `REQUEST#id` / `EVENT#DELETED` з автором і часом. Історія не видаляється і не має TTL. Умова версії запобігає гонці з адміністративним оновленням; повтор після конфлікту повторно читає поточний стан. Після збою Telegram доставка використовує збережену відповідь без повторного видалення.

IAM воркера доповнено Query лише потрібного GSI та DeleteItem/ConditionCheckItem лише таблиці command-data. Права webhook та адміністраторської таблиці не розширюються.

## Сповіщення про адміністративні зміни

`DynamoAdminStore.UpdateRequestAsync` у тій самій транзакції з ActorCheck, versioned Update та аудитом додає `ResidentNotification`, якщо змінився Status або нормалізоване Resolution. Номер та наступна версія формують стабільний event ID. Окремого виклику Telegram або SQS з API немає; конфлікт прав чи версії не створює сповіщення. Повторне збереження незмінного статусу/пояснення не надсилає його знову. Видалення пояснення також повідомляється, решта адміністративних полів самі по собі не створюють події. Контакти, email адміністратора, опис і приватне листування в подію не додаються; текст пояснення доступний тільки автору в приватному Telegram-чаті.

Спільний payload `ResidentNotification` зберігає сумісність із раніше створеними повідомленнями заявок; `RequestId` та `RequestVersion` для реєстрацій дорівнюють null.

`NotificationSchedule` (EventBridge Scheduler, rate 1 minute, flexible window OFF) асинхронно викликає `NotificationFunction`. І Scheduler, і Lambda мають окремо налаштовані retries та спільну стандартну SQS NotificationFailureQueue з 14-денним retention. Це черга помилок запуску, а не самих повідомлень: невідправлені повідомлення лишаються в DynamoDB до обробки. Секрет читає лише роль воркера; AdminApiRole не отримує Telegram-секретів. DynamoDB-доступ воркера обмежений LeadingKeys partition поточного комплексу, без Scan. Окремі read-only дозволи дають воркеру Query `AdministratorsTable/DirectoryIndex` і GetItem поточних налаштувань адміністратора; записів до таблиці адміністраторів він не виконує.

`DynamoNotificationRepository` узгоджено читає CONTROL, потім Query за partition та діапазоном `DUE#` до поточного часу, Limit 25. Claim використовує умовний Update з випадковим leaseToken та leaseExpiresAt = now + 90 seconds; відсутні або зайняті завдання пропускаються. Lambda має timeout 60 секунд, внутрішній бюджет 50: при перериванні lease відновлюється наступним запуском. Після sendMessage транзакція прибирає DUE-запис за leaseToken та додає RESULT без тексту з TTL 30 днів. Обидва ключі лишаються в одному приватному partition і не потрапляють до BuildingRequestsIndex.

Тимчасова помилка атомарно переносить DUE-ключ на наступний час і збільшує attempts: 60, 120, 240 секунд тощо, до 3600 секунд. Невідправлені записи не мають TTL чи максимального числа спроб. Для 429 враховується retry_after і зберігається спільний pauseUntil, який може лише збільшуватись; поточний batch зупиняється. HTTP 400/403 закривають завдання як Undeliverable і не блокують решту; операційний notifier отримує тільки ID події. Фатальна помилка читання/запису журналюється лише за типом, після безпечного сервісного сповіщення виняток передається Lambda для повтору/DLQ.

Успішно завершені завдання не надсилаються повторно. Вузьке вікно між Telegram і commit результату залишається at-least-once: після збою можливий дублікат. Повтори окремих подій можуть змінити порядок повідомлень; текст містить точний час зміни. Історія заявки зберігається без TTL, а попередні адміністративні зміни не ставляться в новий outbox заднім числом.

## Пагінація вебпанелі

Query для заявок, pending-реєстрацій, зареєстрованих мешканців та адміністраторів має Limit 25; runtime не використовує Scan. Cursor з LastEvaluatedKey повертається без змін до наступного запиту й перевіряється на комплекс/каталог. Для обох списків мешканців додатково перевіряється prefix sk, щоб cursor одного списку не використовувався в іншому. Ліміт DynamoDB застосовується до переглянутих записів до фільтрів, тому результат може бути меншим за 25 або порожнім із cursor.

`PaginationComponent` відображає Bootstrap-навігацію та передає дії батьківському `WorkspaceComponent`. Для заявок, pending-реєстрацій, повідомлень та адміністраторів батьківський компонент зберігає поточний номер, cursor наступної сторінки та історію вхідних cursor для переходу назад. Успішна відповідь замінює список; перехід за номером перечитує відповідну сторінку, зберігаючи відомі cursor наступних сторінок. Якщо оновлена відповідь змінила cursor наступної сторінки, подальші cursor відкидаються; якщо cursor відсутній, історія обрізається на поточній сторінці. Загальної кількості та довільного переходу на неотримані сторінки API не обчислює. Числовий пагінатор показує до 10 сусідніх сторінок, першу й останню відомі, а пропуски позначає трикрапкою. Нова доступна сторінка додається за отриманим next cursor; ці списки не завантажуються повністю заради загальної кількості.

Застосовані фільтри зберігаються окремо від редагованих полів форми. Новий пошук, розділ чи список мешканців скидає пагінацію; refresh зберігає поточний вхідний cursor. Номер, дані й cursor змінюються лише після успішного переходу. Навігація блокується під час завантаження/збереження; epoch та номер запиту захищають від запізнілих відповідей після виходу або зміни користувача. Призначення відповідального продовжує завантажувати всі сторінки окремого списку assignees.

### Сортування й фільтри зареєстрованих мешканців

API `/admin/residents` лишається посторінковим Query (Limit 25, узгоджене читання приватного каталогу комплексу). Для сортування всього довідника Workspace послідовно завантажує всі сторінки при відкритті списку та оновленні. Неповне завантаження не підміняє останній успішний список; помилка відображається, повторний cursor перериває цикл. Після кожної відповіді перевіряються epoch та номер завантаження, тому вихід/зміна користувача зупиняють обхід і відкидають застарілі дані. У пам’яті зберігається лише довідник поточного перегляду; вихід і зміна списку очищують його, browser storage не використовується.

Окремий ResidentDirectory фільтрує BuildingNumber (чотири будинки, Unspecified для null/порожнього значення), сортує за RegisteredAt або LastName через Intl.Collator('uk-UA') та розбиває результат по 25. Однойменні мешканці впорядковуються також за ім’ям, потім стабільним ID; відсутні прізвища залишаються в кінці в обох напрямках. Дата використовує час схвалення ApprovedAt з наявним fallback UpdatedAt. Типово registeredAt/desc та всі будинки. Панель показує всі відомі локальні сторінки; зміна фільтра чи напрямку скидає номер на першу, повторне оновлення зберігає параметри й обмежує номер останньою доступною сторінкою.

Початкове читання має вартість O(N) записів і O(N) пам’яті на відкритий довідник; локальні переходи та зміни параметрів не читають DynamoDB повторно. Для поточного комплексу це дозволяє коректний український порядок без нових індексів, дублювання профілів і міграцій. Перегляд є завантаженим знімком, нові зміни з’являються після оновлення; атомарного знімка між API-сторінками немає. Тести цієї логіки запускаються `npm run test --prefix src/Frontend` (Node.js 24, без додаткового test framework), також у CI.

## Сповіщення адміністраторам

Адміністративний запис містить `TelegramChatId` (рядок або null), `NotifyNewResidents`, `NotifyNewRequests`, `NotifyNewAdministrators` (відсутні означають false). `PATCH /admin/administrators/{id}/notifications` приймає лише ці поля та `version`. Активний адміністратор може змінити власні підписки, активний супер адміністратор - також чужі. Для чужого запису транзакція містить ActorCheck ролі та versioned Update; для власного - перевірку IsActive безпосередньо в Update, щоб не звертатися двічі до одного ключа в транзакції. IsSuperAdmin не входить до Update чи його умови; IAM заборона запису цього поля збережена. Settings Update не змінює IsActive. Аудит не містить Chat ID або тексту повідомлень.

`DynamoCommandRepository.CommitAsync` разом із receipt та результатами додає broadcast для завершеної Pending-реєстрації або нової заявки. Чернетки не створюють подій. API додає broadcast для першого адміністративного акаунта в тій самій транзакції з його створенням. Стабільні ID: `new-resident-<reference>-v<version>`, `new-request-<requestId>`, `new-administrator-<sub>`. Broadcast - `ResidentNotification` з AdministratorEvent та OwnerId=0; він ніколи не відправляється в Telegram напряму.

Після lease `ExpandAsync` читає сторінку DirectoryIndex (Limit 25), а для кожного кандидата - узгоджений GetItem основного запису. Поточні IsActive, підписка й валідний Chat ID визначають одержувачів. Транзакція додає індивідуальні DUE-повідомлення (`<eventId>-admin-<sub>`) і checkpoint audienceCursor зі зняттям lease або видаляє завершений broadcast із RESULT=Expanded. При збої checkpoint і повідомлення не розходяться; Retry переносить також audienceCursor. Обробка не обмежується першими 25 адміністраторами. Відсутні підписки та неактивні записи пропускаються. Вибір кандидатів через GSI є eventually consistent.

Індивідуальна доставка повторно GetItem перевіряє актуальну активність, тип підписки та збіг Chat ID. За зміни налаштувань або доступу завдання завершується як Skipped без Telegram. Від’ємні Chat ID дозволені лише для адресних адміністративних повідомлень. Telegram-відправлення та commit результату залишаються at-least-once; стандартні retries, 429 pause, Undeliverable та TTL лише результатів спільні з повідомленнями мешканцям. Типовий broadcast потребує одного запуску для розподілу й наступного для доставки (1–2 хвилини). Повідомлення містять час за Києвом та короткі відомості про подію. NewRequest додатково містить повний Description (до 2000 UTF-16 одиниць) між рядками `~~~~~`; разом із метаданими це вкладається в 4096 символів Telegram. Текст записується в той самий приватний outbox атомарно зі створенням заявки й без змін переноситься в адресні завдання активних підписаних адміністраторів, для Public і Private. Поля профілю мешканця, OwnerId, Resolution та AssignedTo до тексту не додаються. Сервісний notifier не отримує опису; правила публічної проєкції залишаються чинними (опис Public-заявки вже доступний мешканцям, Private - лише автору й адміністраторам). Новий формат застосовується до новостворених подій; наявні outbox-записи не перезаписуються.

## Текст заявки у списках бота

`/my` показує повний опис власних заявок; `/complex` додає Description до `PublicRequestSummary` лише після перевірки поточного основного запису (свій комплекс, Public, New/InProgress). ПІБ, контакти та Resolution до цієї проєкції не входять. Загальнодоступний опис - саме текст Public-заявки, а не приватне листування.

`RequestListText` спільно форматує дату подання (Europe/Kyiv), рядок місця й опис для `/my` та `/complex`. Опис оточений окремими рядками `~~~~~`, а посилання `/request` у власному списку розміщене після нижнього розділювача. LocationLine включає тільки непорожній будинок і наявні значення під’їзду/поверху; floor=0 залишається «Парадне», Scope=Complex - «Весь комплекс». За відсутності всіх частин рядок місця повністю пропускається; заглушки «Не зазначено», «без прив’язки» та «Будинок не уточнено» у списках не показуються. Спільний ComplexLayout.Label для деталей, повідомлень та інших сценаріїв не змінюється.

`RequestListText` формує одне повідомлення до 4096 UTF-16 code units разом із заголовком, розділювачами та командою наступної сторінки. Повні валідні описи до 2000 символів не скорочуються. За браку місця список завершується на межі заявки: `/my` продовжує за ID останньої показаної заявки, `/complex` - за її CreatedAt#Id. Якщо всі отримані елементи показано, зберігається cursor репозиторію; це також забезпечує перехід після порожніх відфільтрованих сторінок. Backend-ліміти читання залишаються 10 та 5 відповідно. Завеликі поля старих записів обмежуються захисно, без розриву UTF-16 surrogate pair; runtime не додає Scan чи нових індексів.

`Entrance` зберігається в payload заявки та чернетки; початковий аудит містить його за наявності, аудит адміністративних змін - у changes. API перевіряє під’їзд спільним ComplexLayout.IsValid, не допускає 2 для 4Б або будь-який під’їзд для Scope=Complex. Нового індексу чи Scan немає. Вебпанель показує під’їзд у рядку місця та дозволяє редагування через ng-select. Відкриття старої заявки не заповнює під’їзд; явний вибір будинку 4Б в редакторі встановлює 1. Для розгортання backend потрібно оновити перед фронтендом.

## Масові повідомлення мешканцям

`GET/POST /admin/messages` доступні лише активним супер адміністраторам. POST приймає UUID `id` та звичайний `text` (1–4096 UTF-16 одиниць до trim); інші поля відхиляються. Сервер призначає автора й час. Транзакція перевіряє поточні `IsActive` і `IsSuperAdmin`, створює immutable записи `MESSAGES#<complexId>` / `ID#<uuid>` та `MESSAGE#<UTC timestamp>#<uuid>` і приватний outbox. Історія одночасно є аудитом створення й не має TTL. Повтор того самого UUID повертає існуючий запис лише за збігу автора й тексту; інший payload отримує 409. GET виконує strongly consistent Query префіксу `MESSAGE#`, descending, Limit 25; курсор перевіряє partition і префікс.

`ResidentNotification.ResidentBroadcastId` позначає розсилку. Батьківський job має OwnerId=0 та `IsBroadcast`; він ніколи не передається Telegram. Воркер читає `BUILDING#<complexId>` / `RESIDENT#` через strongly consistent Query по 25 записів, перевіряє комплекс, Approved, позитивний UserId та дату схвалення не пізніше дати розсилки. Тим самим нові реєстрації не отримують старих оголошень. Одержувачі відповідають підтвердженим реєстраціям, як і в розділі мешканців; окремої перевірки поточного membership немає.

Транзакція за lease створює recipient jobs зі стабільними ID й зберігає курсор наступної сторінки батька або завершує його. Claim порівнює прочитаний audienceCursor, щоб застарілий список завдань з іншого запуску не повторив уже розгорнуту сторінку. Після збоїв продовження використовує збережений курсор; pending jobs не мають TTL. Recipient job використовує звичайні retry, throttling та terminal результати доставки. IAM воркера додає лише Query до partition довідника поточного комплексу, без Scan чи права запису до нього; роль не отримує доступу до історії повідомлень.

Вебпанель має маршрут `/messages` і приховує навігацію/перенаправляє прямий вхід для звичайного адміністратора. CloudFront переписує цей SPA-маршрут на index.html. UI зберігає ID спроби після помилки для безпечного повтору незміненого тексту, блокує повторні дії й навігацію під час POST та очищує форму лише після підтвердження API. Історія показує прийняття розсилки, а не непідтверджений стан доставки.

## Приватні дані автора заявки

Лише `GET /admin/requests/<ownerId>/<requestId>` додає `author` до адміністративного DTO: FirstName, LastName, BuildingNumber та ApartmentNumber. Сервер перевіряє комплекс і власника профілю, читає його через strongly consistent GetItem; за відсутності чи невідповідності повертає null. Список заявок не виконує lookup кожного автора; PATCH і читання історії не завантажують цю проєкцію. Профіль не додається до MaintenanceRequest, GSI чи PublicRequestSummary, телефон та Telegram ID не входять до author.

Діалог завантажує деталі та історію паралельно, показує стан завантаження автора, потім ПІБ і лише наявні частини адреси під описом. Epoch, номер запиту та вибрана заявка захищають від застарілих відповідей при виході, закритті та повторному відкритті. Старі мешканці мають ПІБ без вигаданої адреси; за відсутності імені показується «Мешканець». Приватні списки Pending та Approved також повертають і показують nullable BuildingNumber і ApartmentNumber для перевірки адміністратором.

## Персональне меню Telegram

Початок, продовження й повторне подання реєстрації після відхилення доступні через /start. При повторному поданні бот показує попередню причину відхилення та починає з власного контакту. Старий alias початку реєстрації збережено для сумісності введених вручну повідомлень, але він відсутній у меню та користувацьких текстах. У /help немає команди окремого перегляду категорій - категорія обирається під час /new.

`Telegram/command-menu.json` вбудовується в assembly бота і використовується операторським `configure-telegram-menu.py`. Список схваленого мешканця додатково виключає /start. Кожне приватне меню встановлюється через setMyCommands зі scope chat для language_code="" та "uk". CommandProcessor перевіряє поточний membership перед доставкою незавершеної відповіді й синхронізує меню; доставлений receipt не повторює зовнішніх дій. NotificationProcessor встановлює меню мешканця перед доставкою приватного сповіщення, включно з підтвердженням схвалення. Broadcast, skipped jobs та адміністративні сповіщення не змінюють меню.

TelegramClient кешує лише успішне завершення обох мов для chat/status, максимум 1000 чатів на інстанс. Зміна membership інвалідує відповідний кеш за значенням; нова версія Lambda починає без кешу. Оновлення меню ідемпотентне; частковий збій повторюється через наявні SQS/outbox retries, 429 передає retry_after. Токени й payload не журналюються. Операторський --include-residents оновлює chat scope вже схваленим мешканцям через пагінований Query каталогу, без Scan та sendMessage. Це зміна доступності команд у меню, а не заборона введення прихованих сумісних команд вручну і не заміна перевірки доступу.

## Самостійне керування профілем

Команди `/edit_profile` та `/delete_profile` доступні лише за активним membership і показуються лише в персональному меню мешканця (`registered_only` у спільному JSON, без цього службового атрибута в Telegram payload). Профіль редагується через окремий versioned `USER#<id>` / `PROFILE_DIALOG`: action, expectedProfileVersion, active та draft. Поточний Approved-профіль не використовується як чернетка. Редагування повторює перевірку власного contact і введення ПІБ, будинку та квартири через спільний RegistrationService.Advance; фінальний Pending-результат перетворюється на Approved без подання на повторне схвалення і без NewResident broadcast. Видалення приймає лише точне підтвердження кнопкою, contact замість тексту не підходить.

Commit атомарно з receipt закриває й очищує діалог, перевіряє membership комплексу і version джерела, записує USER/REGISTRATION, поточний REGISTRATION#reference/META та BUILDING#complex/RESIDENT#user. Заявки, їхні індекси й історія не змінюються; Scan та масового обходу заявок немає. Перерваний або скасований діалог не змінює Approved-профіль. Зміна версії під час діалогу закриває його з пропозицією почати знову. Owner і complex перевіряються в сервісі та persistence; повтор update використовує receipt.

PersonalDataDeleted та PersonalDataDeletedAt - nullable-сумісна позначка очищення поточних даних. Tombstone не містить телефону, ПІБ, адреси або причини рішення; лише внутрішні ключі, версію та дати. ApprovedAt фіксує попередню дату схвалення (для старих записів - попередній UpdatedAt), тому редагування не змінює дату реєстрації чи аудиторію раніше створених розсилок. API показує позначку видалення, поки PersonalDataDeleted=true, Stage=Deleted або профіль із PersonalDataDeletedAt ще не схвалений. Після Approved та PersonalDataDeleted=false показується поточний профіль за UserId і комплексом незалежно від дати створення заявки та reference нової реєстрації. PersonalDataDeletedAt зберігається як історична позначка, але не забороняє відображення актуальних даних після повторної реєстрації. Імена в історії створення використовують ту саму перевірку. Обчислювана HasDeletedPersonalData не серіалізується в DynamoDB; міграції та перезапису заявок немає.

Команда очищує три поточні проєкції профілю й активну чернетку. Історичні реєстрації з іншими reference, receipt, черги, резервні копії та зовнішні Telegram-повідомлення не видаляються цією транзакцією; це не процедура повного стирання всіх копій персональних даних. Наявні TTL/retention не змінюються. Внутрішній UserId залишається для належності збережених заявок; після видалення membership стає неактивним.

## Автоматичне схвалення мешканців

`residentApprovalMode` у Serverless params типово Automatic; лише commandProcessor отримує RESIDENT_APPROVAL_MODE. ResidentApprovalConfiguration приймає Automatic/Manual, невідоме значення перериває запуск замість надання доступу. CommandHandler передає режим RegistrationService. Спільний Advance як і раніше готує Pending, тому редагування профілю та ручний процес збережені. ContinueAsync у Automatic перетворює лише нове успішне завершення чернетки в Approved, встановлює ApprovedAt і явний AutomaticallyApproved у RegistrationChange. Наявний Pending не переводиться автоматично.

Commit перевіряє власника, завершені дані, version та дату схвалення. Одна транзакція містить receipt, versioned USER/REGISTRATION, REGISTRATION#reference/META, каталог RESIDENT#, активний membership зі scope поточного комплексу, аудит EVENT#DECIDED (actor=system, approvalMode=Automatic) та NewResident outbox. Pending-проєкція не створюється. Підтвердження мешканцю міститься в receipt останнього кроку; окреме дублююче сповіщення йому не створюється. Після commit CommandProcessor синхронізує меню з активним membership. Підписані адміністратори отримують NewResident із текстом про автоматичне схвалення, без пропозиції повторної перевірки. Повтор update не додає другу подію чи аудит.

Manual зберігає Pending-проєкцію, закритий доступ та ручне рішення через API/скрипт. Налаштування не впливає на RegisterAccountAsync, IsActive/IsSuperAdmin адміністраторів чи Cognito. Міграції та масового схвалення наявних записів немає.

## Відкликання доступу після видалення профілю

Підтвердження /delete_profile записує Stage=Deleted і active=false в membership у тій самій транзакції з очищенням трьох профільних проєкцій, закриттям діалогу та receipt. Замість ConditionCheck для цього membership використовується умовний Update, щоб не звертатися двічі до того самого item. Condition перевіряє активний доступ і комплекс до відкликання. CommandProcessor бачить неактивний membership і встановлює загальний chat menu до надсилання підтвердження. /start починає нову реєстрацію з телефону, старі дані не підставляються. До завершення всіх кроків команди заявок недоступні; схвалення діє за чинним режимом Automatic/Manual. Позначка попереднього видалення переноситься в нову реєстрацію, щоб приховувати дані до її схвалення. Після схвалення старі заявки знову показують поточний профіль того самого Telegram-користувача.

Notification repository перед доставкою мешканцю strongly consistent GetItem перевіряє поточну проєкцію RESIDENT#: комплекс, UserId, Approved, відсутність PersonalDataDeleted. Події видалених профілів пропускаються та не можуть повернути registered menu. Меню встановлює лише сповіщення про схвалення реєстрації, а не довільні старі зміни заявок чи розсилки. Fan-out також виключає видалені профілі. IAM воркера додає лише GetItem до вже доступного partition каталогу поточного комплексу.

revoke-deleted-residents.py узгоджує старі Approved+PersonalDataDeleted профілі з новою поведінкою через Query каталогу й strongly consistent читання поточного профілю. Транзакція перевіряє version/payload, змінює три поточні копії на Deleted і деактивує membership. Відновлений профіль не змінюється; повторний запуск пропускає вже узгоджені записи. configure-telegram-menu.py --include-residents встановлює гостям із позначкою видалення common chat scope, а схваленим - resident scope. Списки взаємно виключаються, результат перевіряється для обох мов.

## Сортування вебпанелі за пріоритетом

`requestPriorityCreatedAt` = `<rank>#<CreatedAt UTC O>#<requestId D20>`, rank: Urgent=3, High=2, Normal=1, Low=0. Відсутній/невідомий старий пріоритет в індексному ключі вважається Normal. Новий GSI BuildingPriorityRequestsIndex має PK=requestBuildingId, SK=requestPriorityCreatedAt, ALL projection; API має Query-дозвіл на нього. Створення ботом записує ключ разом із payload; UpdateRequestAsync атомарно оновлює його з versioned payload та аудитом, зберігаючи CreatedAt. Старий BuildingRequestsIndex збережено для Telegram та початкового Date-режиму.

ListRequestsAsync у Priority-режимі проходить bucket 3→2→1→0; кожен Query descending у межах rank#date range. From/To обмежують KeyCondition кожного bucket, решта фільтрів застосовуються як раніше. На сторінку оцінюється сумарно не більше 25 записів, до чотирьох Query; сторінка може бути порожньою з продовженням після фільтрів. Cursor містить complex, priority та LastEvaluatedKey поточного bucket або наступний bucket без ключа. Перевіряються комплекс, rank і префікси ключів. Сортування не виконується в браузері й охоплює всі сторінки. Рівні часи впорядковані за ID. Як і раніше, GSI має eventual consistency, а пагінація при паралельних редагуваннях не є snapshot.

REQUEST_SORT_MODE передається лише Admin API з Serverless param requestSortMode (Priority за замовчуванням, Date для міграції/відкату). Початковий деплой Date створює GSI й оновлює writers без зміни чинної вибірки. Операторський backfill-request-priority.py через окремий Scan додає ключі лише заявкам свого комплексу з condition на попередній payload. Після перевірки заповнення індексу виконується перемикання Priority. Нових таблиць немає; Runtime Scan не додається. Інструкція у README є обов’язковою для першого розгортання цього індексу.

Bootstrap warning/danger бейджі у першому рядку картки дублюють кольоровий лівий бордер 4px, зберігаючи текстове значення пріоритету. Ng-select використовує спільний список ticketPriorities з ng-option-tmp та ng-label-tmp. Інші бордери картки не потовщуються. Після успішної зміни пріоритету Workspace скидає cursor й завантажує першу сторінку; при помилці форма зберігається.

## Сервісні сповіщення про помилки

OsbbRequests.Shared/Telegram містить кешований SsmSecretProvider та TelegramServiceNotifier, доступні Bot і AdminApi без залежності API від Bot. Сервісний чат типово 38627946, SecureString типово /shared/telegram/service-bot-token; це той самий сервісний канал, що у olx-watcher. Provider environment містить лише SERVICE_NOTIFICATION_CHAT_ID і SERVICE_BOT_TOKEN_PARAMETER, а не значення токена. Чотири окремі IAM-ролі отримують GetParameter тільки цього параметра додатково до власних дозволів. Власні чат/параметр задаються Serverless params serviceNotificationChatId/serviceBotTokenParameter. ADMIN_TELEGRAM_CHAT_ID замінено цими налаштуваннями.

Webhook та Admin API обробляють операцію з таймаутом сім секунд, резервуючи до двох секунд для повідомлення у межах timeout 10. SQS-воркер зберігає FIFO partial failure і visibility retry_after; помилка Defer теж повідомляється. NotificationProcessor спочатку фіксує retry/Undeliverable, потім сповіщає сервіс; помилки сховища виходять у NotificationFunction, яка повідомляє і повторно кидає початковий виняток. Бізнесові 4xx та штатний 429 не створюють зайвих сповіщень. Усі виклики проходять ReportSafelyAsync: навіть throwing notifier у тесті не маскує основний результат.

У сервісне повідомлення входять Lambda, stage, назва операції, тип винятку, AWS Request ID або ID події та до п’яти назв методів, без файлових шляхів. Exception.Message/ToString та текст команд/контактів/HTTP-запитів не копіюються. Поля обмежені по довжині, формат plain text, preview вимкнений. Збій читання секрету, Telegram HTTP/ok=false, таймаут або транспортна помилка журналюються лише за типом чи HTTP-кодом, без URL/response body і токена. Сервісний канал має двосекундний timeout незалежно від скасованого робочого token; повторів/рекурсивних алертів немає. Це best effort, без outbox: керовані помилки обробки повідомляються, hard timeout/OOM та помилки ініціалізації потребують зовнішніх alarm/DLQ. Доставка мешканцям з API як і раніше здійснюється лише через транзакційний outbox, без прямого Telegram-виклику.
