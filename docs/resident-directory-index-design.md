# Індекс каталогу зареєстрованих мешканців

Це проєкт першого етапу оптимізації `/admin/residents/directory` для сортування за датою реєстрації. Поточний API читає весь розділ `ResidentsByDate` зі схваленими профілями, фільтрує й сортує в пам’яті та повертає 25 рядків. Запропонована схема читає потрібний діапазон компактних рядків. Експорт, сортування за прізвищем, реєстрації на перевірці й мешканці з ключами залишаються поза першим етапом.

## Ключі та кількість записів

У таблиці `residents` основний ключ складається лише з `pk`. Для швидкого читання каталогу пропонується розріджений GSI `ResidentDirectoryByDate` з ключами `listGroup` і `listOrder` та `ResidentDirectoryByDateDescending` з ключами `listGroup` і `listOrderDescending`. В індекс потрапляють окремі рядки проєкції чинних схвалених реєстрацій. Основний ключ рядка має формат `COMPLEX#<id>#DIRECTORY_ROW#<вид>#<userId>`, де вид — `ALL`, `BUILDING`, `TYPE` або `BUILDING_TYPE`. Ключ рядка стабільний при зміні будинку чи типу, тому запис можна оновити умовним `Put`. DynamoDB перенесе відповідний запис між розділами GSI, якщо зміниться `listGroup`.

| Фільтр | Значення `listGroup` після `COMPLEX#<id>#APPROVED#` | Приклад |
| --- | --- | --- |
| Усі | `ALL` | `…#APPROVED#ALL` |
| Будинок | `BUILDING#<building>` | `…#APPROVED#BUILDING#4Б` |
| Тип | `TYPE#<type>` | `…#APPROVED#TYPE#Owner` |
| Будинок і тип | `BUILDING_TYPE#<building>#<type>` | `…#APPROVED#BUILDING_TYPE#4Б#Owner` |

Порожній будинок нормалізується до `Unspecified`, тип береться з десеріалізованого профілю, включно з типовим `FamilyMember` для старих записів. Усі чотири види мають однакову проєкцію `INCLUDE`: ID реєстрації, ім’я, прізвище, тип, будинок і квартира. Дата доступна з ключа сортування. Телефон, email, згода, історія, версія редагування та повний `payload` у проєкцію не входять. Для деталей потрібне окреме авторизоване читання поточного профілю. Поточна модалка отримує частину цих полів зі списку, тож цей контракт треба змінити до перемикання читання.

| Варіант | Рядків проєкції на мешканця | Читання сторінки |
| --- | ---: | --- |
| `ALL` | 1 | Усі читаються напряму. Будинок і тип відсіюються після читання. |
| `ALL` + `BUILDING` | 2 | Усі й будинок читаються напряму. Тип відсіюється в обраному діапазоні. |
| Усі чотири види | 4 | Кожен сценарій читає один відповідний діапазон, без відсіювання за будинком чи типом. |

Для першого запуску рекомендовано **два види (`ALL` і `BUILDING`)**. Вони одразу усунуть повне читання каталогу для типового списку й списку за будинком. Фільтр типу виконуватиметься по компактних рядках відповідного діапазону й зупинятиметься, щойно набрано сторінку або вичерпано діапазон. Для рідкісного типу запит може прочитати значну частину діапазону. `TYPE` і `BUILDING_TYPE` мають сенс, якщо вимірювання покажуть, що типові фільтри часто відсіюють багато рядків. Для `N` чинних мешканців це відповідно `N`, `2N` або `4N` базових рядків і стільки ж записів **на кожен** індекс порядку. Це оцінка кількості записів, а не WRU. На WRU впливають розмір, транзакційні записи й зміни ключів індексу.

## Порядок, статистика й пагінація

- Джерело дати — `ApprovedAt ?? UpdatedAt`, як у поточному API. Поточний порядок для однакової дати — ID реєстрації за зростанням в обох напрямках. Простий розворот одного GSI розверне й ID. Для точного збереження порядку рекомендовано два GSI з однаковим `listGroup`, але різними ключами сортування. Для зростання це UTC ticks у форматі `D19` та `#<registrationId>`. Для спадання — `(DateTime.MaxValue.Ticks - utcTicks)` у форматі `D19` та той самий суфікс. Обидва читаються за зростанням. Другий GSI додає індексні записи, не збільшуючи кількості рядків проєкції.
- Для точних підрахунків достатньо окремого запису з кількістю за типом для комплексу та кожного будинку, включно з `Unspecified`. Для комплексу з чотирма будинками це шість записів, незалежно від кількості мешканців. Сума за типами дає панель статистики, а значення вибраного типу — `total` списку для пагінації. Як і зараз, фільтр типу не звужує панель статистики. Проєкції та зміни лічильників слід записувати в транзакції профілю. GSI може короткочасно відставати від лічильників.
- Для переходів використовувати курсор, прив’язаний до комплексу, фільтрів і напрямку. Перший стрибок на невідвідану сторінку потребує проходу від найближчого відомого курсора в тому самому діапазоні. Під час фільтрації за типом рахуються лише відповідні рядки. Точний `total` дає кількість сторінок, але не позицію курсора.

Перед перемиканням читання потрібно охопити всі зміни чинного профілю, зокрема автоматичне й ручне схвалення, зміну будинку або типу, видалення, повторну реєстрацію й `manage-residents.py`. Заповнення наявних проєкцій має враховувати версію джерела, а початкові лічильники потребують звірки з паралельними змінами. Перевірка має охопити старі профілі, однакові дати, порядок в обох напрямках і адреси без будинку. В dev порівнювати RRU для кожного сценарію, частку відсіяних рядків і WRU на зміну профілю.

## Розгортання запису

Перший пакет підтримує запис `ALL` і `BUILDING` у транзакціях бота, Admin API та `manage-residents.py`. Будинковий рядок зберігає версію, будинок і тип останньої врахованої проєкції. Редагування та видалення читають його узгоджено, а транзакція перевіряє версію рядка або його відсутність. Профіль, обидва рядки й зміни лічильників фіксуються разом. Для ще не врахованих старих профілів перше редагування додає проєкції та лічильники, а видалення перевіряє відсутність рядка на випадок одночасного заповнення. Після початку запису використовуйте оновлений операторський скрипт разом з оновленим бекендом. Якщо повертається стара версія запису, перед перемиканням читання потрібно повторно звірити й відновити проєкції та лічильники.

CloudFormation приймає одну зміну GSI таблиці за оновлення. Стандартний деплой додає `ResidentDirectoryByDate`. Дочекайтеся стану `ACTIVE` у `DescribeTable`, а тоді додайте `ResidentDirectoryByDateDescending` наступним оновленням із параметром `--param=residentDirectoryDescendingIndex=true`. Зберігайте це значення в наступних деплоях відповідного середовища. [AWS CloudFormation: AWS::DynamoDB::Table](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-dynamodb-table.html)

Читання адмінпанелі використовує чинні індекси. Нові лічильники охоплюють тільки профілі, для яких уже записано проєкції. Наступний етап додає заповнення та звірку з чинними профілями. Кожен запис заповнення має перевірити версію джерела і відсутність проєкції в транзакції, що додає обидва рядки та збільшує лічильники.
