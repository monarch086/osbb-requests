# Індекс каталогу зареєстрованих мешканців

Це проєкт першого етапу оптимізації `/admin/residents/directory` для сортування за датою реєстрації. Поточний API читає весь розділ `ResidentsByDate` зі схваленими профілями, фільтрує й сортує в пам’яті та повертає 25 рядків. Запропонована схема читає потрібний діапазон компактних рядків. Експорт, реєстрації на перевірці й мешканці з ключами використовують попередній шлях. Сортування за прізвищем підключається окремим етапом.

## Ключі та кількість записів

У таблиці `residents` основний ключ складається лише з `pk`. Для швидкого читання каталогу пропонується розріджений GSI `ResidentDirectoryByDate` з ключами `listGroup` і `listOrder` та `ResidentDirectoryByDateDescending` з ключами `listGroup` і `listOrderDescending`. В індекс потрапляють окремі рядки проєкції чинних схвалених реєстрацій. Основний ключ рядка має формат `COMPLEX#<id>#DIRECTORY_ROW#<вид>#<userId>`, де вид — `ALL`, `BUILDING`, `TYPE` або `BUILDING_TYPE`. Ключ рядка стабільний при зміні будинку чи типу, тому запис можна оновити умовним `Put`. DynamoDB перенесе відповідний запис між розділами GSI, якщо зміниться `listGroup`.

| Фільтр | Значення `listGroup` після `COMPLEX#<id>#APPROVED#` | Приклад |
| --- | --- | --- |
| Усі | `ALL` | `…#APPROVED#ALL` |
| Будинок | `BUILDING#<building>` | `…#APPROVED#BUILDING#4Б` |
| Тип | `TYPE#<type>` | `…#APPROVED#TYPE#Owner` |
| Будинок і тип | `BUILDING_TYPE#<building>#<type>` | `…#APPROVED#BUILDING_TYPE#4Б#Owner` |

Порожній будинок нормалізується до `Unspecified`, тип береться з десеріалізованого профілю, включно з типовим `FamilyMember` для старих записів. Усі чотири види мають однакову проєкцію `INCLUDE`: ID реєстрації, ім’я, прізвище, тип, будинок і квартира. Дата доступна з ключа сортування. Телефон, email, згода, історія, версія редагування та повний `payload` у проєкцію не входять. Для деталей потрібне окреме авторизоване читання поточного профілю. Поточна модалка отримує частину цих полів зі списку, тож цей контракт треба змінити до перемикання читання.

| Варіант | Рядків проєкції на мешканця | Читання сторінки |
| --- | ---: | --- |
| `ALL` | 1 | Усі читаються напряму. Будинок і тип відсіюються після читання. |
| `ALL` + `BUILDING` | 2 | Усі й будинок читаються напряму. Тип відсіюється в обраному діапазоні. |
| Усі чотири види | 4 | Кожен сценарій читає один відповідний діапазон, без відсіювання за будинком чи типом. |

Для першого запуску рекомендовано **два види (`ALL` і `BUILDING`)**. Вони одразу усунуть повне читання каталогу для типового списку й списку за будинком. Фільтр типу виконуватиметься по компактних рядках відповідного діапазону й зупинятиметься, щойно набрано сторінку або вичерпано діапазон. Для рідкісного типу запит може прочитати значну частину діапазону. `TYPE` і `BUILDING_TYPE` мають сенс, якщо вимірювання покажуть, що типові фільтри часто відсіюють багато рядків. Для `N` чинних мешканців це відповідно `N`, `2N` або `4N` базових рядків і стільки ж записів **на кожен** індекс порядку. Це оцінка кількості записів, а не WRU. На WRU впливають розмір, транзакційні записи й зміни ключів індексу.

## Порядок, статистика й пагінація

- Джерело дати — `ApprovedAt ?? UpdatedAt`, як у поточному API. Поточний порядок для однакової дати — ID реєстрації за зростанням в обох напрямках. Простий розворот одного GSI розверне й ID. Для точного збереження порядку рекомендовано два GSI з однаковим `listGroup`, але різними ключами сортування. Для зростання це UTC ticks у форматі `D19` та `#<registrationId>`. Для спадання — `(DateTime.MaxValue.Ticks - utcTicks)` у форматі `D19` та той самий суфікс. Обидва читаються за зростанням. Другий GSI додає індексні записи, не збільшуючи кількості рядків проєкції.
- Для точних підрахунків достатньо окремого запису з кількістю за типом для комплексу та кожного будинку, включно з `Unspecified`. Для комплексу з чотирма будинками це шість записів, незалежно від кількості мешканців. Сума за типами дає панель статистики, а значення вибраного типу — `total` списку для пагінації. Як і зараз, фільтр типу не звужує панель статистики. Проєкції та зміни лічильників слід записувати в транзакції профілю. GSI може короткочасно відставати від лічильників.
- Для переходів використовувати курсор, прив’язаний до комплексу, фільтрів і напрямку. Перший стрибок на невідвідану сторінку потребує проходу від найближчого відомого курсора в тому самому діапазоні. Під час фільтрації за типом рахуються лише відповідні рядки. Точний `total` дає кількість сторінок, але не позицію курсора.

Перед перемиканням читання потрібно охопити всі зміни чинного профілю, зокрема автоматичне й ручне схвалення, зміну будинку або типу, видалення, повторну реєстрацію й `manage-residents.py`. Заповнення наявних проєкцій має враховувати версію джерела, а початкові лічильники потребують звірки з паралельними змінами. Перевірка має охопити старі профілі, однакові дати, порядок в обох напрямках і адреси без будинку. В dev порівнювати RRU для кожного сценарію, частку відсіяних рядків і WRU на зміну профілю.

## Розгортання запису

Перший пакет підтримує запис `ALL` і `BUILDING` у транзакціях бота, Admin API та `manage-residents.py`. Будинковий рядок зберігає версію, будинок і тип останньої врахованої проєкції. Редагування та видалення читають його узгоджено, а транзакція перевіряє версію рядка або його відсутність. Профіль, обидва рядки й зміни лічильників фіксуються разом. Для ще не врахованих старих профілів перше редагування додає проєкції та лічильники, а видалення перевіряє відсутність рядка на випадок одночасного заповнення. Після початку запису використовуйте оновлений операторський скрипт разом з оновленим бекендом. Якщо повертається стара версія запису, перед перемиканням читання потрібно повторно звірити й відновити проєкції та лічильники.

CloudFormation приймає одну зміну GSI таблиці за оновлення. Стандартний деплой додає `ResidentDirectoryByDate`. Дочекайтеся стану `ACTIVE` у `DescribeTable`, а тоді додайте `ResidentDirectoryByDateDescending` наступним оновленням із параметром `--param=residentDirectoryDescendingIndex=true`. Для dev після другого оновлення значення `true` зафіксовано у `serverless.yml`. Для інших середовищ зберігайте це значення в наступних деплоях після створення обох індексів. [AWS CloudFormation: AWS::DynamoDB::Table](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-dynamodb-table.html)

Читання адмінпанелі використовує чинні індекси. Нові лічильники охоплюють тільки профілі, для яких уже записано проєкції. Скрипт заповнення перевіряє версію й вміст джерела та відсутність обох проєкцій у транзакції, що додає рядки й збільшує лічильники. Він залишає часткові або змінені проєкції для окремого розбору, щоб уникнути подвійного підрахунку.

Після деплою всіх шляхів запису в dev:

```bash
python3 scripts/backfill-resident-directory.py --stage dev --region eu-central-1
python3 scripts/backfill-resident-directory.py --stage dev --region eu-central-1 --apply --confirm-stage dev
python3 scripts/backfill-resident-directory.py --stage dev --region eu-central-1 --verify-indexes
```

Перший виклик тільки читає дані. Ненульовий код із `missing_rows` і `counter_mismatches` очікуваний до заповнення. Перед `--apply` перегляньте `invalid_profiles`, `orphaned_rows` і `changed_rows`, а також переконайтеся, що `partial_profiles` дорівнює нулю. Операція ідемпотентна й повторно звіряє базову таблицю після запису. Останній виклик також перевіряє, що обидва GSI мають статус `ACTIVE` і повертають ті самі рядки в очікуваному порядку. Перед перемиканням читання всі лічильники розбіжностей мають бути нульовими. Паралельні зміни та затримка GSI можуть дати тимчасові розбіжності, тому повторіть звірку після стабілізації. Для нестандартного ID комплексу вкажіть `--complex-id` у всіх командах. Скрипт виводить лише кількості.


## Перемикання читання

Після звірки запускайте backend з `--param=compactResidentDirectory=true`, потім розгорніть фронтенд. У dev параметр увімкнено в `serverless.yml` після звірки. Для відкату читання передайте `--param=compactResidentDirectory=false`; повний профіль і далі завантажуватиметься через `GET /admin/residents/{id}`. Цей маршрут перевіряє доступ до зареєстрованих мешканців і перечитує поточну реєстрацію узгоджено.

Новий фронтенд запитує компактний контракт явно через `compact=true`. Для порядку за датою API читає один узгоджений лічильник і потрібний діапазон GSI. Фільтр за типом може потребувати додаткових читань. Переходи на відвідані сторінки повторно використовують їхні курсори. При стрибку на невідвідану сторінку API відраховує рядки від найближчого відомого курсора. GSI оновлюється асинхронно, тому одразу після змін рядки можуть короткочасно відставати від лічильників. Підрозділ реєстрацій на перевірці та Excel використовують попередній шлях.

## Порядок за прізвищем

Компактні рядки мають два двійкові ключі `listNameOrder` та `listNameOrderDescending`. Генератор використовує правила `uk-UA`, порівнює прізвище й ім’я без урахування регістру, а за рівності впорядковує за ID реєстрації. Записи без прізвища стоять в кінці в обох напрямках. Бот, Admin API та операторський .NET-генератор використовують однакову зафіксовану версію ICU. Для операторських скриптів потрібен .NET SDK із `global.json`. Курсори прив’язані до виду сортування, групи, фільтра типу та напрямку.

`ResidentDirectoryByName` та `ResidentDirectoryByNameDescending` є розрідженими індексами компактних рядків. Вони використовують чинні `ALL` / `BUILDING` групи та ті самі лічильники. Старий `ResidentsByName` не використовується для нового читання.

1. Розгорніть підтримку запису та перший GSI через `--param=residentDirectoryNameIndex=true`. Після `ACTIVE` додайте до цієї команди `--param=residentDirectoryNameDescendingIndex=true` і дочекайтеся `ACTIVE` другого GSI. Використовуйте оновлений `manage-residents.py`. Обидва GSI вже включені до конфігурації dev після поетапного деплою.
2. Запустіть dry-run `scripts/backfill-resident-directory.py` з відповідним stage і region. Скрипт перевірить порядок ключів проти поточного компаратора. З `--apply --confirm-stage STAGE` він допише відсутні ключі до наявних рядків у транзакції з перевіркою версії, без повторного збільшення лічильників.
3. Повторіть dry-run із `--verify-indexes --verify-name-indexes`. За відсутності розбіжностей додайте `--param=compactResidentNameDirectory=true` до наступного деплою. У dev нове читання увімкнене за замовчуванням після звірки. Зберігайте параметри створення GSI у наступних деплоях. Щоб відкотити шлях читання, передайте `--param=compactResidentNameDirectory=false` разом з обома параметрами створення GSI.
4. Якщо для профілю ключ перевищив обмеження DynamoDB у 1024 байти, запис профілю та каталогу за датою продовжується. Сортування за прізвищем у відповідних групах повертається до попереднього читання. Перед увімкненням нового читання dry-run має пройти для всіх профілів.
