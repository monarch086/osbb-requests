# ЖК «Зелений острів 2» — заявки мешканців

Telegram-бот і вебпанель ОСББ для чотирьох будинків комплексу (4Б, 4В, 4Г, 4Д) та прибудинкової території.

## Можливості

- Мешканець реєструється в боті, керує своїм профілем, створює заявки, переглядає власні й відкриті заявки комплексу та отримує сповіщення. Для власників доступні замовлення ключів, а також подання додаткових квартир на перевірку.
- Адміністратор керує заявками, реєстраціями та ключами, переглядає історію змін, експортує відфільтровані списки в Excel і налаштовує доступи та сповіщення відповідно до своєї ролі.
- Розсилки надходять мешканцям через Telegram. Пояснення адміністратора додається до історії заявки. Мешканець може відповісти на сповіщення або використати `/comment номер текст`.

Функціональні вимоги описані в [docs/requirements.md](docs/requirements.md), а структура застосунку — в [docs/architecture.md](docs/architecture.md).

### Створення заявки

Команда `/new` спочатку запитує категорію. Для звичайної заявки потім показує кнопки «Будинок 4Б», «Будинок 4В», «Будинок 4Г», «Будинок 4Д» та «Прибудинкова територія». Для будинків 4В, 4Г та 4Д бот спочатку запитує під’їзд: «1», «2» або «Не зазначено». Для 4Б під’їзд автоматично дорівнює 1, запит пропускається. Для конкретного будинку бот далі пропонує кнопки поверхів 1–25, потім запитує опис. Старі кнопки «Парадне» та «Без поверху», які могли залишитися у відкритих діалогах, підтримуються для сумісності. Для прибудинкової території крок поверху пропускається. Після коректного опису заявка створюється; `/new` відновлює незавершений діалог, `/cancel` очищує його. Швидка команда підтримує п’ять полів: будинок/комплекс, під’їзд (1, 2, «Не зазначено» або `-`), поверх або `-`, категорія, опис. Наприклад: `/new 4В | 2 | 12 | Сантехніка МЗК | Протікає труба`. Старий формат із чотирьох полів залишається сумісним: під’їзд не зазначений, а для 4Б автоматично 1. Увесь текст після роздільника перед описом є описом, включно з подальшими `|`. Окреме місце не запитується: достатньо будинку та поверху або прив’язки до прибудинкової території. Нові заявки мають видимість «Для мешканців комплексу»; видимість відображається в адмінпанелі. Наявні заявки зберігають поточну видимість. Раніше введені варіанти «комплекс», «Весь комплекс» і «Весь комплекс та прибудинкова територія» залишаються сумісними. Старий формат із трьома полями не створює заявку без явної прив'язки.

Опція «Парадне» доступна у вебпанелі та фільтрі заявок; бот приймає її у швидкій команді й зі старої клавіатури. Вона зберігається як `Floor = 0`; `null` залишається значенням «Без поверху». Наприклад: `/new 4Б | Парадне | інше | Зламано двері парадного`.

Категорії: Електрика МЗК, Сантехніка МЗК, Ліфти, Прибирання МЗК, Інше. Опис - 10–2000 символів. Текст відповіді надсилається без HTML/Markdown. Час подання показується за Києвом.

### Експорт

Кнопка «Експортувати в Excel» у розділах заявок і мешканців завантажує `.xlsx` з усіма сторінками вибраного списку. До назви файлу додається дата за Києвом, наприклад `Заявки-08-11-2026.xlsx`. Для заявок використовуються фільтри, застосовані кнопкою «Знайти»; експорт містить ім’я, прізвище, телефон і квартиру автора з поточного профілю; для зареєстрованих мешканців - поточні фільтр будинку та сортування. Окремо можна експортувати список реєстрацій, що очікують перевірки, з урахуванням вибраного будинку. Файл заявок формує сервер за одним запитом із застосованими фільтрами; файли мешканців також формуються сервером за одним запитом з урахуванням фільтрів і сортування. Файли можуть містити контактні дані; Telegram Chat Id до експорту мешканців не включається. Експорт заявок читає всі сторінки на сервері, а експорт мешканців читає відфільтрований довідник на сервері; дані, які змінюються під час читання, не утворюють атомарного знімка. Експорт обмежений розміром файлу 4 МіБ і часом обробки 25 секунд; якщо експорт завеликий або не встигає завершитись, звузьте фільтри.

## Налаштування Docker і PostgreSQL

Створіть приватний файл середовища з `.env.data.example`. Задайте окремі налаштування для кожного середовища. Вкажіть `OSBB_DATABASE`, `OSBB_CONNECTION_STRING`, відповідні ID Cognito й токен бота. Для наявного тому збережіть чинний пароль PostgreSQL.

```bash
docker compose --env-file .env.data.dev -f compose.data.yml up -d --wait postgres
./scripts/osbb-data migrate
```

`migrate` використовує контейнер `command-listener` і застосовує EF Core міграції до робочої бази `OSBB_DATABASE`. Для нового тому PostgreSQL створює порожню базу з цією назвою. Щоб перенести чинний комплекс на іншу машину, відновіть дамп його робочої бази, а потім застосуйте нові міграції. Для запуску бота та API база має містити рядок комплексу з відповідним зовнішнім ID. Зміна `OSBB_DATABASE` у наявному томі не перейменовує базу.

`OSBB_DATA_ENV_FILE=.env.data.prod` вибирає інший файл для `osbb-data` та `osbb-web-api`. За замовчуванням ці скрипти читають `.env.data.dev`. Для локального перегляду PostgreSQL використовуйте Adminer на `http://127.0.0.1:8081/` із сервером `postgres` та робочою назвою бази. Адресу й порт Adminer задають `OSBB_ADMINER_BIND` і `OSBB_ADMINER_PORT`.

### Резервна копія

```bash
./scripts/osbb-data backup
```

Команда зберігає узгоджений дамп `OSBB_DATABASE` у `backups/` із правами `0600` і перевіряє каталог через `pg_restore --list`. Для іншого призначення задайте `OSBB_BACKUP_DIR`, а для іншої бази — `OSBB_POSTGRES_DB`. Відновлюйте дамп у порожню базу. Архіви містять персональні дані й виключені з Git у типовому каталозі.

### Створення міграцій

Задайте `ConnectionStrings__Postgres` для доступної з хоста бази й виконайте:

```bash
dotnet tool restore --tool-manifest dotnet-tools.json
dotnet ef migrations add Назва --project src/OsbbRequests.Postgres --startup-project src/OsbbRequests.WebApi --output-dir Storage/Migrations
```

## Локальний слухач Telegram

Контейнер `command-listener` запускається за окремим профілем Compose і отримує повідомлення через Telegram `getUpdates`. Він використовує ту саму робочу базу `OSBB_DATABASE` (типово `osbb_dev`) і рядок підключення `OSBB_CONNECTION_STRING`, що й локальна адмінпанель.

У приватному `.env.data.dev` задайте `OSBB_LISTENER_BOT_TOKEN` і `OSBB_LISTENER_BOT_USERNAME` бота без webhook. За потреби задайте окремий `OSBB_LISTENER_SERVICE_BOT_TOKEN` для сервісних сповіщень про зупинку. За замовчуванням слухач використовує комплекс локальної адмінпанелі. `OSBB_LISTENER_COMPLEX_ID` задає інший зовнішній ID комплексу, а `OSBB_LISTENER_POSTGRES_COMPLEX_ID` дає змогу вибрати конкретний рядок у `complexes`, якщо зовнішній ID повторюється.

Після ініціалізації робочої бази застосуйте міграції в її контейнерному оточенні й запустіть слухач.

```bash
docker compose --env-file .env.data.dev -f compose.data.yml build command-listener
docker compose --env-file .env.data.dev -f compose.data.yml run --rm command-listener migrate
docker compose --env-file .env.data.dev -f compose.data.yml up -d command-listener
docker compose --env-file .env.data.dev -f compose.data.yml logs -f command-listener
docker compose --env-file .env.data.dev -f compose.data.yml stop command-listener
```

Для одного токена запускайте один слухач. Якщо Telegram повертає `409` через активний webhook або інший процес опитування, слухач завершується. Нові сповіщення з локальної адмінпанелі й бота записуються в `notifications` зі станом `LOCAL_PENDING`. Їх доставляє сервіс `jobs` із тією самою локальною конфігурацією Telegram.

### Локальна доставка сповіщень

Застосуйте міграції до робочої бази й запустіть `jobs`. Після запуску воркер обробляє також сповіщення, які вже очікують у PostgreSQL.

```bash
docker compose --env-file .env.data.dev -f compose.data.yml build command-listener jobs
docker compose --env-file .env.data.dev -f compose.data.yml run --rm command-listener migrate
docker compose --env-file .env.data.dev -f compose.data.yml up -d command-listener jobs
docker compose --env-file .env.data.dev -f compose.data.yml logs -f jobs
```

Hangfire створює службову схему `hangfire` в цій PostgreSQL і щохвилини запускає доставку. Воркер бере до 25 завдань за запуск, відправляє повідомлення від імені налаштованого бота, враховує підписки адміністраторів і розбиває розсилки на сторінки. Тимчасові помилки повторюються, а відповідь Telegram `429` відкладає доставку на вказаний час. Налаштування читання команд через long polling і доставки через Hangfire використовують той самий бот і комплекс.

## Локальний Web API

Скрипт `./scripts/osbb-web-api` збирає та запускає в Compose адмінпанель на `http://127.0.0.1:8083` і Web API на `http://127.0.0.1:8082`. Він читає `OSBB_COGNITO_USER_POOL_ID` і `OSBB_COGNITO_CLIENT_ID` із файлу середовища. Потрібна підготовлена робоча база `OSBB_DATABASE`. Порти можна налаштувати через `OSBB_FRONTEND_PORT` та `OSBB_WEB_API_PORT`.

```bash
./scripts/osbb-web-api
curl --fail http://127.0.0.1:8082/health
```

Образ адмінпанелі має тег `osbb-requests-frontend:local`. Nginx віддає Angular і під час запуску підставляє Cognito ID і `OSBB_ENVIRONMENT` в `/assets/app-config.json`. Для `dev` адмінпанель показує оранжеву стрічку над заголовком на всіх сторінках. Для `prod` стрічка прихована. Запити `/admin/*` надходять до локального Web API через той самий origin. Для окремої збірки образу виконайте `docker compose --env-file .env.data.dev -f compose.data.yml build frontend`.

Для запитів до локального Web API з JSON-тілом використовуйте `Content-Type: application/json`. Максимальний розмір тіла адміністративного запиту становить 30 003 байти.

Для доступу з іншої машини в локальній мережі задайте `OSBB_FRONTEND_BIND` у `.env.data.dev` як LAN-адресу хоста, наприклад `192.168.0.41`, і повторіть запуск. Відкрийте панель за локальним іменем хоста, наприклад `http://nuc.local:8083/`. HTTP для локального імені `.local` дозволений для запитів до API через той самий origin.

Усі адміністративні маршрути читають і зберігають дані у PostgreSQL. Для нових редагувань історія заявки відображає ті самі поля аудиту, що й хмарний API. Cognito використовується для перевірки токенів і підтвердженого email при першому вході. Вебпанель і Web API отримують Cognito ID із локального файлу середовища; робочі сервіси не потребують AWS credentials. Локальний API читає колонку `administrators."IsSuperAdmin"`.

Початкові дані перенесено з DynamoDB один раз. Compose запускає лише сервіси, потрібні для роботи застосунку та PostgreSQL. Робоча база `osbb_dev` зберігає власні зміни, історію й події `LOCAL_PENDING`. Локальний слухач читає актуальні зміни з `osbb_dev`. Події `LOCAL_PENDING` доставляє окремий контейнер `jobs`. Локальний API показує статистику DynamoDB зі знімка. Для бекапу робочої бази виконайте `./scripts/osbb-data backup`.

## AWS-пакування й розгортання

Потрібні AWS credentials та автентифікація Serverless Framework v4.

```bash
npm run package -- --stage dev --region eu-central-1
npm run deploy -- --stage dev --region eu-central-1
```

`package` генерує CloudFormation у `.serverless/` без оновлення стеку. Шаблон залишає CloudFront і функцію редіректу, чинний Cognito User Pool та його клієнт. Web API, фронтенд, Telegram-слухач, доставка сповіщень і база даних працюють у Docker.

Старий стек уже скорочено. Таблиці DynamoDB і бакет фронтенду збережено за політикою `Retain`. Окремо створені параметри SSM та службовий бакет Serverless також залишилися в AWS. Стара адреса CloudFront перенаправляє на `https://zeleniy-ostriv2.com`, зберігаючи шлях.

## Перевірки

Використовуйте Node.js із `.nvmrc` та .NET SDK із `global.json`. Для інтеграційних тестів задайте `OSBB_POSTGRES_TEST_CONNECTION` на окремий сервер або на службову базу `postgres` із правом створювати тимчасові тестові бази.

```bash
dotnet restore OsbbRequests.sln --locked-mode
npm run build -- --no-restore
npm run test -- --no-build --no-restore
npm run check
npm ci --prefix src/Frontend
npm run check --prefix src/Frontend
npm run test --prefix src/Frontend
npm run build --prefix src/Frontend
```
