# ЖК «Зелений острів 2» — заявки мешканців

Telegram-бот для звернень мешканців і вебпанель ОСББ житлового комплексу «Зелений острів 2». Runtime — .NET 10, Linux ARM64.

## Що працює

У приватному чаті бот підтримує:

| Команда | Результат |
| --- | --- |
| `/start` | Початок або продовження реєстрації; стан доступу |
| `/register` | Реєстрація: власний телефон, ім’я та прізвище |
| `/cancel` | Скасування незавершеної реєстрації або чернетки заявки |
| `/help` | Список команд |
| `/categories` | Категорії заявок |
| `/new` | Покрокове створення приватної заявки: будинок/комплекс → поверх → категорія → місце → опис |
| `/my` | Власні заявки, по 10 на сторінку |
| `/my номер` | Наступна сторінка за курсором із попереднього списку |
| `/request номер` | Деталі власної заявки |

Команди нечутливі до регістру та підтримують `/command@BotUsername`. Створення і перегляд заявок потребують активного доступу до комплексу. Новий мешканець надає телефон кнопкою Telegram, вводить ім’я та прізвище; адміністратор перевіряє ці дані й надає доступ. Telegram ID є внутрішнім ключем і користувачу не показується. Приклад:

```text
/new 4В | 3 | сантехніка | під’їзд 2, біля ліфта | Протікає труба біля ліфта
/new комплекс | - | електрика | двір | Не працює освітлення майданчика
```

Команда `/new` показує кнопки «Будинок 4Б», «Будинок 4В», «Будинок 4Г», «Будинок 4Д» та «Весь комплекс». Для конкретного будинку бот запитує поверх 1–25 або «Без поверху» (наприклад, фасад чи підвал), потім категорію, місце й опис. Для всього комплексу крок поверху пропускається. Після коректного опису заявка створюється; `/new` відновлює незавершений діалог, `/cancel` очищує його. Швидка команда має п'ять полів: будинок/комплекс, поверх або `-`, категорія, місце, опис. Старий формат із трьома полями не створює заявку без явної прив'язки.

Категорії: сантехніка, електрика, прибирання, місця загального користування, інше. Місце — 1–200 символів, опис — 10–2000. Текст відповіді надсилається без HTML/Markdown. Час подання показується за Києвом.

Вебпанель дозволяє перевіряти реєстрації мешканців, фільтрувати й оновлювати заявки, призначати відповідального, пріоритет і планову дату та переглядати історію. Фото, коментарі, перегляд публічних заявок і підписки в боті ще не реалізовані. Зміни статусів доступні мешканцю через `/my` і `/request`; автоматичні сповіщення про адміністративні зміни ще не реалізовані. Цільові вимоги: [docs/requirements.md](docs/requirements.md).

## Структура та обробка

```text
POST /telegram/webhook
  → перевірка secret із SSM
  → FIFO-черга команд
  → CommandFunction
  → DynamoDB: заявка + історія + збережена відповідь
  → Telegram sendMessage
```

`OsbbRequests.Bot.Function` перевіряє secret до розбору payload, приймає лише повідомлення від людини у приватному чаті та підтверджує update після запису в SQS. Непідтримувані/некоректні update підтверджуються без обробки; недоступність SSM або черги дає `503`, щоб Telegram повторив доставку.

`OsbbRequests.Bot.CommandFunction` обробляє команди із SQS; транзакція DynamoDB захищає від повторного створення заявки. Збережена відповідь повторно використовується після збою доставки. Після успішної доставки встановлюється ознака `delivered`. FIFO забезпечує послідовну обробку повідомлень одного чату.

Спільні типи — у `OsbbRequests.Shared`; API вебпанелі — у `OsbbRequests.AdminApi`. Деталі таблиці та гарантій: [docs/architecture.md](docs/architecture.md).

## Прив’язка заявки

Нова заявка обов’язково має `Scope = Building` із `BuildingNumber` як рядок `4Б`, `4В`, `4Г` або `4Д` або `Scope = Complex` без номера будинку. `Floor` — необов’язковий номер 1–25 лише для конкретного будинку. Адміністратор бачить і може уточнити ці поля; список фільтрується за ними. Старі заявки без цих полів залишаються доступними як «Будинок не уточнено»; під час наступного редагування адміністратор має явно вибрати прив’язку. Автоматичного вгадування чи перепризначення старих заявок немає.

Історичні `BUILDING_ID`, `BuildingId`, partition `BUILDING#...` та `requestBuildingId` збережені для сумісності даних і тепер означають ідентифікатор усього комплексу. Не змінюйте їх на адміністративні номери будинків: це відокремить чинні membership і дані. Фізичний будинок визначається тільки `BuildingNumber`.

## Локальний запуск перевірок

Потрібні .NET SDK 10.0.3xx, Node.js 24, npm, Bash і `zip`.

```bash
npm ci
npm ci --prefix src/Frontend
npm run check --prefix src/Frontend
npm run build --prefix src/Frontend
dotnet restore OsbbRequests.sln --locked-mode
npm run build
npm run test -- --no-build --no-restore
python3 -m unittest discover -s tests/admin -v
npm run check
npm run package:dotnet
```

Для адміністративного скрипта та його тестів потрібен Python 3 (лише стандартна бібліотека). Тести не звертаються до AWS або Telegram. Остання команда створює ZIP для Bot та AdminApi у `artifacts/` без AWS credentials; глобальний Amazon.Lambda.Tools не потрібний. Після оновлення NuGet-залежностей виконайте `dotnet restore OsbbRequests.sln --force-evaluate` і додайте `packages.lock.json` до Git.

GitHub Actions запускає restore, build, тести, перевірку форматування та ZIP-пакування. Деплой у CI не налаштований.

## Вебпанель адміністраторів

Angular-застосунок у `src/Frontend` побудований за прикладом `~/projects/PingLight/src/Frontend`: Cognito для входу, підтвердження email, відновлення пароля, sessionStorage для сесії та сторінки робочого простору. Оформлення використовує Bootstrap 5 (форми, сітка, кнопки, картки, повідомлення й діалоги), а випадаючі списки — `@ng-select/ng-select` 21 із пошуком у категоріях і відповідальних. Зелено-оливкову палітру Bootstrap (кнопки, посилання, навігацію та фокус полів) перевизначено в `src/Frontend/src/_theme.scss`; кольори ng-select узгоджено з нею у `styles.scss`. Bootstrap і тема ng-select включені до локальної збірки; CDN і Bootstrap JavaScript не потрібні. Це SPA; приватні дані завантажуються лише з авторизованого API. Статичні файли зберігаються у приватному S3 і доступні через CloudFront HTTPS.

Якість фронтенду перевіряють ESLint (рекомендовані правила TypeScript із перевіркою типів, Angular і доступності шаблонів), Stylelint (`standard-scss`) та Prettier. Команда `npm run check --prefix src/Frontend` запускає всі перевірки; вона також виконується в CI. Для автоматичних виправлень: `npm run lint:fix --prefix src/Frontend`, потім `npm run format --prefix src/Frontend`. Збірки, кеші та залежності виключено з перевірок.

Розділи: **Заявки**, **Мешканці**, **Адміністратори** (тільки для супер адміністратора). У заявках є пошук за входженням у місце/опис, фільтри будинку/комплексу, поверху, статусу, категорії й UTC-дат подання, пагінація, відповідальний, пріоритет, планова дата, видимість і пояснення. Пояснення є обов'язковим для виконаних і відхилених заявок. В історії показуються до 100 останніх записів. Фото, коментарі й зв'язування дублікатів ще не додані.

Список адміністраторів зберігається **окремо** від мешканців у `osbb-requests-<stage>-administrators`:

| Поле | Призначення |
| --- | --- |
| `UserId` | Ключ, Cognito `sub`; не Telegram ID |
| `Email`, `DisplayName` | Дані підтвердженого облікового запису |
| `IsActive` | Дозвіл працювати із заявками та реєстраціями |
| `IsSuperAdmin` | Дозвіл надавати й відкликати доступ інших адміністраторів |
| `Directory`, `Version` | Індекс списку та захист від одночасних змін |

Під час першого входу створюється неактивний запис. `IsSuperAdmin` відсутній і читається як `false`; застосунок ніколи не записує це поле. Для першого супер адміністратора:

1. Зареєструйте обліковий запис у вебпанелі, підтвердьте email та увійдіть. Буде показано очікування доступу.
2. В **AWS Console → DynamoDB → osbb-requests-dev-administrators → Explore table items** знайдіть запис за своїм `Email` (або через `DirectoryIndex`, `Directory = ADMINS`).
3. Встановіть `IsActive` як **Boolean `true`** та додайте `IsSuperAdmin` як **Boolean `true`**. Зміна `IsSuperAdmin` виконується тільки безпосередньо в AWS Console.
4. Натисніть «Перевірити доступ» у панелі. З'явиться розділ «Адміністратори».

Наступний адміністратор так само створює й підтверджує акаунт і входить у панель; супер адміністратор знаходить його email і натискає «Надати доступ». Це надає право обробляти заявки та реєстрації, але не право керувати іншими адміністраторами. `IsSuperAdmin` не редагується в UI або API навіть супер адміністратором. IAM окремо забороняє Lambda запис цього атрибута, PutItem/DeleteItem у таблиці адміністраторів та дозволяє UpdateItem лише визначених звичайних полів.

```bash
# Локальна розробка (конфігурацію власного stage візьміть із outputs stack).
npm start --prefix src/Frontend

# Після успішного деплою інфраструктури: збірка й завантаження панелі.
python3 scripts/deploy-frontend.py --stage dev --region eu-central-1
```

Скрипт генерує публічний `app-config.json` із URL API та ID Cognito, завантажує файли у S3 й оновлює кеш CloudFront. Він не читає Telegram-секрети. Порожня конфігурація у source є шаблоном; локально замініть її власними публічними ID без додавання чужої конфігурації до Git.

Для вже схвалених мешканців після першого деплою цієї функції заповніть каталог (скрипт не змінює профілі, membership чи ролі адміністраторів і не виводить персональних даних):

```bash
python3 scripts/backfill-residents.py --stage dev --region eu-central-1
python3 scripts/backfill-residents.py --stage dev --region eu-central-1 --apply
```

Нові схвалення через панель або `manage-residents.py` додають мешканця до каталогу тією самою транзакцією, що й рішення. Повторний запуск міграції пропускає вже наявні записи. Для власного `BUILDING_ID` передайте скрипту `--building-id`.

Для заявок, створених до появи індексу адмінпанелі, після деплою виконайте міграцію (спочатку dry run):

```bash
python3 scripts/backfill-request-index.py --stage dev
python3 scripts/backfill-request-index.py --stage dev --apply
```

Тільки ця одноразова операторська міграція використовує Scan. API та бот працюють через GetItem/Query; Lambda не отримують Scan. Міграція не видаляє заявки та перевіряє незмінність payload перед записом індексних атрибутів.

## Конфігурація та секрети

Одне середовище — один бот та один житловий комплекс із чотирьох будинків. Перед розгортанням задайте:

```bash
export TELEGRAM_BOT_USERNAME=YourOsbbBot  # без @
export BUILDING_ID=osbb-example # історична назва змінної: ідентифікатор комплексу, не номер будинку
# Необов'язково: приватний чат або група для операційних помилок.
# У приватному чаті адміністратор спочатку має запустити бота.
export ADMIN_TELEGRAM_CHAT_ID=123456789
```

Для `dev` у `serverless.yml` задано username `zeleniy_ostriv2_bot`; для інших stage за замовчуванням — `OsbbRequestsBot`. `TELEGRAM_BOT_USERNAME` перевизначає значення відповідного stage. Building ID за замовчуванням — `osbb-requests-<stage>`. Команди з адресацією `@username` потребують правильного username. Для імен без `@` значення username не впливає на маршрутизацію.

У AWS Systems Manager Parameter Store створіть два `SecureString` у тому самому регіоні:

- `/osbb-requests/dev/telegram-bot-token` — токен від BotFather;
- `/osbb-requests/dev/telegram-webhook-secret` — випадковий секрет із символів `A–Z`, `a–z`, `0–9`, `_`, `-`, довжиною 1–256.

Для іншого stage замініть `dev`. Конфігурація розрахована на стандартний ключ `aws/ssm`; для власного KMS-ключа додайте точні `kms:Decrypt` permissions у відповідну роль та key policy. Lambda отримують тільки імена параметрів і читають секрети під час роботи з кешем до п'яти хвилин. Секрети не підставляються в Serverless-артефакти. Значення вводьте через захищений інтерфейс AWS або свій менеджер секретів; не додавайте їх у Git, журнали чи shell history.

## AWS-пакування й розгортання

Потрібні AWS credentials та автентифікація Serverless Framework v4.

```bash
npm run package -- --stage dev --region eu-central-1
npm run deploy -- --stage dev --region eu-central-1
```

`package` генерує CloudFormation у `.serverless/` без розгортання; потребує AWS credentials. `deploy` створює три Lambda, HTTP API, FIFO-чергу та DLQ, дві таблиці DynamoDB із point-in-time recovery, Cognito, приватний S3/CloudFront для панелі, окремі IAM-ролі та CloudWatch logs. Регіон за замовчуванням — `eu-central-1`, stage — `dev`.

Після розгортання зареєструйте в Telegram `setWebhook` URL `<HTTP API URL>/telegram/webhook`, вкажіть той самий `secret_token` і `allowed_updates: ["message"]`. Токен бота та webhook secret передавайте з менеджера секретів без журналювання. Перевірка реального обміну з Telegram виконується після налаштування секретів і деплою.

## Реєстрація та надання доступу

1. Мешканець надсилає `/start` або `/register`.
2. Бот пояснює, що телефон, ім’я та прізвище побачить адміністратор для надання доступу, і показує кнопку «Поділитися номером телефону».
3. Приймається лише власний Telegram-контакт: `contact.user_id` має збігатися з відправником. Введений текстом номер або чужа контактна картка не приймаються. Номер нормалізується до міжнародного формату з `+`.
4. Мешканець окремими повідомленнями вводить ім’я та прізвище. Після цього реєстрація має стан `Pending`, доступ залишається закритим.
5. Адміністратор переглядає ПІБ і телефон, перевіряє мешканця та схвалює або відхиляє запит. Мешканець перевіряє рішення через `/start`.

`/start` продовжує незавершений діалог. `/cancel` скасовує чернетку та очищує телефон й імена у поточному профілі; копії в черзі/receipt видаляються за своїми строками зберігання. Відхилений запит можна подати знову через `/register`. Наявний запит на перевірці не перезаписується, а повторні update не просувають діалог удруге. Телефон є підтвердженим контактом акаунта Telegram; належність до комплексу й правильність імені перевіряє адміністратор.

У розділі «Мешканці» є два списки: «Очікують перевірки» для нових запитів і «Зареєстровані мешканці» для схвалених реєстрацій. У другому показано ПІБ, телефон і дату підтвердження; кнопка «Завантажити ще» дозволяє переглянути всі сторінки по 50 записів. Доступ до обох списків мають лише активні адміністратори. Список зареєстрованих відображає підтверджені реєстрації, а не окрему перевірку поточного membership. Telegram ID не відображається. Реєстрації перевіряються у розділі «Мешканці» вебпанелі. Як операторський резерв залишається скрипт зі своїми AWS credentials:

```bash
# Показує приватні ім’я, прізвище, телефон і reference запитів на доступ.
python3 scripts/manage-residents.py --stage dev list

# reference береться зі списку; мешканцю не потрібно знати або передавати Telegram ID.
python3 scripts/manage-residents.py --stage dev approve <reference>
python3 scripts/manage-residents.py --stage dev reject <reference> --reason 'Уточніть прізвище'
```

Якщо `BUILDING_ID` перевизначено, перед підкомандою додайте `--building-id <building>`. За замовчуванням використовується `osbb-requests-<stage>`. Список містить персональні дані — він призначений тільки для адміністратора, не для публікації чи CI-журналів.

Скрипт атомарно змінює стан реєстрації, membership, прибирає запит зі списку очікування та зберігає аудит із AWS-ідентичністю оператора. Застаріле рішення не перезапише змінений профіль. Відхилення потребує пояснення. Автоматичне Telegram-сповіщення про рішення поки не реалізоване: стан і причина відхилення доступні мешканцю через `/start`.

Бот не має команди, яка надає доступ самому користувачу. Адміністративний скрипт потребує AWS-дозволів на `sts:GetCallerIdentity` та відповідні `dynamodb:GetItem`, `Query`, `PutItem`, `UpdateItem`, `DeleteItem` для таблиці свого stage. Ці адміністративні дозволи не додаються Lambda або мешканцям.

## Відмови та експлуатація

Повторна обробка одного update не створює другу заявку. При неоднозначному мережевому результаті `sendMessage` або збої між доставкою та записом `delivered` повторне Telegram-повідомлення можливе: Telegram не має idempotency key для цього виклику.

Черга утримує команди до чотирьох днів; після п'яти невдалих обробок повідомлення переходить у DLQ зі зберіганням до 14 днів. Звичайний retry — після 180 секунд; для Telegram `429` враховується `retry_after` через visibility timeout (до ліміту SQS 12 годин). Після усунення причини помилки оператор має виконати redrive DLQ до основної черги. Не запускайте довільні нові команди зі старих payload: відновлюйте оригінальні повідомлення в межах 30-денного строку дедуплікації.

Записи відповідей та дедуплікації мають TTL 30 днів і можуть містити приватний текст заявки. TTL видаляється DynamoDB асинхронно. Заявки, історія, членство й реєстраційні профілі TTL не мають. Реєстраційні профілі та приватний список адміністратора містять ПІБ і телефон; вони не додаються до загальнодоступних заявок. Політику довгострокового зберігання цих даних потрібно визначити окремо. Черга й DLQ також містять текст команди — доступ до них лише для операторів і відповідних Lambda.

Помилки журналюються за типом та SQS Message ID без тексту команд, контактів і секретів. Якщо заданий `ADMIN_TELEGRAM_CHAT_ID`, воркер намагається сповістити адміністратора; збій цього повідомлення не перешкоджає retry. Стежте за DLQ та CloudWatch; окремі зовнішні alarm destinations ще не налаштовані.

Видалення середовища:

```bash
npm run remove -- --stage dev --region eu-central-1
```

DynamoDB має `DeletionPolicy: Retain`: дані й витрати на таблицю зберігаються після видалення stack. Повторне створення stack з тим самим іменем таблиці потребуватиме імпорту збереженої таблиці або окремого рішення оператора. Секрети SSM також не видаляються автоматично.
