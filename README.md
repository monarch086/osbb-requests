# ЖК «Зелений острів 2» - заявки мешканців

Telegram-бот для звернень мешканців і вебпанель ОСББ житлового комплексу «Зелений острів 2». Runtime - .NET 10, Linux ARM64.

## Що працює

У приватному чаті бот підтримує:

| Команда | Результат |
| --- | --- |
| `/start` | Початок або продовження реєстрації; стан доступу |
| `/cancel` | Скасування поточного діалогу (реєстрація, створення, перегляд або видалення) |
| `/help` | Список команд |
| `/contacts` | Телефони диспетчерів сантехніки, електрики та ліфтів |
| `/new` | Покрокове створення заявки для всіх мешканців: будинок/комплекс → під’їзд → поверх → категорія → опис |
| `/my` | Власні заявки, по 10 на сторінку |
| `/my номер` | Наступна сторінка за курсором із попереднього списку |
| `/request номер` | Деталі власної заявки |
| `/complex` | Нові та в роботі заявки, відкриті для мешканців комплексу, з датою створення |
| `/complex курсор` | Наступна сторінка за командою зі списку |
| `/delete номер` | Видалення власної заявки лише зі статусом «Нова», після підтвердження «Так» |

Команди нечутливі до регістру та підтримують `/command@BotUsername`. Створення, перегляд і видалення заявок потребують активного доступу до комплексу. Новий мешканець надає телефон кнопкою Telegram, вводить ім’я та прізвище; адміністратор перевіряє ці дані й надає доступ. Telegram ID є внутрішнім ключем і користувачу не показується. Приклад:

```text
/new 4В | 3 | Сантехніка МЗК | Протікає труба біля ліфта
/new комплекс | - | електрика | Не працює освітлення майданчика
```

Команда `/new` показує кнопки «Будинок 4Б», «Будинок 4В», «Будинок 4Г», «Будинок 4Д» та «Прибудинкова територія». Для будинків 4В, 4Г та 4Д бот спочатку запитує під’їзд: «1», «2» або «Не зазначено». Для 4Б під’їзд автоматично дорівнює 1, запит пропускається. Для конкретного будинку бот далі пропонує кнопки поверхів 1–25, потім запитує категорію й опис. Старі кнопки «Парадне» та «Без поверху», які могли залишитися у відкритих діалогах, підтримуються для сумісності. Для прибудинкової території крок поверху пропускається. Після коректного опису заявка створюється; `/new` відновлює незавершений діалог, `/cancel` очищує його. Швидка команда підтримує п’ять полів: будинок/комплекс, під’їзд (1, 2, «Не зазначено» або `-`), поверх або `-`, категорія, опис. Наприклад: `/new 4В | 2 | 12 | Сантехніка МЗК | Протікає труба`. Старий формат із чотирьох полів залишається сумісним: під’їзд не зазначений, а для 4Б автоматично 1. Увесь текст після роздільника перед описом є описом, включно з подальшими `|`. Окреме місце не запитується: достатньо будинку та поверху або прив’язки до прибудинкової території. Нові заявки мають видимість «Для мешканців комплексу»; адміністратор може змінити її. Наявні заявки зберігають поточну видимість. Раніше введені варіанти «комплекс», «Весь комплекс» і «Весь комплекс та прибудинкова територія» залишаються сумісними. Старий формат із трьома полями не створює заявку без явної прив'язки.

Опція «Парадне» доступна у вебпанелі та фільтрі заявок; бот приймає її у швидкій команді й зі старої клавіатури. Вона зберігається як `Floor = 0`; `null` залишається значенням «Без поверху». Наприклад: `/new 4Б | Парадне | інше | Зламано двері парадного`. Міграція наявних заявок не потрібна; перед frontend-деплоєм потрібно оновити backend для підтримки нового значення.

Категорії: Електрика МЗК, Сантехніка МЗК, Ліфти, Прибирання МЗК, Інше. Опис - 10–2000 символів. Текст відповіді надсилається без HTML/Markdown. Час подання показується за Києвом.

Після схвалення реєстрації мешканець отримує в Telegram підтвердження доступу та команди для роботи із заявками, зазвичай протягом хвилини. Це працює як у вебпанелі, так і через операторський скрипт `manage-residents.py`; відхилення автоматичного повідомлення не створює.

Вебпанель дозволяє перевіряти реєстрації мешканців, фільтрувати й оновлювати заявки, призначати відповідального, пріоритет і планову дату та переглядати історію. Перегляд відкритих для мешканців комплексу нових заявок і заявок у роботі доступний через `/complex`. Фото, коментарі й підписки в боті ще не реалізовані. Зміни статусу та додавання, редагування або очищення поля «Пояснення для мешканця» надсилаються автору заявки в Telegram окремим воркером, зазвичай протягом хвилини. Деталі також доступні через `/my` і `/request`. Цільові вимоги: [docs/requirements.md](docs/requirements.md).

`/complex` охоплює всі будинки й спільну територію. Показуються лише `Public` («Для мешканців комплексу») зі статусами «Нова» або «В роботі»: номер, статус, дата за Києвом, будинок/поверх або комплекс, категорія, місце та повний текст заявки. Контакти, автор, приватне листування та адміністративні поля не показуються. Список добирає до 5 доступних заявок за кілька запитів до бази; через ліміт Telegram на довжину повідомлення їх може бути менше. Для обмеження роботи бот виконує до 25 запитів на сторінку: якщо прихованих заявок дуже багато, сторінка може містити менше записів або бути порожньою, але матиме продовження. Код продовження `/complex` має 10 символів, наприклад `/complex abc2345678`. Це випадкове посилання на повний курсор у поточній таблиці DynamoDB, прив’язане до мешканця та комплексу; регістр літер не має значення. Курсор записується атомарно з відповіддю з TTL `expiresAt` на 30 днів від створення; прострочені коди відхиляються відразу, навіть до асинхронного видалення DynamoDB, і бот пропонує почати з `/complex`; один перехід додає один GetItem, сторінка з продовженням - один невеликий запис у транзакції. Нових таблиць чи міграції немає. Старі 26-символьні та довгі коди також приймаються. `/my` продовжує використовувати короткий числовий номер заявки.

`/delete` запитує номер наступним повідомленням; `/delete 123` одразу запитує підтвердження. Лише відповідь «Так» видаляє власну нову заявку. `/cancel` або інша команда припиняє очікування. Якщо адміністратор змінив заявку після запиту підтвердження, видалення блокується; потрібно почати його знову. Заявка зникає зі списків і вебпанелі, а історія та подія видалення зберігаються для аудиту.

**Перехід на одну таблицю мешканців.** Після розгортання змін транзакції бота, API та `manage-residents.py` записують дані мешканців тільки в `residents`; сповіщення й службові записи залишаються в `command-data` у тій самій транзакції. До завершення такого розгортання не запускайте нову версію `manage-residents.py` для погодження або відхилення. Старі записи мешканців поки не видаляйте.

Перед розгортанням виконайте обидві міграційні звірки нижче в dry-run, переконайтеся, що всі профілі та пов’язані записи перенесені без конфліктів і всі незавершені розсилки зі старими курсорами завершилися. Сканування не є атомарним знімком; повторіть звірку за відсутності змін і перевірте індекси. Після перемикання старі записи стають неактуальними: не використовуйте `migrate-residents-table.py` та `migrate-resident-records.py` з `--apply` у перемкненому середовищі і не покладайтеся на результати їхньої звірки. Відкат на стару версію без зворотної синхронізації втратить нові зміни. `backfill-residents.py` та `revoke-deleted-residents.py` є історичними; їхній CLI блокує `--apply`. Дані ще не очищено.

## Структура та обробка

```text
POST /telegram/webhook
  → перевірка secret із SSM
  → FIFO-черга команд
  → CommandFunction
  → DynamoDB: заявка + історія + збережена відповідь
  → Telegram sendMessage
```

`OsbbRequests.Bot.Function` перевіряє secret до розбору payload, приймає лише повідомлення від людини у приватному чаті та підтверджує update після запису в SQS. Непідтримувані/некоректні update підтверджуються без обробки; недоступність SSM або черги дає `503`, щоб Telegram повторив доставку.

`OsbbRequests.Bot.CommandFunction` обробляє команди із SQS; транзакція DynamoDB захищає від повторного створення заявки. Збережена відповідь повторно використовується після збою доставки. Після успішної доставки встановлюється ознака `delivered`. FIFO забезпечує послідовну обробку повідомлень одного чату.

Спільні типи - у `OsbbRequests.Shared`; API вебпанелі - у `OsbbRequests.AdminApi`. Деталі таблиці та гарантій: [docs/architecture.md](docs/architecture.md).

У списках вебпанелі використовується серверна пагінація: до 25 записів на сторінці, стрілки переходу та кнопки номерів сторінок у зеленій темі. Поточна сторінка виділена; довгі ряди номерів скорочуються трикрапкою. Номери відповідають відомим сторінкам (отриманим або доступним за cursor наступної); останній показаний номер не є загальною кількістю сторінок. Можна одразу повернутися до будь-якої відомої сторінки. Нові сторінки замінюють поточні рядки. Показники заявок враховують усі записи за застосованими фільтрами. Застосування фільтрів, перемикання розділу або типу списку мешканців відкриває першу сторінку; «Оновити» перечитує поточну. Перехід зберігає застосовані фільтри, навіть якщо поля форми вже змінено, але пошук ще не запущено. Порожня відфільтрована сторінка може мати наступну. Якщо завантаження не вдалося, поточні рядки й номер сторінки зберігаються, перехід можна повторити.

## Сповіщення автору заявки

Коли активний адміністратор змінює статус або поле «Пояснення для мешканця», API атомарно зберігає заявку, аудит і завдання доставки. Одночасна зміна статусу й пояснення створює одне повідомлення: номер заявки, будинок/поверх або комплекс, час зміни за Києвом, статус і пояснення. Незмінне пояснення (зокрема відмінності лише в пробілах по краях), пріоритет, відповідальний, планова дата чи видимість без зміни статусу/пояснення не створюють повідомлення. Сповіщення приватне та адресується лише автору; публічність заявки не впливає на одержувача.

`notificationSender` перевіряє outbox раз на хвилину, до 25 завдань за виклик. Невідправлені завдання зберігаються без TTL; збій Telegram не скасовує збережену зміну. Тимчасові помилки повторюються з паузою від хвилини до години, `429` відкладає наступну спробу за `retry_after` і призупиняє весь воркер доставки. HTTP 400/403 фіксуються як `Undeliverable` (наприклад, бот заблокований), інші повідомлення продовжують оброблятися. Результати доставки без тексту зберігаються 30 днів. Доставка має семантику at-least-once: збій між відправленням і записом результату може спричинити повтор; кожне повідомлення містить час, а для оновлень заявки - також її номер.

Воркер сповіщень читає токен бота мешканців із наявного SSM-параметра; Admin API не має доступу до цього токена й надсилає мешканцям повідомлення тільки через outbox. Для операційних помилок усі чотири Lambda використовують окремого сервісного бота, описаного нижче. Перевірте CloudWatch `/aws/lambda/osbb-requests-<stage>-notificationSender`, увімкнений Scheduler `osbb-requests-<stage>-notifications` і SQS `osbb-requests-<stage>-notification-failures` для невдалих запусків Scheduler/Lambda. Адміністративні зміни не відтворюються заднім числом.

Налаштування запусків і повторів відповідають документації [Lambda destinations](https://www.serverless.com/framework/docs/providers/aws/guide/functions#asynchronous-invocation) та [Scheduler retry/DLQ](https://docs.aws.amazon.com/scheduler/latest/UserGuide/configuring-schedule-dlq.html).

## Меню команд Telegram

У приватному чаті меню команд містить `/start`, `/help` та `/cancel`. Основні дії доступні на головній клавіатурі; решта slash-команд залишаються доступними для ручного введення. Номер можна передати одразу (`/request 123`) або надіслати наступним повідомленням після `/request` або `/delete`: бот попросить «Введіть номер заявки». Некоректний номер можна виправити наступним повідомленням; `/cancel` або інша команда припиняє очікування. `/my` без номера показує першу сторінку власних заявок із повним описом. У `/my` та `/complex` текст кожної заявки відокремлений рядками `~~~~~` зверху й знизу. Обидва списки показують дату подання за Києвом і лише зазначені частини місця: будинок, під’їзд та поверх; порожні значення й пояснювальні заглушки пропускаються без порожнього рядка. Для Scope=Complex показується «Прибудинкова територія», для поверху 0 - «Парадне». Довгі описи автоматично зменшують кількість заявок на сторінці, щоб повідомлення разом із розділювачами та командою продовження не перевищувало 4096 символів. Наступна сторінка продовжує після останньої показаної заявки без пропусків. Для схвалених мешканців головна клавіатура не містить початку реєстрації та додатково містить «Змінити профіль» і «Видалити профіль». Довідка містить актуальні команди. Кнопка «Скасувати» доступна під час діалогу; команду `/cancel` також можна ввести вручну. Меню не змінює перевірку доступу до заявок.

Після першого деплою або зміни переліку команд налаштуйте меню окремим скриптом із кореня репозиторію:

```bash
# Попередній перегляд без читання токена й без змін у Telegram.
python3 scripts/configure-telegram-menu.py --stage dev --region eu-central-1 --bot-username zeleniy_ostriv2_bot --include-residents
# Застосування та перевірка налаштувань.
python3 scripts/configure-telegram-menu.py --stage dev --region eu-central-1 --bot-username zeleniy_ostriv2_bot --include-residents --apply
```

Токен читається з `/osbb-requests/<stage>/telegram-bot-token` у SSM лише в пам'ять; оператору потрібні відповідні AWS credentials і дозвіл читання SecureString. Перед змінами скрипт звіряє `getMe` з `--bot-username`, налаштовує `setMyCommands` для `all_private_chats` (fallback та `uk`) і кнопку `setChatMenuButton`, потім перевіряє результат через read API. Команди не запускаються, повідомлення мешканцям не надсилаються. Для іншого stage вкажіть його бот. Перелік команд спільний для воркера й скрипта: `src/OsbbRequests.Bot/Telegram/command-menu.json`. Після backend-деплою воркер команд синхронізує меню чату за поточним membership, а воркер сповіщень встановлює меню мешканця перед підтвердженням схвалення та іншими приватними сповіщеннями. Успішні оновлення кешуються в межах теплого запуску Lambda. Для оновлення меню всіх уже схвалених мешканців без очікування їхньої наступної взаємодії запустіть скрипт із `--include-residents --apply` (спочатку dry run без `--apply`). Він читає каталог через GSI `ResidentRecordsByGroup` нової таблиці мешканців і узгоджено перечитує кожен запис (індекс оновлюється із затримкою, тому нещодавні зміни можуть бути пропущені до повторного запуску), змінює chat scope для fallback та `uk` і перевіряє результат. Якщо BUILDING_ID налаштовано вручну, передайте `--complex-id`. При 429 або іншій помилці скрипт завершується; пізніше його можна безпечно повторити. Довідка API: [меню команд](https://core.telegram.org/bots/api#setmycommands), [кнопка меню](https://core.telegram.org/bots/api#setchatmenubutton).

## Прив’язка заявки

Нова заявка обов’язково має `Scope = Building` із `BuildingNumber` як рядок `4Б`, `4В`, `4Г` або `4Д` або `Scope = Complex` без номера будинку. `Floor` - номер 1–25 або 0 («Парадне») лише для конкретного будинку; null означає «Без поверху». `Entrance` - 1, 2 або null («Не зазначено»), лише для будинку; для 4Б допустимі 1 або null для історичних заявок. У нових заявках бота для 4Б завжди 1. Наявні заявки без поля `Entrance`, включно з 4Б, залишаються «Не зазначено»: міграція й автоматична зміна даних не виконуються. Поле видно в списках бота та панелі, воно редагується адміністратором разом із заявкою. Адміністратор бачить і може уточнити ці поля; список фільтрується за ними. Старі заявки без цих полів залишаються доступними як «Будинок не уточнено»; під час наступного редагування адміністратор має явно вибрати прив’язку. Автоматичного вгадування чи перепризначення старих заявок немає.

Історичні `BUILDING_ID`, `BuildingId`, partition `BUILDING#...` та `requestBuildingId` збережені для сумісності даних і тепер означають ідентифікатор усього комплексу. Не змінюйте їх на адміністративні номери будинків: це відокремить чинні membership і дані. Фізичний будинок визначається тільки `BuildingNumber`.

## Вебпанель адміністраторів

Angular-застосунок у `src/Frontend` побудований за прикладом `~/projects/PingLight/src/Frontend`: Cognito для входу, підтвердження email, відновлення пароля, localStorage для сесії (refresh-токен до 7 днів, access- та ID-токени по 15 хвилин) та сторінки робочого простору. Оформлення використовує Bootstrap 5 (форми, сітка, кнопки, картки, повідомлення й діалоги), а випадаючі списки - `@ng-select/ng-select` 21 із пошуком у категоріях і відповідальних. Зелено-оливкову палітру Bootstrap (кнопки, посилання, навігацію та фокус полів) перевизначено в `src/Frontend/src/_theme.scss`; кольори ng-select узгоджено з нею у `styles.scss`. Bootstrap і тема ng-select включені до локальної збірки; CDN і Bootstrap JavaScript не потрібні. Це SPA; приватні дані завантажуються лише з авторизованого API. Статичні файли зберігаються у приватному S3 і доступні через CloudFront HTTPS.

Розділи панелі мають окремі адреси: `/requests` (заявки), `/residents` (мешканці), `/messages` (повідомлення, за наявності доступу), `/administrators` (адміністратори, лише для супер адміністратора). Оновлення сторінки та кнопки браузера «Назад / Вперед» зберігають розділ. Пряме посилання зберігається також під час входу. Під час перемикання розділів навігація залишається видимою, а завантаження відображається в області вмісту. Фільтри й номер сторінки при повторному відкритті розділу скидаються. CloudFront Function передає ці шляхи до `index.html`; запити статичних ресурсів не переписуються. Для першого розгортання маршрутизації потрібно оновити інфраструктуру перед деплоєм фронтенду.

Якість фронтенду перевіряють ESLint (рекомендовані правила TypeScript із перевіркою типів, Angular і доступності шаблонів), Stylelint (`standard-scss`) та Prettier. Додаткові ESLint-правила забезпечують type-only imports, автоматичне сортування імпортів та реекспортів, readonly для приватних незмінних полів і Angular outputs, перевірку повноти switch та умов, порядок членів класів і фігурні дужки для всіх керуючих конструкцій. Stylelint обмежує ID-селектори та вкладеність SCSS трьома рівнями. Статуси й пріоритети заявок мають union-типи, а члени компонентів, призначені лише для їхніх шаблонів, позначені protected. Команда `npm run check --prefix src/Frontend` запускає всі перевірки; вона також виконується в CI. Для автоматичних виправлень: `npm run lint:fix --prefix src/Frontend`, потім `npm run format --prefix src/Frontend`. Збірки, кеші та залежності виключено з перевірок.

Розділи: **Заявки**, **Мешканці**, **Адміністратори** (тільки для супер адміністратора). У заявках є пошук за входженням у місце/опис, фільтри будинку/комплексу, поверху, статусу, категорії й UTC-дат подання, пагінація, відповідальний, пріоритет, планова дата, видимість і пояснення. У фільтрі «Статус» можна обрати кілька значень; початково вибрано «Нова» та «В роботі». Заявка відповідає будь-якому з вибраних статусів. Очищення вибору означає «Усі статуси», включно з виконаними й відхиленими; зміни застосовуються кнопкою «Знайти». Пояснення є обов'язковим для виконаних і відхилених заявок. У діалозі заявки під описом показуються ім’я та прізвище автора, а також його телефон, будинок проживання й квартира, якщо зазначені. Дані беруться з поточного приватного реєстраційного профілю й не копіюються до загальнодоступної заявки; адреса автора може відрізнятися від місця проблеми. В історії показуються до 100 останніх записів; подія «Створено заявку» містить ім’я та прізвище автора з його поточного реєстраційного профілю. Це працює також для старих заявок без міграції. Якщо дані відсутні, показується «Мешканець»; телефон і Telegram ID до історії не додаються. Фото, коментарі й зв'язування дублікатів ще не додані.

Список адміністраторів зберігається **окремо** від мешканців у `osbb-requests-<stage>-administrators`:

| Поле | Призначення |
| --- | --- |
| `UserId` | Ключ, Cognito `sub`; не Telegram ID |
| `Email`, `DisplayName` | Дані підтвердженого облікового запису |
| `IsActive` | Дозвіл працювати із заявками та реєстраціями |
| `IsSuperAdmin` | Дозвіл надавати й відкликати доступ інших адміністраторів |
| `Directory`, `Version` | Індекс списку та захист від одночасних змін |
| `TelegramChatId` | Числовий Telegram Chat ID як рядок; порожній - сповіщення вимкнені |
| `NotifyNewResidents`, `NotifyNewRequests`, `NotifyNewKeyOrders`, `NotifyNewAdministrators` | Незалежні підписки на реєстрації, заявки по комплексу, замовлення ключів і акаунти адміністраторів |

У картці адміністратора секція «Сповіщення» відкриває налаштування Telegram Chat Id та трьох незалежних підписок, а секція «Доступи» — вибір дозволених сторінок. Усі підписки початково вимкнені. Для ввімкнення потрібен числовий ненульовий Chat ID; підтримуються також від’ємні ID груп. Бот повинен мати доступ до чату; для особистого чату одержувач спочатку надсилає `/start`. Власні налаштування може змінити активний адміністратор через API; налаштування інших - лише активний супер адміністратор. Сторінка адміністраторів залишається доступною лише супер адміністратору. Зміна сповіщень не змінює доступ чи `IsSuperAdmin`, перевіряє version і записується в аудит.

«Новий мешканець» - завершена реєстрація, автоматично схвалена або подана на перевірку залежно від режиму; «нова заявка» - її успішне створення; «новий адміністратор» - створення неактивного запису після першого входу з підтвердженим email. Сповіщення про нову заявку містить також її повний опис між рядками `~~~~~`, включно з переносами рядків. Адміністративне сповіщення надсилається лише активним адміністраторам, які підписані на нові заявки; видимість заявки для мешканців не змінюється, а сервісні повідомлення не містять опису. Ці події атомарно записуються в приватний outbox разом із даними й не відтворюються заднім числом. Воркер формує завдання активним адміністраторам із відповідною підпискою та перед відправленням повторно перевіряє доступ, підписку й Chat ID. Типовий час доставки - 1–2 хвилини; для великого списку одержувачів або повторів довше. Після відкликання доступу, вимкнення підписки або зміни Chat ID старе завдання пропускається. Кілька адміністраторів з одним Chat ID можуть отримати окремі повідомлення в цей чат.

Для розгортання потрібен повний backend-деплой перед фронтендом: оновлюються IAM воркера й `ADMINISTRATORS_TABLE`. Міграція наявних адміністраторів не потрібна; відсутні поля читаються як порожній Chat ID і вимкнені підписки.

Під час першого входу створюється неактивний запис. `IsSuperAdmin` відсутній і читається як `false`; застосунок ніколи не записує це поле. Для першого супер адміністратора:

1. Зареєструйте обліковий запис у вебпанелі, підтвердьте email та увійдіть. Буде показано очікування доступу.
2. В **AWS Console → DynamoDB → osbb-requests-dev-administrators → Explore table items** знайдіть запис за своїм `Email` (або через `DirectoryIndex`, `Directory = ADMINS`).
3. Встановіть `IsActive` як **Boolean `true`** та додайте `IsSuperAdmin` як **Boolean `true`**. Зміна `IsSuperAdmin` виконується тільки безпосередньо в AWS Console.
4. Натисніть «Перевірити доступ» у панелі. З'явиться розділ «Адміністратори».

Наступний адміністратор так само створює й підтверджує акаунт і входить у панель; супер адміністратор знаходить його email і натискає «Надати доступ». Це надає право обробляти заявки та реєстрації, але не право керувати іншими адміністраторами. `IsSuperAdmin` не редагується в UI або API навіть супер адміністратором. IAM окремо забороняє Lambda запис цього атрибута, PutItem/DeleteItem у таблиці адміністраторів та дозволяє UpdateItem лише визначених звичайних полів.

```bash
# Локальна розробка (конфігурацію власного stage візьміть із outputs stack).
npm start --prefix src/Frontend
```

Порожня конфігурація `src/Frontend/src/assets/app-config.json` у source є шаблоном; для локальної розробки замініть її власними публічними API/Cognito ID без додавання конфігурації середовища до Git.

### Повідомлення мешканцям

Розділ «Повідомлення» (`/messages`) розташований після «Мешканці» й доступний активним адміністраторам із відповідним дозволом та супер адміністраторам. Форма надсилає звичайний текст (до 4096 символів, зі збереженням переносів рядків) схваленим мешканцям поточного комплексу зі списку «Зареєстровані мешканці». Аудиторія читається з GSI нової таблиці, що оновлюється із затримкою; нещодавно схвалений мешканець може не потрапити до розсилки, якщо його запис ще не з’явився в індексі. Незавершені й непідтверджені реєстрації не включаються. Реєстрації, схвалені після створення розсилки, не отримують її заднім числом.

Після відправлення форма очищується, а повідомлення з’являється в історії: текст, email автора й час створення, від новіших до старіших, до 25 на сторінці. Позначка «Передано на розсилку» підтверджує постановку в чергу, а не доставку кожному мешканцю. Історія зберігається без TTL. Повтор запиту з тим самим ID і текстом не створює нову розсилку.

Доставка використовує щохвилинний воркер сповіщень: одержувачі обробляються сторінками по 25, тимчасові помилки повторюються, `429` враховує `retry_after`, заблокований бот не зупиняє решту розсилки. Великі розсилки можуть тривати довше кількох хвилин; гарантії exactly-once немає. Результати доставки зберігаються 30 днів, невідправлені завдання - без TTL.

Для розгортання змін спочатку виконайте повний backend-деплой (новий дозвіл Query довідника мешканців для воркера та маршрут SPA у CloudFront), потім деплой фронтенду. Нова таблиця чи міграція даних не потрібні; наявні повідомлення не розсилаються повторно.

### Обмеження частоти API

API Gateway застосовує до кожного маршруту базовий ліміт 30 запитів за секунду з короткочасним сплеском до 60. Для `GET /admin/requests/export` діє окремий ліміт: 0,2 запиту за секунду (у середньому один за п’ять секунд), сплеск до двох. Ліміти спільні для всіх клієнтів відповідного маршруту; при перевищенні API Gateway може повернути HTTP 429, а панель запропонує повторити дію пізніше. Webhook Telegram використовує базові значення, тому за тривалого перевантаження повідомлення можуть доставлятися із затримкою через повторні спроби Telegram.

Тротлінг API Gateway працює за принципом best effort і не гарантує жорсткої межі або захисту від усіх DDoS-атак. HTTP API не підтримує безпосередньої інтеграції з AWS WAF та окремих лімітів за IP; для такого захисту потрібна інша архітектура. Під час атаки спільний ліміт маршруту може обмежити й звичайних користувачів. Значення задано в `serverless.yml`, змінюються деплоєм і потребують коригування за реальними метриками.

### Деплой фронтенду

Запускайте команди з кореня репозиторію. Потрібні Node.js 24, npm, Python 3, AWS CLI та активні AWS credentials потрібного акаунта (за потреби задайте `AWS_PROFILE`). Оператору потрібні дозволи читати outputs CloudFormation-стека, читати список об'єктів і завантажувати файли в S3-бакет фронтенду та створювати CloudFront invalidation.

Стек `osbb-requests-<stage>` має вже існувати й мати статус `CREATE_COMPLETE` або `UPDATE_COMPLETE`. Для першого розгортання або змін контракту API спочатку розгорніть backend та інфраструктуру:

```bash
npm ci
npm run deploy -- --stage dev --region eu-central-1
```

Для наступних суто frontend-змін достатньо:

```bash
npm ci --prefix src/Frontend
npm run check --prefix src/Frontend
python3 scripts/deploy-frontend.py --stage dev --region eu-central-1
```

Скрипт сам виконує production-збірку Angular і читає `HttpApiUrl`, `UserPoolClientId`, `UserPoolId`, `FrontendBucketName`, `FrontendDistributionId` та `FrontendUrl` з outputs стека. Він генерує публічний `app-config.json` тільки в `dist/osbb-admin/browser`, завантажує версійні ресурси в приватний S3-бакет, потім `index.html` і конфігурацію з `Cache-Control: no-store,max-age=0`, і створює invalidation для `/`, `/index.html`, `/assets/app-config.json`. Попередні файли з хешами залишаються для відкритих браузерних сесій. Токени Telegram скрипту не потрібні.

Для іншого середовища передайте відповідні `--stage` і `--region`; ID ресурсів вручну підставляти не потрібно. Скрипт не створює інфраструктуру й не оновлює Lambda API або бота. Якщо змінено поля запитів чи відповіді API, backend потрібно розгорнути перед фронтендом. Множинний фільтр передає `status=New,InProgress` і потребує актуального API; один статус і відсутність фільтра залишаються сумісними. Поля `scope`, `buildingNumber`, `floor` також потребують актуального API.

Після успішного завантаження скрипт виведе URL панелі. Для dev: https://d2aeffc3h35yt5.cloudfront.net. Дочекайтеся завершення invalidation у CloudFront, відкрийте сторінку й перевірте вхід, завантаження даних і змінений сценарій. Сам факт завантаження файлів у S3 ще не підтверджує сумісність з API. Автоматичного frontend-деплою в GitHub Actions зараз немає.

### Пріоритети заявок і перший деплой сортування

У вебпанелі заявки впорядковані за пріоритетом: «Терміновий», «Високий», «Звичайний», «Низький», а всередині групи - від новіших до старіших. Високий пріоритет має жовтий лівий бордер і бейдж поруч із категорією, терміновий - червоний. У редакторі всі значення пріоритету відображаються бейджами; вибраний елемент зберігає колір. Після зміни пріоритету список оновлюється з першої сторінки. Списки Telegram зберігають свій поточний порядок.

Глобальний порядок і пагінацію забезпечує GSI `BuildingPriorityRequestsIndex`. Перший деплой потребує заповнення атрибута сортування наявних заявок. Щоб вони залишалися доступними під час міграції, спочатку розгорніть backend у сумісному режимі сортування за датою:

```bash
npm run deploy -- --stage dev --region eu-central-1 --param="requestSortMode=Date"
python3 scripts/backfill-request-priority.py --stage dev --region eu-central-1
python3 scripts/backfill-request-priority.py --stage dev --region eu-central-1 --apply
python3 scripts/backfill-request-priority.py --stage dev --region eu-central-1
```

Останній dry run має показати 0 записів до оновлення. Дочекайтеся ACTIVE нового індексу й завершення його backfill, після чого перемкніть API на новий порядок і розгорніть фронтенд:

```bash
npm run deploy -- --stage dev --region eu-central-1 --param="requestSortMode=Priority"
python3 scripts/deploy-frontend.py --stage dev --region eu-central-1
```

Типове значення `requestSortMode` - `Priority`; `Date` призначено для початкового заповнення індексу або відкату сортування. Якщо BUILDING_ID перевизначено, додайте до міграції `--complex-id`. Скрипт оновлює лише заявки свого комплексу, має dry run, перевіряє незмінність payload перед записом та безпечно повторюється. Він додає індексні атрибути, не змінюючи payload, version, історію чи TTL. Після переключення оновіть відкриті сторінки панелі, щоб скинути курсори старого порядку. Усі наступні створення й зміни пріоритету автоматично підтримують новий ключ.

### Міграції даних після оновлень

Для вже схвалених мешканців після першого деплою цієї функції заповніть каталог (скрипт не змінює профілі, membership чи ролі адміністраторів і не виводить персональних даних):

```bash
python3 scripts/backfill-residents.py --stage dev --region eu-central-1
```

Нові схвалення через панель або `manage-residents.py` додають мешканця до каталогу тією самою транзакцією, що й рішення. Повторний запуск міграції пропускає вже наявні записи. Для власного `BUILDING_ID` передайте скрипту `--building-id`.

Для заявок, створених до появи індексу адмінпанелі, після деплою виконайте міграцію (спочатку dry run):

```bash
python3 scripts/backfill-request-index.py --stage dev
python3 scripts/backfill-request-index.py --stage dev --apply
```

Тільки ця одноразова операторська міграція використовує Scan. API та бот працюють через GetItem/Query; Lambda не отримують Scan. Міграція не видаляє заявки та перевіряє незмінність payload перед записом індексних атрибутів.

## Конфігурація та секрети

Одне середовище - один бот та один житловий комплекс із чотирьох будинків. Перед розгортанням задайте:

```bash
export TELEGRAM_BOT_USERNAME=YourOsbbBot  # без @
export BUILDING_ID=osbb-example # історична назва змінної: ідентифікатор комплексу, не номер будинку
# Операційні сповіщення використовують сервісний чат 38627946
# і SSM-параметр /shared/telegram/service-bot-token.
# Їх можна перевизначити Serverless params serviceNotificationChatId/serviceBotTokenParameter.
```

Для `dev` у `serverless.yml` задано username `zeleniy_ostriv2_bot`; для інших stage за замовчуванням - `OsbbRequestsBot`. `TELEGRAM_BOT_USERNAME` перевизначає значення відповідного stage. Building ID за замовчуванням - `osbb-requests-<stage>`. Команди з адресацією `@username` потребують правильного username. Для імен без `@` значення username не впливає на маршрутизацію.

У AWS Systems Manager Parameter Store створіть два `SecureString` у тому самому регіоні:

- `/osbb-requests/dev/telegram-bot-token` - токен від BotFather;
- `/osbb-requests/dev/telegram-webhook-secret` - випадковий секрет із символів `A–Z`, `a–z`, `0–9`, `_`, `-`, довжиною 1–256.

Для іншого stage замініть `dev`. Конфігурація розрахована на стандартний ключ `aws/ssm`; для власного KMS-ключа додайте точні `kms:Decrypt` permissions у відповідну роль та key policy. Lambda отримують тільки імена параметрів і читають секрети під час роботи з кешем до п'яти хвилин. Секрети не підставляються в Serverless-артефакти. Значення вводьте через захищений інтерфейс AWS або свій менеджер секретів; не додавайте їх у Git, журнали чи shell history.

## AWS-пакування й розгортання

Потрібні AWS credentials та автентифікація Serverless Framework v4.

```bash
npm run package -- --stage dev --region eu-central-1
npm run deploy -- --stage dev --region eu-central-1
```

`package` генерує CloudFormation у `.serverless/` без розгортання; потребує AWS credentials. `deploy` створює чотири Lambda (включно з доставкою сповіщень), щохвилинний EventBridge Scheduler, HTTP API, FIFO-чергу та DLQ, дві таблиці DynamoDB із point-in-time recovery, Cognito, приватний S3/CloudFront для панелі, окремі IAM-ролі та CloudWatch logs. Регіон за замовчуванням - `eu-central-1`, stage - `dev`.

Після розгортання зареєструйте в Telegram `setWebhook` URL `<HTTP API URL>/telegram/webhook`, вкажіть той самий `secret_token` і `allowed_updates: ["message"]`. Токен бота та webhook secret передавайте з менеджера секретів без журналювання. Перевірка реального обміну з Telegram виконується після налаштування секретів і деплою.

## Реєстрація та надання доступу

Режим схвалення мешканців визначається Serverless-параметром `residentApprovalMode`: типово `Automatic`, для ручного процесу - `Manual`. Він передається лише воркеру команд як `RESIDENT_APPROVAL_MODE`; на Cognito та схвалення адміністраторів не впливає. Для повернення ручного режиму виконайте backend-деплой з явним параметром:

```bash
npm run deploy -- --stage dev --region eu-central-1 --param="residentApprovalMode=Manual"
```

Для постійного налаштування змініть параметр відповідного stage у `serverless.yml`; без CLI override діє значення з конфігурації (зараз `Automatic`). Автоматизація стосується лише нових завершень реєстрації: наявні Pending не схвалюються заднім числом і залишаються у ручному списку.

1. Мешканець надсилає `/start`.
2. Бот пояснює поточний режим надання доступу та приватність профілю, і показує кнопку «Поділитися номером телефону».
3. Приймається лише власний Telegram-контакт: `contact.user_id` має збігатися з відправником. Введений текстом номер або чужа контактна картка не приймаються. Номер нормалізується до міжнародного формату з `+`.
4. Мешканець окремими повідомленнями вводить ім’я та прізвище, обирає будинок 4Б, 4В, 4Г або 4Д й вводить номер квартири цілим додатним числом. Потім він може ввести email або натиснути «Пропустити». Формат email перевіряється, але володіння адресою не підтверджується. Після цього мешканець обирає тип: «Власник», «Член родини» або «Орендар». Власник переходить у `Pending` до рішення адміністратора; член родини та орендар у режимі `Automatic` отримують стан `Approved`. У режимі `Manual` усі переходять у `Pending`. Будинок проживання зберігається в `BuildingNumber`, квартира - в `ApartmentNumber`; історичний `BuildingId` залишається ID комплексу. У старих профілях нові поля порожні: міграція та повторна реєстрація не потрібні.
5. У режимі `Manual` адміністратор переглядає дані й схвалює або відхиляє запит; мешканець перевіряє рішення через `/start`. За автоматичного схвалення бот одразу підтверджує доступ, а мешканець з’являється у списку зареєстрованих.

`/start` продовжує незавершений діалог. `/cancel` скасовує чернетку та очищує телефон й імена у поточному профілі; копії в черзі/receipt видаляються за своїми строками зберігання. Відхилений запит можна подати знову через `/start`. Наявний запит на перевірці не перезаписується, а повторні update не просувають діалог удруге. Телефон є підтвердженим контактом акаунта Telegram; належність до комплексу й правильність імені перевіряє адміністратор.

Кнопка «Експортувати в Excel» у розділах заявок і мешканців завантажує `.xlsx` з усіма сторінками вибраного списку. До назви файлу додається дата за Києвом, наприклад `Заявки-08-11-2026.xlsx`. Для заявок використовуються фільтри, застосовані кнопкою «Знайти»; експорт містить ім’я, прізвище, телефон і квартиру автора з поточного профілю; для зареєстрованих мешканців - поточні фільтр будинку та сортування. Окремо можна експортувати список реєстрацій, що очікують перевірки, з урахуванням вибраного будинку. Файл заявок формує сервер за одним запитом із застосованими фільтрами; файли мешканців також формуються сервером за одним запитом з урахуванням фільтрів і сортування. Файли можуть містити контактні дані; Telegram Chat Id до експорту мешканців не включається. Експорт заявок читає всі сторінки на сервері, а експорт мешканців читає відфільтрований довідник на сервері; дані, які змінюються під час читання, не утворюють атомарного знімка. Експорт обмежений розміром файлу 4 МіБ і часом обробки 25 секунд; якщо експорт завеликий або не встигає завершитись, звузьте фільтри.

У розділі «Мешканці» є два списки: «Зареєстровані мешканці» для схвалених реєстрацій і «Очікують перевірки» для нових запитів. За замовчуванням відкривається список зареєстрованих мешканців. У кожному списку картка показує ім’я та прізвище, тип мешканця, будинок і квартиру. Натискання відкриває повну інформацію, зокрема телефон, email, Telegram Chat Id, згоду та дату реєстрації; у вікні доступні дії відповідно до прав адміністратора. Для підтверджених мешканців окремо показується адміністратор, який схвалив реєстрацію, або позначка автоматичного схвалення; за відсутності аудиту зазначається, що даних немає. Доступні сортування за датою реєстрації або прізвищем (український алфавіт), іконки напрямку за зростанням/спаданням і фільтр за будинками 4Б, 4В, 4Г, 4Д або «Не зазначено». Типово новіші реєстрації першими, усі будинки. Зміна параметрів одразу повертає на першу сторінку, до 25 записів на кожній; профілі без прізвища розміщуються наприкінці при сортуванні за прізвищем. Панель отримує поточну сторінку з API; сервер застосовує сортування й фільтри до довідника. Кнопка оновлення перечитує сторінку; обсяг читання DynamoDB пропорційний кількості мешканців. Доступ до обох списків мають лише активні адміністратори. Список зареєстрованих відображає підтверджені реєстрації, а не окрему перевірку поточного membership. В обох списках показується Telegram Chat Id мешканця (для приватного діалогу з ботом він збігається з його Telegram user ID). Це поле доступне лише активним адміністраторам; у публічних заявках і повідомленнях мешканцю його немає. Реєстрації перевіряються у розділі «Мешканці» вебпанелі. Як операторський резерв залишається скрипт зі своїми AWS credentials:

```bash
# Показує приватні ім’я, прізвище, телефон і reference запитів на доступ.
python3 scripts/manage-residents.py --stage dev list

# reference береться зі списку; мешканцю не потрібно знати або передавати Telegram ID.
python3 scripts/manage-residents.py --stage dev approve <reference>
python3 scripts/manage-residents.py --stage dev reject <reference> --reason 'Уточніть прізвище'
```

Якщо `BUILDING_ID` перевизначено, перед підкомандою додайте `--building-id <building>`. За замовчуванням використовується `osbb-requests-<stage>`. Список містить персональні дані - він призначений тільки для адміністратора, не для публікації чи CI-журналів.

Скрипт читає реєстрації з нової таблиці мешканців; список використовує GSI `ResidentsByDate`, який може оновлюватися із затримкою, і узгоджено перечитує кожен профіль. Скрипт атомарно змінює стан реєстрації та membership у новій таблиці, прибирає запит зі списку очікування та зберігає аудит із AWS-ідентичністю оператора. Застаріле рішення не перезапише змінений профіль. Відхилення потребує пояснення. При схваленні та сама транзакція додає сповіщення мешканцю в Telegram. Стан і причина відхилення доступні мешканцю через `/start`.

Бот не має команди, яка надає доступ самому користувачу. Адміністративний скрипт потребує AWS-дозволів на `sts:GetCallerIdentity` та відповідні `dynamodb:GetItem`, `Query`, `PutItem`, `UpdateItem`, `DeleteItem` для обох таблиць свого stage та Query індексу `ResidentsByDate` нової таблиці. Ці адміністративні дозволи не додаються Lambda або мешканцям.

## Відмови та експлуатація

Повторна обробка одного update не створює другу заявку. При неоднозначному мережевому результаті `sendMessage` або збої між доставкою та записом `delivered` повторне Telegram-повідомлення можливе: Telegram не має idempotency key для цього виклику.

Черга утримує команди до чотирьох днів; після п'яти невдалих обробок повідомлення переходить у DLQ зі зберіганням до 14 днів. Звичайний retry - після 180 секунд; для Telegram `429` враховується `retry_after` через visibility timeout (до ліміту SQS 12 годин). Після усунення причини помилки оператор має виконати redrive DLQ до основної черги. Не запускайте довільні нові команди зі старих payload: відновлюйте оригінальні повідомлення в межах 30-денного строку дедуплікації.

Записи відповідей та дедуплікації мають TTL 30 днів і можуть містити приватний текст заявки. TTL видаляється DynamoDB асинхронно. Заявки, історія, членство й реєстраційні профілі TTL не мають. Реєстраційні профілі та приватний список адміністратора містять ПІБ і телефон; вони не додаються до загальнодоступних заявок. Політику довгострокового зберігання цих даних потрібно визначити окремо. Черга й DLQ також містять текст команди - доступ до них лише для операторів і відповідних Lambda.

Помилки журналюються за типом та SQS Message ID без тексту команд, контактів і секретів. Для помилок Telegram CloudWatch додатково містить контрольовану категорію та HTTP-статус, якщо він відомий; відповідь Telegram і повідомлення винятку не записуються. TelegramServiceNotifier зі спільного проєкту повідомляє про неочікувані помилки webhook, команд, доставки outbox та Admin API у сервісний чат `38627946`, як у `olx-watcher`. Використовується окремий сервісний бот: його токен читається з SSM SecureString `/shared/telegram/service-bot-token` лише під час помилки, кешується в пам’яті до п’яти хвилин і не потрапляє до environment, артефактів або логів. IAM кожної Lambda дозволяє GetParameter тільки цього додаткового параметра; Admin API не отримує токен бота мешканців.

Налаштування Serverless: `serviceNotificationChatId` і `serviceBotTokenParameter` (типові значення вище) передаються в Lambda як `SERVICE_NOTIFICATION_CHAT_ID` та `SERVICE_BOT_TOKEN_PARAMETER`. За потреби перевизначте параметри відповідного stage. Попередня змінна `ADMIN_TELEGRAM_CHAT_ID` більше не використовується. Для активації виконайте звичайний backend-деплой із явним stage; міграції, frontend-деплой і зміни меню не потрібні. SSM-параметр має існувати у регіоні розгортання; для власного KMS key потрібен окремий дозвіл decrypt.

Сповіщення містить Lambda, stage, контрольовану назву етапу, тип винятку, ID запиту/події та до п’яти назв методів зі стеку. Текст винятку, вкладені payload, HTTP URL, контакти, паролі та токени не передаються. Очікувані 4xx API та коректно відкладений Telegram 429 не створюють сервісних повідомлень; збій відкладання, недоступний одержувач і повтор доставки повідомляються. Надсилання має окремий таймаут дві секунди, без повторів: його збій лише журналюється і не змінює 503, FIFO partial failure, backoff або повтор Lambda/Scheduler. Webhook та API залишають дві секунди на цей виклик у межах 10-секундного timeout. Сповіщення є best effort; hard timeout/OOM/помилки запуску Lambda та недоступність самого сервісного бота потребують контролю через CloudWatch і DLQ. Окремі alarm destinations ще не налаштовані.

Видалення середовища:

```bash
npm run remove -- --stage dev --region eu-central-1
```

DynamoDB має `DeletionPolicy: Retain`: дані й витрати на таблицю зберігаються після видалення stack. Повторне створення stack з тим самим іменем таблиці потребуватиме імпорту збереженої таблиці або окремого рішення оператора. Секрети SSM також не видаляються автоматично.

### Зміна та видалення профілю мешканця

Схвалений мешканець може виконати `/edit_profile`: підтвердити власний контакт Telegram і повторно ввести ім’я, прізвище, будинок та номер квартири і за бажанням email. Пропуск email очищує попередню адресу. Поточний профіль залишається чинним до завершення всіх кроків; повторне схвалення адміністратором не потрібне. `/cancel` або кнопка «Скасувати» очищує чернетку, не змінюючи старого профілю. Перехід до іншої явної команди також скасовує цей діалог. Оновлення синхронізує приватний профіль, поточну реєстраційну копію та каталог мешканців і зберігає початкову дату схвалення.

`/delete_profile` вимагає натискання «Видалити мої дані». Після підтвердження очищуються ім’я, прізвище, телефон, email, будинок і квартира у трьох поточних копіях профілю, а чернетка видаляє введені дані. Доступ відкликається, меню повертається до незареєстрованого стану з `/start`; потрібна повна повторна реєстрація. Внутрішній Telegram ID, номери та вміст заявок зберігаються. Видалений профіль має стан `Deleted` і не відображається у списку зареєстрованих. У деталях та історії збережених заявок показується «Мешканець видалив свої дані». Після завершення й схвалення повторної реєстрації у всіх заявках цього Telegram-користувача, включно зі старими, показуються поточні ПІБ, будинок і квартира. До схвалення нового профілю позначка видалення зберігається.

Це очищення актуального профілю, а не повне видалення всіх історичних даних акаунта: попередні receipt команд, вміст SQS/DLQ, резервні копії, раніше надіслані Telegram-повідомлення та архівні реєстрації з інших спроб ця команда не змінює. Receipt мають TTL 30 днів, черги й резервні копії - власні строки зберігання. Текст створених заявок зберігається навіть якщо мешканець раніше сам написав у ньому персональні дані.

Для розгортання потрібні backend і фронтенд, потім оновлення меню скриптом `configure-telegram-menu.py --include-residents` для відповідного stage (спочатку dry run, потім `--apply`). Нових таблиць немає; для раніше видалених профілів потрібне одноразове узгодження доступу, описане нижче.

Після першого деплою поведінки з відкликанням доступу узгодьте профілі, видалені за попередньої версії (використовується Query каталогу, поточний профіль перевіряється перед записом; відновлені профілі пропускаються):

```bash
python3 scripts/revoke-deleted-residents.py --stage dev --region eu-central-1
python3 scripts/configure-telegram-menu.py --stage dev --region eu-central-1 --bot-username zeleniy_ostriv2_bot --include-residents --apply
```

Для власного BUILDING_ID додайте `--building-id` до міграції та `--complex-id` до налаштування меню. Скрипт меню тепер також повертає персональне меню видалених мешканців до загального стану; інакше старий chat scope Telegram міг би перекривати загальний список команд. Дані заявок і адміністраторів ці процедури не змінюють.

Для переходу на категорії «Електрика МЗК», «Сантехніка МЗК», «Ліфти», «Прибирання МЗК» та «Інше» після оновлення backend і фронтенду виконайте міграцію наявних заявок, спочатку без запису:

```bash
python3 scripts/migrate-request-categories.py --stage dev --region eu-central-1
python3 scripts/migrate-request-categories.py --stage dev --region eu-central-1 --apply
```

Колишня категорія «місця загального користування» переходить до «Інше», інші зіставляються за назвою. Скрипт обмежений одним комплексом (`--complex-id` за потреби), оновлює категорію у payload та індексному полі, збільшує версію, перевіряє відсутність паралельних змін і допускає повторний запуск. Для невідомої категорії виконання зупиняється; перед `--apply` перевірте dry run. Чернетки та старі назви, введені вручну, під час завершення створення нормалізуються до нових категорій.

Реєстрація починається з ознайомлення з умовами обробки персональних даних та натискання кнопки згоди. До згоди ввести дані й завершити реєстрацію неможливо; боту достатньо команди `/cancel`, щоб скасувати її. Час згоди та версія тексту зберігаються в профілі; час показується адміністраторам на сторінці мешканців. Для старих профілів без такого запису показується «не зафіксована», їхній доступ автоматично не змінюється. Якщо реєстрацію було розпочато раніше й не завершено, після згоди її можна продовжити з попереднього кроку. При видаленні даних профілю запис згоди також видаляється; системні черги та receipt мають власні строки зберігання.

Схваленим мешканцям команда `/account` («Мій особовий рахунок») показує номер `000219` + номер будинку малими літерами + номер квартири з доповненням нулями до трьох цифр, наприклад `0002194б001`. Якщо в профілі немає коректного будинку чи квартири, бот запитує тільки необхідні дані, після чого умовно оновлює всі поточні копії профілю та показує номер. Підтримуються квартири 1–999. `/cancel` скасовує введення. Після backend-деплою застосуйте скрипт `configure-telegram-menu.py` з `--include-residents`, щоб оновити меню всім зареєстрованим; без цього меню окремого мешканця оновиться під час наступного повідомлення боту.

Після введення імені та прізвища під час нової реєстрації користувач обирає тип: «Власник», «Член родини», «Орендар» або «Працівник ОСББ». Працівник не вводить будинок і квартиру. Власник і працівник очікують рішення адміністратора, до схвалення доступ до функцій бота не надається; членів родини й орендарів у стандартному режимі `Automatic` схвалюють автоматично. Режим `Manual` зберігається як операторське перевизначення для всіх нових реєстрацій. Попередні профілі без поля типу інтерпретуються як «Член родини» без перезапису даних та зміни доступу; наявні Pending залишаються на перевірці. Під час редагування профілю тип зберігається. Тип показано на сторінці мешканців і в обох Excel-експортах після імені. Кнопка «Очікують перевірки» показує загальну кількість заявок у приватному каталозі; кількість оновлюється при завантаженні розділу, оновленні та після рішення адміністратора.

Підтверджені власники можуть створити через `/new` приватну заявку категорії «Замовлення ключів»: після вибору локації потрібно обрати «Магніт» або «Перепустка» та ввести додатну кількість. Іншим мешканцям категорія не пропонується; перед завершенням і під час збереження перевіряються тип, версія профілю та активність доступу. Замовлення не публікується в `/complex`. В адмінпанелі розділ «Заявки» має підрозділи «По комплексу» і «Замовлення ключів»; фільтри, пагінація та експорт застосовуються до обраного підрозділу. Адміністратор не може зробити замовлення ключів публічним. Наявні заявки не змінюються.

Команда `/contacts` («Контакти майстрів») доступна в меню всім користувачам, зокрема до реєстрації, і показує телефони сантехніка/електрика та ліфтера. Після backend-деплою оновіть меню скриптом `configure-telegram-menu.py --include-residents` для відповідного stage.

Головне меню бота також відображається як постійна клавіатура з кнопками: набір кнопок залежить від статусу реєстрації; меню команд містить лише `/start`, `/help` і `/cancel`. Кнопки запускають ті самі команди; введення `/команди` залишається доступним. Під час активного діалогу показуються кнопки поточного кроку або поле введення, а після завершення чи скасування повертається головна клавіатура. Відповіді, що збігаються з назвою кнопки, під час діалогу залишаються введеними даними. Клавіатура з’являється при наступній взаємодії з ботом; сповіщення не замінюють клавіатуру активного діалогу.

У списках `/my` та `/complex`, якщо є продовження, бот показує кнопки «Скасувати» і «Далі». «Далі» відкриває наступну сторінку відповідного списку, «Скасувати» завершує перегляд і повертає головне меню; після останньої сторінки головне меню також повертається. Команди продовження в тексті залишаються сумісними. Стан кнопок зберігається окремо для мешканця й комплексу на 30 днів та не містить заявок.

Бот перевіряє, чи є ще доступна заявка, і не показує «Далі», коли досягнуто кінця списку. Заявки можуть змінитися після цієї перевірки; якщо обмеження до 25 запитів не дозволило визначити наявність наступної, продовження зберігається, щоб не приховати можливі заявки. Така перевірка може вимагати додаткових читань DynamoDB.

У розділі зареєстрованих мешканців фільтри будинку та типу мешканця застосовуються до списку й експорту Excel для всіх сторінок. Старі профілі без типу вважаються членами родини.

У списку «Очікують перевірки» фільтр будинку застосовується на сервері до списку та експорту Excel; для відсутньої адреси доступне «Не зазначено». Лічильник вкладки показує загальну кількість.

На сторінці заявок API повертає до 25 відповідних заявок, курсор і показники «Усі», «Нові» та «В роботі» для застосованих фільтрів і обраного підрозділу. Підрахунок виконується на сервері шляхом читання всіх відповідних записів індексу, тому його вартість і час зростають разом із кількістю заявок; одночасні зміни не утворюють атомарного знімка. Перехід між сторінками й оновлення перераховують показники. Експорт працює окремо та включає всі відфільтровані заявки.

Працівник ОСББ після схвалення користується функціями бота; замовлення ключів залишається доступним лише власникам. Під час редагування профілю працівник повторно вводить контакт, ім’я, прізвище та необов’язковий email, а тип, згода й доступ зберігаються. Для незавершених реєстрацій з попереднім порядком кроків порядок не змінюється.

Супер адміністратор налаштовує доступ до заявок комплексу, замовлень ключів, зареєстрованих мешканців, реєстрацій на перевірці та розсилок. Перевірки виконуються в API, зокрема для деталей і змін заявки; старі облікові записи без налаштувань зберігають доступ до заявок і мешканців, але не до розсилок. Супер адміністратор має всі дозволи; `IsSuperAdmin` змінюється лише через AWS Console. Налаштування мають перевірку версії й аудит. Після backend-деплою потрібно розгорнути frontend; передача ролей відбувається через API.

Адміністратор із доступом до мешканців на перевірці може через «Редагувати дані» змінювати ім’я, прізвище та тип як мешканців на перевірці, так і зареєстрованих мешканців (за наявності доступу до відповідного списку). Зміна не впливає на стан реєстрації або згоду. «Історія змін» містить адміністратора й час, попередній і новий тип та відмітки зміни імені й прізвища без збереження їхніх попередніх значень.

### Очищення старих записів мешканців

Скрипт `scripts/cleanup-legacy-residents.py` підготовлений для окремого етапу після переходу на таблицю `residents`. До запуску перевірте, що всі Lambda та операторські інструменти використовують нову таблицю, жодна стара версія не працює, стан системи стабільний, а PITR або інша резервна копія перевірена. Переконайтеся, що незавершені розсилки зі старим курсором завершилися; скрипт додатково перевіряє активні завдання, але не може заборонити появу старого читача після перевірки. Відкат на старий код без зворотного відновлення даних неможливий.

Спочатку виконайте лише перевірку з потрібним stage та регіоном:

```bash
python3 scripts/cleanup-legacy-residents.py --stage dev --region eu-central-1
```

Результат містить лише агреговані лічильники. `eligible` — записи, які можна перевірено видалити, `missing` — записи без цільової копії, `unsafe` — розбіжності або непідтверджена належність. Перш ніж застосовувати, дослідіть усі `missing` та `unsafe`: жодного запису не буде видалено, якщо початкова перевірка знайде хоча б один такий запис. Змінені або вже видалені після переходу проєкції можуть не мати відповідної копії і потребують окремого аналізу. Сканування не є атомарним знімком; при одночасних змінах повторіть перевірку.

Лише після окремого рішення про очищення використовуйте `--apply --confirm-stage dev --confirm-cutover --max-deletes N`, де N — додатна межа кількості видалень за один запуск. Скрипт повторно перевіряє всі записи, після чого кожне видалення старого запису та перевірка незмінності знайденої копії виконуються в одній транзакції. При помилці вже виконані транзакції не відкочуються; повторний запуск пропускає видалені записи. `limited` показує кількість записів поза межею цього запуску. Заявки, receipt та outbox не входять до переліку дозволених ключів. Скрипт не перевіряє автоматично стан PITR, версії всіх читачів чи відсутність ручних операторських дій; `--confirm-cutover` підтверджує, що оператор зробив це сам. Оператору потрібні `Scan`, `Query`, `GetItem`, `DeleteItem` і дозволи на транзакційні умови відповідних таблиць. Після очищення старі копії можуть залишатися в резервних копіях до завершення строку їх зберігання.

### Підготовка таблиці мешканців

Стек створює `osbb-requests-<stage>-residents` із PITR та індексами `ResidentsByDate` і `ResidentsByName`. Бот, адмінпанель та операторський скрипт записують нові й змінені профілі в нову таблицю з перевіркою версії. Перед перемиканням списків необхідно перенести та звірити профілі й пов’язані записи наведеними нижче скриптами. Перевірка доступу та нові аудиторії розсилок читаються з `residents`; незавершені розсилки зі старими курсорами завершуються через `command-data`. Операторським обліковим записам для зміни реєстрацій і відкликання доступу тепер потрібен дозвіл `dynamodb:PutItem` для нової таблиці.

Для перенесення наявних профілів після розгортання подвійного запису використовуйте операторський скрипт з явним stage і регіоном:

```bash
python3 scripts/migrate-residents-table.py --stage dev --region eu-central-1
python3 scripts/migrate-residents-table.py --stage dev --region eu-central-1 --apply
python3 scripts/migrate-residents-table.py --stage dev --region eu-central-1
```

Перший і останній запуски лише перевіряють дані. Скрипт виводить агреговані кількості, не персональні дані. Він читає поточні профілі через операторський Scan, перевіряє комплекс і версію, а запис у нову таблицю виконує в транзакції з перевіркою незмінності старого профілю. Новішу копію не перезаписує; у разі конфлікту повторює читання або завершується з помилкою. Повторні запуски ідемпотентні. Видалені персональні дані не копіюються. Для переходу до читання з нової таблиці потрібні окрема звірка й зміна коду; сам цей скрипт читання не перемикає. Для іншого ID комплексу додайте `--complex-id`. Оператору потрібні права DynamoDB Scan/GetItem для старої таблиці та GetItem/PutItem для нової; транзакційні умови також перевіряються на відповідних таблицях.

Пов’язані записи мешканців копіюються окремо: поточні та історичні реєстрації, рішення, події історії, membership, діалоги профілю та старі проєкції списків. Вони зберігаються в новій таблиці з усіма початковими атрибутами у `recordData`; `ResidentRecordsByGroup` дозволяє знайти записи конкретної реєстрації, мешканця або комплексу. Після переходу старі записи зберігаються як історичні копії та не оновлюються.

Списки мешканців адмінпанелі читають `ResidentsByDate`, повертають по 25 записів і загальну кількість після фільтрів; пагінатор дозволяє перейти на будь-яку сторінку за номером і показує поточну та загальну кількість сторінок відповідно до фільтрів. Для точного підрахунку й українського сортування сервер читає весь відповідний розділ індексу при кожному запиті, тому DynamoDB витрачає ресурси пропорційно кількості записів. Експорт окремим запитом формує файл із усіх відфільтрованих записів на сервері. GSI оновлюється асинхронно, тому не забезпечує миттєвої видимості та незмінного знімка між сторінками. Деталі погодження та історія мешканців також читаються з нової таблиці. Бот читає профілі, діалоги та доступ з нової таблиці, як і API дані авторів; незавершені розсилки зі старими курсорами можуть використовувати `command-data`, тому видаляти звідти записи мешканців поки не можна.

```bash
python3 scripts/migrate-resident-records.py --stage dev --region eu-central-1
python3 scripts/migrate-resident-records.py --stage dev --region eu-central-1 --apply
python3 scripts/migrate-resident-records.py --stage dev --region eu-central-1
```

Перший і третій запуски лише перевіряють записи. Скрипт не виводить персональних даних, перевіряє власність комплексу, не перезаписує наявні копії та умовно порівнює оригінал у транзакції. Конфлікти чи записи з невстановленим комплексом потребують розгляду. Після копіювання потрібні окремі звірка й перемикання всіх залежних читань і операцій; скрипт нічого не видаляє. Стару таблицю повністю видаляти не можна, оскільки вона містить заявки й інші дані.

Адміністратор може окремо підписатися на нові заявки по комплексу та замовлення ключів. Для наявних налаштувань без `NotifyNewKeyOrders` використовується значення попередньої підписки `NotifyNewRequests`; після збереження налаштування працюють незалежно. Події `NewRequest`, уже записані до черги до оновлення, доставляються за попередньою підпискою на заявки.

У кожному списку мешканців панель показує загальну кількість, власників, членів родини, орендарів та працівників ОСББ. Показники враховують вибраний будинок, але не фільтр типу; сам список і експорт застосовують обидва фільтри. Підрахунок використовує той самий прохід індексу, що й завантаження сторінки.

Перед розгортанням змін читання слід повторно звірити профілі й пов’язані записи обома міграційними скриптами у режимі dry-run. Нові розсилки використовують GSI `ResidentRecordsByGroup` та узгоджену перевірку кожного кандидата в новій таблиці. GSI не підтримує узгодженого читання, тому через затримку індексу деякі придатні одержувачі можуть бути пропущені; старі курсори продовжують читатися зі старого каталогу.
